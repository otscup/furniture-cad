## 二、抓到的 4 个真实问题（都已修复 + 加了防复发断言）

这一节是本次 Spike 最有价值的产出 —— 这些问题如果不做实测，会在 Phase 3~5 才炸，那时返工成本是现在的 10 倍。

### 问题 1（严重）· 标注文字放大 100 倍

**现象**：图纸上总高标注写的是 `240000`，而模型是 2400。
**根因**：`ezdxf.new(..., setup=True)` 内置的 `EZDXF` 标注样式里 `dimlfac = 100`。我复制它建 `FURN` 样式时继承了这个值，DIMENSION 的文字 = 实测值 × 100。
**危害等级**：★★★ 直接送厂 = 全部报废。
**修复**：`ds.dxf.dimlfac = 1.0`
**防复发**：验证脚本新增 `[8b]` —— 逐个 DIMENSION 比对"图上文字"与"实测值"，不等即 FAIL。
**教训**：**"引用了默认样式"是一种隐蔽的隐式假设。** 所有 factory 默认值都必须显式覆盖，不能靠"应该是 1 吧"。

### 问题 2（严重）· 中文被写成 `\U+XXXX` 转义

**现象**：ezdxf 默认 `doc.encoding = cp1252`，中文被序列化成 `\U+4e3b\U+5367...`，回读也是转义串。
**实测对照**（这就是选型依据）：

| 版本 | 编码 | 中文写入方式 | 回读正确 |
|---|---|---|---|
| R2000 | auto (cp1252) | ❌ `\U+XXXX` 转义 | ❌ 回读是转义串 |
| R2000 | **gbk + ANSI_936** | ✅ GBK 原生字节 | ✅ |
| **R2007** | auto | ✅ **UTF-8 原生字节** | ✅ |
| R2013 | auto | ✅ UTF-8 原生字节 | ✅ |

**额外发现（决定主交付版本）**：GBK 版被 JS 解析器 `dxf-parser` 读成乱码 —— 因为它只按 UTF-8 解码、**不认 `$DWGCODEPAGE`**。AutoCAD / 中望 / 浩辰认，但很多现代轻量解析器不认。

**结论**：
- **主交付 = R2007 (AC1021, 原生 UTF-8)**。R2007 是 2007 年的格式，2026 年不存在兼容顾虑，且编码零歧义。
- **兼容备用 = R2000 + GBK (ANSI_936)**，只给确认识别 $DWGCODEPAGE 的老软件。
- 我们自己的 Web DXF 阅读器（Phase 1）必须**只支持 UTF-8 路径**，遇到 GBK 文件要么转换要么明确报错，绝不静默乱码。

### 问题 3（中）· ACI 颜色 7 在白底上隐形

**现象**：第一次渲染 PNG，尺寸标注**完全看不见**。DIM 图层用了 ACI 颜色 7。
**根因**：颜色 7 是"黑/白随背景反转"。AutoCAD 模型空间黑底 → 白线可见；白色图纸/白底渲染 → 白线隐形。
**处理**：预览渲染改深色底（模拟 AutoCAD 模型空间）。
**对架构的影响**：出图时的颜色策略必须显式定义 —— 用 CTB/STB 打印样式表映射，不能依赖 ACI 7 的"聪明"反转。**Phase 5 出图必须实测"打印预览"**，不能只看屏幕。

### 问题 4（中）· 校验器自己的公式写错了

**现象**：首次运行报了 1 条 ERROR：`抽屉面板高之和 + 缝 = 净高`（左 2272，右 2284）。
**排查**：不是拆板算错，是**我的校验公式漏算了每块面板内缩的 2 道缝**。正确式子是 `Σ面板高 + (n+1)×gap + 2n×gap = 净高`。
**教训**：**校验器本身也需要被验证。** 它必须有一组"故意造错"的负样本（金标准错误集），否则"0 ERROR"只证明校验器没在工作，不证明模型是对的。
→ 已记入 Phase 4 要求：每条规则必须配 ≥2 正例 + ≥2 反例的单测。

## 三、一个业务级的重要发现（比技术坑更值钱）

### 你给的尺寸在真实拆板逻辑下**不自洽**

需求原话：柜体 **2400 宽**，左侧 **600** 抽屉柜 + 中间 **1200** 挂衣区 + 右侧 **600** 层板柜。

真实拆板时：
```
2400（总宽）
 − 18×2（两侧板）= 2364（柜内空宽）
 − 18×2（两块立板）= 2328（三个分区的净宽总和）
```
而 600 + 1200 + 600 = **2400 ≠ 2328**，**差 72mm**。

也就是说：如果按总宽 2400 做，三个分区的**净宽**只能是 582 / 1164 / 582。如果按净宽 600/1200/600 做，总宽就得是 **2472**。

**这不是用户说错了，而是"分区宽"这个词本身有歧义**（是指净宽？中到中？占位宽？）。系统如果不显式定义，结果就是：AI 把 600/1200/600 直接写进模型 → 到工厂才发现装不上。

**本 Spike 的处理**（已实现并作为架构约定）：
- 模型里新增 `layout.widthMode`，只有两个取值：
  - `fit_total`（**总宽优先**，默认）：总宽是硬约束，净宽按期望比例重新分配，并报 INFO 说明差异
  - `fit_units`（净宽优先）：净宽是硬约束，总宽随之变化
- 实际输出：`Unit_L 600→582、Unit_M 1200→1164、Unit_R 600→582`，并产生 INFO 明示：
  > 总宽 2400 固定，扣除两侧板 18×2 与立板 18×2 后可用净宽 2328，按期望比例重新分配……

**产品含义**：这类"用户数字不自洽"的情况会占真实需求的很大比例。系统必须**主动指出并给出两个选项**，而不是默默选一个。这条要写进 AI 命令的 `assumptions` 和 dry-run diff。

## 四、其他实测结论（写进架构约定）

1. **恒等式断言是这套系统最划算的投资。** 本次实现的 6 类断言在 30 行代码内，直接抓住 2 个问题（问题 1 之外的隐藏不一致也会被抓）。Phase 2 起，几何生成器的任何改动都必须先过断言。
2. **1:1 模型空间排布是对的，但打印必须靠图纸空间。** 板件图 1:1 排布后是 6.3m × 13.8m —— 不可能打印在单张纸上。正确做法（CAD 标准做法）：**模型空间永远 1:1，Phase 5 用图纸空间（Paper Space）加 A2 图框 + 视口按 1:10/1:20 出图**。绝不能为了"能打印"去缩放模型。
3. **TS 算几何 + Python 只做序列化** 这个分工实测成立且干净：`neutral.json` 是纯粹的数据契约，Python 侧没有一行几何计算。将来换导出实现（ODA SDK）不用碰几何。
4. **两条独立实现交叉验证很便宜且很有用。** 加 `dxf-parser` 只花了 1 分钟安装，却提供了一个 ezdxf 之外的独立证据。这个"双解析器"模式应该保留到 Phase 5，作为交付前的常规门禁。
5. **`DIMENSION` 必须是真实体，不能是画出来的线。** 实测 63 个 DIMENSION 全部带几何块，在 CAD 里可选中、可编辑、可改标注样式。工厂拆单员会改标注，如果标注是死线，他们会骂人。

## 六、交付物与如何运行

```
spike/
├── model/cabinet-001.json        语义模型（唯一真相源，只存参数）
├── ruleset/factory-default.json  行业默认规则集（换工厂=换文件）
├── src/
│   ├── types.ts                  领域类型
│   ├── allocate.ts               尺寸分配 + 余量归属（整数毫米，不丢 1mm）
│   ├── generate.ts               ★ 拆板：Semantic → Panel Model
│   ├── validate.ts               ★ 恒等式断言 + 生产硬规则
│   ├── export-neutral.ts         Panel Model → 中立交换格式（含立面派生）
│   └── main.ts                   入口
├── py/
│   ├── export_dxf.py             中立格式 → DXF（只序列化，不算几何）
│   ├── verify_dxf.py             10 项交付验证
│   └── render_preview.py         DXF → PNG（人眼检查）
├── js/verify-with-dxf-parser.mjs 独立解析器交叉验证
├── run.sh                        一键复现
└── out/                          产物
```

**一条命令跑通：** `bash spike/run.sh`

**本次产出的真实数据**：28 种板件、31 件、板材面积 22.8 m²、估重 244.8 kg；3 条 WARNING（背板超幅面需拆 2 块 / 抽屉面板 756mm 过高 / 挂衣区层板跨度 1164mm 超 900mm 建议加中立板）、2 条 INFO。
