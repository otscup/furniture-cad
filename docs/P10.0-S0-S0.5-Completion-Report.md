## 三、Dockerfile 最终运行时依赖闭包

**根因**：运行阶段 Dockerfile **从未** COPY `scripts` 与 `src`（`git log -S "COPY scripts" -- app/Dockerfile` 命中 0）。
而 `server.mjs` 在**运行期** spawn `node --experimental-strip-types /app/scripts/emit-*.ts`，
这两个入口 import `../src/**` 且**按路径读** `src/core/ruleset/factory-default.json`
⇒ 生产镜像里 `/app/scripts/emit-neutral.ts` 不存在 ⇒ **`/api/export/{dxf,cutlist,roombook}` 三端点必然失败**。
（宿主机源码树里这两个目录恰好都在，所以 58 个 verify 脚本全绿也照样与"生产全坏"同时成立。）

**补齐的是"运行期真实需要"的那几块，不是整棵源码树**：

```
COPY scripts        ./scripts          # 2 个 emit 入口（生产真的是 spawn 它们）
COPY src/core       ./src/core         # 闭包主体（22 文件）
COPY src/export     ./src/export       # neutralSheet / roomBook（2 文件）
COPY src/ai/memory.ts ./src/ai/memory.ts  # commandBus.ts:13 运行期 import 它 ⇒ 必须成对
```

- **故意不写 `COPY src ./src`**：那会把前端源码（`src/ui` / `src/viewport` / `src/state`）带进运行镜像。
- **闭包实测**：两个 emit 入口的运行期闭包 = **26 文件**（2 scripts + 22 `src/core` + 2 `src/export`）；
  `import type` / `export type` 被 `--experimental-strip-types` 擦除 ⇒ **不传播**；裸依赖只有 `node:fs/path/url`（零 npm 依赖）。
- **★ 按路径读的资源不进 import 闭包**：`src/core/ruleset/factory-default.json` 必须显式纳入。
  验收里由 emit 源码的 `join(here, …)` **反推**出该路径（而不是手写一份清单），
  并用"删掉它 → ENOENT"证明是硬依赖。
- **逃逸登记**：`src/core/designScore/score.ts` 运行期 import `src/ai/knowledge/*`（不在镜像内），
  但 `designScore` **不在** emit 闭包里 ⇒ 惰性死代码，登记为已知项而非缺陷。
- **`.dockerignore` 复核**：`node_modules dist .env data memory verify docs spike *.md .git .gitignore`
  —— **不排除** `src`/`scripts`，运行时资源不会被排除掉。

## 六、四项安全前置结果

四项的共同性质：**门已经存在，只是没装在这道口子上**（`canManage` 有、`audit()` 有、`MAX_OUTPUT_TOKENS_CAP` 有）。
所以只补"权限 / 审计 / 硬限制"，**没有删除任何现有能力**。

### ① `/api/settings` 敏感设置修改加 audit

- 写路径新增 `auth.audit({ action:'settings.ai', result:'ok', changed:{provider,baseUrl,model,temperature,maxTokens,apiKey}, provider, model })`。
- **只记"改了哪几项"的布尔与 provider/model 取值；绝不记 key**。
  验收里断言**整份审计文件不含 key 明文**，也不含其后 8 位片段。
- **反假绿**：断言"只改 temperature 时 `changed.apiKey === false`"——防止布尔写成恒 `true`。
- 被拒的写也留痕：`result:'rejected'` + `code`。

### ② `/api/memory` 的写只有 `canManage` 可执行

- `managePaths` 增 `isMemoryWrite = pathname === '/api/memory' && (PUT || POST)`。
- `viewer` → **403 `FORBIDDEN`**；`designer`（有 canDesign 无 canManage）→ **403**。
- **GET 保持"已登录可读"**（面板要显示内容，读的能力没被顺手砍掉）。
- `owner` 合法写 → 200，并留 `memory.write` 审计（只记字节数 + 行数，不记内容）。
- 验收同时断言 **"被拒 = 文件一字未变"**（只看 403 不够）。

> 为什么这条重要：`corrections.jsonl` 的条目会被当**纠错规则**消费（`scope:"rule"` + checkSpec），
> 覆盖它等于替换整套规则，而覆盖前只留一份同名 `.bak`。

### ③④ 输出预算的服务端硬顶（`MAX_OUTPUT_TOKENS_CAP` 成为真闸门）

- 上界 = `MAX_OUTPUT_TOKENS_CAP`（`shared/aiContract.mjs`，**唯一真源**，不在别处再写一个数）。
- `AI_HARD_MAX_TOKENS` 环境变量**只能收紧**（`Math.min(cap, raw)`），**永远不能抬高**。
- 4 个 AI 端点（chat / vision / plan / design）+ settings 写**统一走同一道 `enforceMaxTokens()`**（一处判断）。
- 请求体超顶 ⇒ **400 `MAX_TOKENS_EXCEEDED`（拒绝，不静默夹取）**
  —— 静默改写会制造"用户以为设置生效了、其实没有"的假象。
- **闸门在上游之前**：验收断言被拒时**上游调用数 = 0**，同时用"合法请求上游恰好被调用 1 次"证明该计数器是活的。
- `.env` 里的 `AI_MAX_TOKENS=999999999` 也抬不高它（请求不带 `maxTokens` 时，转发给上游的是被夹到 65536 的值）。
- 写路径同样过闸：`PUT /api/settings {maxTokens:999999}` → 400，且 **`.env` 里没有留下 999999**。

**验收统计**：`verify:security-preflight` = **48 通过 / 0 失败**；
`verify:security-preflight-mutations` = **13 通过 / 0 失败（10 个变异全部被抓住，基线全绿）**。

修复过程中连带发现并修好一处**既有套件被本次改动撑断**的问题：
`preflight-bugfixes-acceptance.ts` 的 P0-2/P0-3 变异锚点原本延伸到 `managePaths` 结尾，
安全前置在两者之间插入 `isMemoryWrite` ⇒ 锚点失配、旧套件判红。已把锚点缩短到"那一处赋值"，该套件回到 24/0。
