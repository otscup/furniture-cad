## 〇、一句话结论

P9.7 证明了"协调候选链路本身是对的"，但它只看得见 **4 个组合**（阶梯锚点 0.5/0.4 × 顺序 2），
真实厨房里这 4 个**全部**压在门洞上 ⇒ 3/3 infeasible。P9.8 把"探索覆盖"扩开：
**空白墙段（起/中/末三点）× 组内顺序（≤2n）× 对齐族 × 缝隙族**，并给每一条丢弃都记了账。
同一夹具、同一返回上限 3：P9.7 是 **1 个族 3 条全不可行**，P9.8 是 **3 个族 3 条，2 条可行、1 条被事实层判 infeasible**。
**判定层一行没改**——可行/不可行仍然只由 Spatial / Validation / Score 说话。

## 二、搜索统计示例：原 4 候选 vs P9.8 覆盖差异

夹具：厨房 5200×4200，三只 900 宽柜（组总宽 2700），南墙门洞 offset=1000 宽=900 hinge=start into-room。

**空白墙段（authored 洞口补集，只读不判定）**

```
rK_w1 沿墙    0..1000mm  长 1000mm   ← 门洞左侧，容不下整组（如实记为不可探索）
rK_w1 沿墙 1900..5200mm  长 3300mm   ← 门洞右侧，容得下整组 ✓
rK_w2/w3/w4  整段（无洞口）
```

**同夹具、同返回上限 3 的对照（口径完全一致，只有"探索覆盖"不同）**

| | P9.7（旧搜索空间） | P9.8 |
|---|---|---|
| 搜索空间 | 阶梯锚点 0.5/0.4 × 顺序 2 = **4 个组合**，`generated: 4` | 空白段三点 × 顺序(≤2n) × 对齐 × 缝隙，`generated: 24`、`explored: 90` |
| 返回 3 条的族数 | **1 个族**（同一簇） | **3 个族**（`seg1` / `legacy0` / `legacy1`） |
| 返回 3 条的判定 | **3/3 infeasible** | **2 valid / 1 infeasible** |
| 台账 | `requested:3, generated:4, returned:3, truncated:1` | `requested:3, generated:24, returned:3, truncated:21, explored:90, rejected{resolve:0,collision:18,duplicate:48}, budget:216, budgetExhausted:false` |

**P9.8 返回上限 9（缺省/政策上限）时的明细**

```
cl_010 族=rK_w1|seg1|align=start|gap=0     洞口 clear  valid      c1(1900,60) c2(2800,60) c3(3700,60)
cl_022 族=rK_w1|legacy0|align=start|gap=0  洞口 clear  valid      c1(2150,60) c2(3050,60) c3(3950,60)
cl_028 族=rK_w1|legacy1|align=start|gap=0  洞口 冲突   infeasible [SPATIAL-CABINET-OPENING, DESIGN-CABINET-DOOR-SWING] c1(1630,60)…
cl_011 族=rK_w1|seg1…（顺序 c2→c3→c1）     洞口 clear  valid
cl_023 族=rK_w1|legacy0…（顺序 c2→c3→c1）  洞口 clear  valid
cl_029 族=rK_w1|legacy1…（顺序 c2→c3→c1）  洞口 冲突   infeasible
cl_012 / cl_024 / cl_030                    第三组顺序（c3→c1→c2），同样 2 valid + 1 infeasible
── 合计 returned=9，覆盖 3 族，valid=6 / infeasible=3
```

账目自检：`explored 90 = generated 24 + rejected(0+18+48)`；`generated 24 = returned 9 + truncated 15`。

> **关键点**：`cl_028/029/030`（压门洞）**仍然被生成出来**，并由完整管线判成 infeasible ——
> 生成器没有为了"全是好候选"而提前把它们过滤掉。这是本阶段最容易被做假的地方，验收 26/27 专门钉死。

## 六、本阶段新踩到的坑（写入记忆）

1. **verify 运行期间改源文件**：为修"核心层夹到 3"，我在 `verify:all` 后台跑着的时候改了 `app/src`，
   那一轮 686/686 的结果**作废**（HMR 整页重载会让后续断言连环假红），改完必须整轮重跑。
2. **断言会因"错的原因"绿**：新增文案里的 `99` 意外满足了旧断言的子串检查（M8 假绿）。
   教训：**子串断言要认特征短语，不要认数字**；新增断言后必须先用变异确认它真会红。
3. **`planCandidates` 的夹取发生在生成之前**：只看 `generate.ts` 的上限是不够的，
   上游 `normalizePlannerRequest` 早就把请求夹掉了 —— 验收必须走**真实管线**而不是只直调生成器。
4. **真实模型回归要用应用自带的提示词**：自己随手写的 system prompt 少一条约束，
   模型就会输出契约外的值；那不是系统缺陷，但会把回归带偏。
5. **容器内跑 `.ts`**：`/app/package.json` 是 `type: module`，`.ts` 会被当 ESM 直接类型剥离运行；
   探针放 `/tmp` 时要写 `.mts`（`/tmp` 没有 package.json，`.ts` 会落回 CJS）。

## 七、遗留（不进 P9.9，仅登记）

- **orientation permutation / 多墙协调**：结构性阻塞仍在 —— `resolveAttach` 返回 `target.rotation`（成员保持自己朝向），
  且 FACE 校验要求相对旋转为 90° 整数倍。本阶段按定界**不做**。

  本阶段目标"门洞之外的空白区段"已在南墙内达成，跨墙属于上面那条阻塞的范畴。
- **缝隙族用的是洞口净宽**：`offsetVariants` 取 authored `Opening.width` 作为 `attach.offset` 候选，
  这是"派生的合法值"而不是编出来的常数；若将来需要别的缝隙档位，来源要重新论证。
