### 1.3 ★「部署镜像未同步」假说被排除（三条互相独立的反证）

指令文档把「镜像未同步」列为第一顺位嫌疑。**它不是原因，而且不可能是原因。**

**反证一：git 历史里从未存在过那两行。**
```
$ git log -S "COPY scripts" -- app/Dockerfile     → 空
$ git log -S "COPY src"     -- app/Dockerfile     → 空
$ git log --oneline --follow -- app/Dockerfile
ab9a4c2 P9.9 Preflight: …
be5a21f 容器化部署：APP_HOST 可配置 + Dockerfile + compose + 部署文档
```
Dockerfile 只被改过两次；`ab9a4c2` 那次只改了 ezdxf 版本（`ezdxf` → `"ezdxf==1.4.4"`）。
⇒ **不存在"某个更老的、含 COPY scripts/src 的 Dockerfile"**。任何一次重建都会缺这两行。

**反证二：NAS 的构建上下文里，那两个目录本来就有。**
```
$ ls /volume1/docker/furniture-cad
… scripts  src  server  shared  py  public  data  Dockerfile  .dockerignore …
$ ls $D/scripts
emit-neutral.ts  emit-roombook.ts
[ -d $D/src ] → /volume1/docker/furniture-cad/src      （存在）
```
且 `app/.dockerignore`（NAS 上那份也逐行相同）**没有排除 `scripts`/`src`**。
⇒ 文件在构建时**就在上下文里**，是被 Dockerfile 丢掉的，不是"没推上去"。

**反证三：NAS 上那份 Dockerfile 与仓库逐字相同，运行阶段只有 10 步。**
```
$ grep -n "^COPY\|^FROM\|^CMD" $D/Dockerfile
14: FROM node:22-slim AS build
16: COPY package.json package-lock.json ./
18: COPY . .                              ← 仅构建阶段
22: FROM node:22-slim
37: COPY package.json package-lock.json ./
39: COPY --from=build /app/dist ./dist
40: COPY server ./server
41: COPY shared ./shared
42: COPY py ./py
48: CMD ["node", "server/server.mjs"]
```
最近一次构建日志 `build-p98.log` 里，运行阶段（stage-1）**只有 10 步**，
第 9 步是 `COPY py ./py`、第 10 步是 `RUN mkdir -p /app/data`，然后就直接 `exporting to image`。
⇒ 构建是**成功**的，容器也确实重建并启动了 —— **成功地产出了一个缺文件的镜像。**

**结论（一句话）**：**根因是源码 Dockerfile 运行阶段缺 `COPY scripts` 与 `COPY src`。**
「部署镜像未同步」**不是**原因；即使把源码完美重推、完美重建，导出依然会坏。

**顺带一个必须诚实登记的观察**：镜像构建于 `2026-10-02 02:51`，而 `ab9a4c2` 的提交时间是 `2026-10-02 05:50`、
P9.9 实现 `5cf19ed` 更晚。也就是说**生产镜像落后于 master 若干提交**（钉版 `ezdxf==1.4.4` 已进镜像，说明推的是提交前的工作树）。
这是一个**独立的、次要的问题**（重建即可解决），**与导出失效无关** —— 不要把它当成导出的解释，否则会修错东西。

### 1.4 ★ 为什么 58 个验收脚本一个都没抓到它

```
$ node -e "…Object.keys(pkg.scripts)…"
含 docker/image/container/deploy/nas 的脚本: (无)
verify 脚本总数: 58
```

**仓库里 58 个 `verify:*` 脚本，零个会构建镜像、零个会进入容器。**
它们全部在**宿主机的源码树**上跑 —— 而源码树里 `scripts/` 和 `src/` 恰好就在盘上。
于是出现一个结构性盲区：

| | 源码树（验收跑的地方） | 生产镜像（用户用的地方） |
|---|---|---|
| `scripts/emit-neutral.ts` | ✅ 在 | ❌ 不在 |
| `src/core/**` | ✅ 在 | ❌ 不在 |
| `py/export_dxf.py` | ✅ 在 | ✅ 在 |
| 导出三端点 | ✅ 全绿 | ❌ 全 500 |

**"验收全绿"与"生产导出全坏"可以同时成立，而且是必然的。**
这正是指令文档点名要防的「代码理论上修了，但生产镜像没验证」——
而且比那更严重一层：**它不是一个疏漏，是一整套验收体系对"部署形态"完全无覆盖。**

### 1.5 最小修复方案（含实测的依赖闭包）

`server.mjs:1580/:1612/:1658` 在**运行期**把导出入口钉在 `/app/scripts/*.ts`；
两个入口又 `import '../src/**'` 并**按路径读** `src/core/ruleset/factory-default.json`
（`emit-neutral.ts:24,45`、`emit-roombook.ts:15,36`）。

实测传递依赖闭包（只读脚本遍历 import 图）：

| 指标 | 实测值 |
|---|---|
| 传递依赖的仓库内文件数 | **35** |
| 涉及的 `src/` 子目录 | **`src/core`（30 个文件）、`src/export`（2）、`src/ai/memory.ts`（1）** |
| **不需要**的 `src/` 子目录 | `src/ui`、`src/viewport`、`src/state`、`src/main.tsx`、`src/styles.css` |
| 裸模块依赖 | 仅 `node:fs` / `node:path` / `node:url`（**无需任何 npm 依赖**） |
| `scripts/` 体积 | 4.1 KB |
| `src/` 全量体积 | 1817.2 KB |
| 仅闭包所需体积 | 1275.0 KB |

**方案甲（指令文档给的写法，推荐）** —— 在运行阶段补两行：
```dockerfile
COPY scripts ./scripts
COPY src ./src
```
优点：与源码树结构一致，将来 emit 入口新增依赖不会漏；`src/` 全是纯逻辑，运行镜像多 1.8 MB 源码可接受。
**注意**：`src/ui`/`src/viewport`/`src/state` 会被一并带入（都是前端源码，不含密钥，无安全风险，但属冗余）。

**方案乙（外科式）** —— 只拷闭包：
```dockerfile
COPY scripts ./scripts
COPY src/core ./src/core
COPY src/export ./src/export
COPY src/ai/memory.ts ./src/ai/memory.ts
```
优点：不带前端源码。缺点：**闭包是"当前"的**，emit 入口将来 import 新目录会在生产静默失效——
**而这个坑已经踩过一次了**。除非同时加一条"闭包断言"验收，否则不推荐。

**★ 无论哪个方案，都必须显式包含规则集 JSON**：
`src/core/ruleset/factory-default.json`（5642 B）是**按路径读**的，
**不出现在 import 闭包里** —— 任何"只拷 import 闭包"的自动化方案都会漏掉它。
这是本节的第二个坑，容易在修复时被引入。

**修复后必须做的验证（不可省）**：
1. 镜像内 `test -f /app/scripts/emit-neutral.ts && test -f /app/src/core/ruleset/factory-default.json`；

⇒ **`viewer` 账号即可整体覆盖 `memory/corrections.jsonl`。**

**后果比"越权"更重**：这个文件不是普通配置文件，它的内容会被当作**纠错记忆/规则**消费

任意登录者可**整文件替换这套"规则"**，且：
- **没有 audit**（该 handler 无任何 `auth.audit`）；
- 备份只留**一步**（`:1548` 每次覆盖都重写同一个 `.bak`）；
- 文件注释自称「**也可以直接进 git**」（`server.mjs:1531`）⇒ 污染会进入工作树；
- 覆盖是 `writeFileSync` 整文件，**并发 PUT 互相覆盖**（§10.3）。

### 2.3 AI 成本上限 / `MAX_OUTPUT_TOKENS_CAP` —— **部分处理**

**(a) 常量与引用**

```
shared/aiContract.mjs:1317   export const MAX_OUTPUT_TOKENS_CAP = 65536;
shared/aiContract.mjs:1366     return Math.min(MAX_OUTPUT_TOKENS_CAP, Math.max(1, Math.round(n)));   ← 全仓库唯一引用
```
相邻：`DEFAULT_MAX_TOKENS = 4096`（:1307）、`PRACTICAL_MAX_TOKENS = 16384`（:1329）。

**(b) 四个 AI 端点的真实夹取情况**

| 端点 | 行号 | max_tokens 来源 | 客户端能否打穿 |
|---|---|---|---|
| `/api/ai/chat` | `server.mjs:917` | `body.maxTokens > 0 ? body.maxTokens : resolveMaxTokens(env.AI_MAX_TOKENS)` | **✅ 能** |
| `/api/ai/vision` | `server.mjs:1081` | 同上 | **✅ 能** |
| `/api/ai/plan` | `server.mjs:1198` | 恒 `resolveMaxTokens(env.AI_MAX_TOKENS)` | ❌ 不能 |
| `/api/ai/design` | `server.mjs:1425` | 同上 | ❌ 不能 |

原文（`:917`，`:1081` 同形）：
```js
max_tokens: typeof body.maxTokens === 'number' && body.maxTokens > 0
  ? body.maxTokens                                   // ← 原值透传，无夹取
  : resolveMaxTokens(env.AI_MAX_TOKENS),
```
⇒ **客户端传 `maxTokens: 100000000` 会被原样转发给上游服务商**，`MAX_OUTPUT_TOKENS_CAP` 完全不参与。
**上限不是硬闸 —— 它只是"默认值计算器"里的一次 `Math.min`。**

**(c) 写入侧同样无夹取**

`server.mjs:671` `patch.AI_MAX_TOKENS = String(Math.round(body.maxTokens));` —— 原值落 `.env`。
而 `GET /api/settings` 回显走 `:278` 的 `resolveMaxTokens(env.AI_MAX_TOKENS)`（夹到 65536）。
⇒ **同一个值两个说法**：用户填 `100000`，`.env` 里是 `100000`，界面显示 `65536`，**且不提示**。
`aiContract.mjs:1345` 的注释「所以即便用户写 `100m` 也只会被夹到 65536」**只在 `resolveMaxTokens` 内成立**，被 chat/vision 的透传路径和 settings 写入路径绕开。

**(d) 唯一真正的服务端成本闸是档位配额，它不是"单次上限"**

`shared/quota.mjs`：`PLANS.free.tokens.limit = 1_000_000` / period `day`；`checkQuota`（`quota.mjs:235-256`）
只判「**已累计**用量是否已超」；用量经 `applyUsage`（:268-282）**事后累计**。
⇒ **单次超大调用照样能发生**，只是被记进账单。没有"单次请求 token 天花板"，也没有"全局成本上限"字段。
`AI_TIMEOUT_MS`（`server.mjs:927/:1203`）是时间闸，不是成本闸。

**(e) 有没有"因内部上限而静默改变请求"的路径 —— 有**

`resolveMaxTokens`（`aiContract.mjs:1350-1367`）把字面意图静默改写：
`0 / inf / infinity / unlimited / 无限 / 不限制` → `16384`（:1361-1362）；非法或 `<=0` → `16384`（:1365）。
加上 (c) 的"落盘值 ≠ 回显值"，构成**静默不一致**，与指令文档要求的
「不能因为内部限制而静默制造错误结果 / 超政策上限时返回明确结构化错误」直接冲突。

### 2.4 四项的共同性质

| 项 | 判定 | 性质 |
|---|---|---|
| ① settings 改 Key 无 audit | **未处理** | 违反本仓库自身既有的审计纪律 |
| ② `/api/memory` PUT 越权 | **未处理** | 漏了一道已存在的 `canManage` 闸；且改的是"规则" |
| ③ AI 无服务端硬成本上限 | **部分处理** | 只有事后累计配额，无单次天花板 |
| ④ `MAX_OUTPUT_TOKENS_CAP` 非硬闸 | **部分处理** | 存在但被两条路径绕开；且值域静默不一致 |

**共同点：四项都不是"缺功能"，而是"门已经存在，只是没装在这道口子上"。**
`canManage` 有了（`auth.mjs:33-38`），`audit()` 有了（`auth.mjs:121-127`），
`MAX_OUTPUT_TOKENS_CAP` 有了（`aiContract.mjs:1317`）——
问题一律是**某个写入口没接上去**。

**这对 MCP 的含义**：MCP 会**新增一批写入口**，而上面每一项都是"新入口忘了接闸"。
⇒ 所以指令文档说「必须作为 P10.0 的安全前置，不允许 MCP 先上线再补」**是对的** ——
如果先上线 MCP，几乎可以确定会复制出第 5、6、7 个同类缺口。

### 3.2 服务端侧事实

| 事实 | 出处 |
|---|---|
| `project` 只出现在三条导出路由，作为**请求体**，`JSON.stringify` 喂子进程后**即弃** | `server.mjs:1562/1609/1655`、`:1581/1613/1659` |
| 服务端主动声明**不替前端读模型** | `server.mjs:1186-1188`「缺少 snapshot —— 前端必须显式给出项目快照，**服务端不替它去读模型**」 |
| 没有 `projectId` / 文档列表 / 草稿列表 / "当前打开的项目" | 全文件无匹配 |
| **没有任何 server→browser 的推送通道**（无 WebSocket / SSE / 长轮询） | `app/server/` 全目录搜 `upgrade`/`EventSource`/`text/event-stream` 无匹配 |
| 服务端唯一的落盘点：`.env` / `memory/corrections.jsonl` / `accounts.json` / `audit.jsonl` / `pending-registrations.json` / 导出临时目录 | `server.mjs:254, 1548, ...`；`auth.mjs:111-118`；`registration.mjs:57-63` |

### 3.3 结论

> **服务端在任何时刻都无法回答"用户 X 现在打开的是哪个 Project、内容是什么"。**
> 当前 Semantic Model 的**唯一拥有者是浏览器进程里的 `bus` 单例**。
> **"共享 workspace"这件事，现在根本不存在** —— 不是设计得不好，是还没有这个概念。

而 MCP 的四个核心工具 `cad.get_state` / `cad.validate` / `cad.* write` / `cad.apply_draft`
**全部要求服务端持有并读改模型**。这是本次审查最大的架构缺口。

**指令文档的告警完全正确**：不能假设「server 直接 import `CommandBus` 就自然拥有当前模型」。
可以 import（§8.1 已证明 `CommandBus` 在 Node 下能跑），但 **import 得到的是一台空总线，不是用户正在编辑的那一份**。

### 3.4 三个方案比较

#### 方案 A：Server-side CAD Workspace Store（服务端持有 workspace + version）

**形状**：服务端引入 `Workspace { id, ownerAccountId, name, project(JSON), modelVersion, updatedAt }`，
持久化到 `data/workspaces/<id>.json`（与 `accounts.json` 同级的落盘纪律：tmp + rename）。
浏览器与 MCP 都读写同一 workspace；draft 独立于 live；`apply` 后 `modelVersion++`。

| 维度 | 评价 |
|---|---|
| `get_state` / `validate` | ✅ 天然可答（服务端有模型） |
| 浏览器关闭时 MCP 能否用 | ✅ 能（服务端自主） |
| 是否需要推送通道 | ❌ 不需要（浏览器按版本号拉取） |
| 与"本地优先"原则 | ⚠ **冲突**，见下 |
| 是否新增持久实体 | **是**（必须显式分类，见 §3.6） |
| 实现量 | 大：服务端要点亮 `CommandBus` + `validate` + 派生，并新增一整套 workspace 生命周期 |

**"本地优先"的冲突是真实的**：项目现行原则是模型住在浏览器、localStorage 自动存草稿、
`project.json` 由用户自己下载/导入（`draftStore.ts:29`、`ExportPanel.tsx:74-87`）。
方案 A 若把真相源搬到服务端，**单机离线可用性会被打破**，这是产品级倒退。

#### 方案 B：Browser 继续唯一持有 live model，MCP 通过浏览器桥接

**形状**：MCP 请求经 server 转发到浏览器（需要 server→browser 通道），浏览器执行后再回传。

| 维度 | 评价 |
|---|---|
| 与现有架构 | ✅ 不引入第二真相源，语义模型所有权不变 |
| 是否需要推送通道 | **❌ 必须新建**（当前完全没有，见 §3.2） |
| 浏览器关闭时 | **❌ MCP 完全不可用** |
| 时序 | 每次调用要等一个往返 + 一个"用户浏览器在线"的前提 |
| 与指令文档 §四 | ❌ 文档要求 transport 走 stateless / API-style，桥接方案本质是 **stateful 且有在线依赖** |

**不适合**。MCP 的目标场景是外部 AI 自主操作 CAD；
"必须先有人把浏览器开着"会把可用性锁死在一个不可控前提上。

#### 方案 C：每次 MCP 调用都携带 Project snapshot

**形状**：与现有 `/api/export/*` 同构 —— 调用方每次把完整 project 传进来。

| 维度 | 评价 |
|---|---|
| `get_state` | **❌ 无法实现**（外部 AI 得先有模型才能传模型，循环依赖） |
| `apply_draft` | ❌ "apply 到哪"没有落点；每次调用都是一份孤立快照 |
| 第二真相源 | **❌ 最危险**：调用方手里的快照、服务端可能算出的新快照、浏览器里那份，三份互不知情 |
| 复用性 | ✅ 与导出链路完全同构，实现最省 |

**不适合作为 MCP 的主模型**。可直接复用为**导出类工具**的输入契约（`cad.export_*` 本就要模型）。

#### 方案比较总表

| | A 服务端 Workspace | B 浏览器桥接 | C 每次带 snapshot |
|---|---|---|---|
| `get_state` 可答 | ✅ | ✅（需在线） | ❌ |
| 浏览器关闭可用 | ✅ | ❌ | ✅（但无状态） |
| 需要新推送通道 | ❌ | **✅（没有）** | ❌ |
| 引入第二真相源 | ⚠ 需严格设计 | ❌ 否 | **❌ 是（三份）** |
| 与"本地优先" | ⚠ 冲突 | ✅ 不冲突 | ⚠ 弱化 |
| 实现量 | 大 | 中 | 小 |
| 结论 | **推荐（分阶段）** | 不适合 | 仅适合导出 |

### 3.5 推荐：A′ —— 服务端 Workspace Store，但**明确限定作用域**，不夺走浏览器的本地所有权

**A′ 的要点（与方案 A 的差别就三条，都是为了不破坏"本地优先"）**：

1. **workspace 是"服务端的那一份文档"，不是"全局唯一真相源"。**
   浏览器仍拥有自己的本地文档与 localStorage 草稿（现状不动）。
   MCP 操作的是**服务端 workspace**；用户要让 MCP 看到自己的模型，走**显式的 load/save**，
   与今天 `project.json` 下载/导入是同一个心智模型（`ExportPanel.tsx:74-112`）。
2. **同一个 workspace 不允许两边同时可写。** 用 `modelVersion` 做**显式 checkout 语义**：
   任何写请求必须带 `baseModelVersion`；不匹配 ⇒ 拒绝（§10）。**不做 merge、不做 last-write-wins。**
3. **Phase 1 不建推送通道。** 诚实承认：MCP 改完之后，浏览器要**重新载入**才看得到。
   这不是"以后补上就好"的小事，而是必须写进文档的**已知限制**（§18.3）。

**为什么 A′ 而不是纯 A**：纯 A 会把真相源搬走，与 `draftStore.ts`/`ExportPanel.tsx` 现有的本地优先链路打架，
且是一次**不可逆的产品级变更**（§19）。A′ 把"服务端的文档"当成**新增的一份可命名文档**，
老路径一个字节不动，MCP 是新能力而不是替换。

**为什么不是 B**：§3.4 已排除（在线依赖 + 无通道 + 与 stateless 要求冲突）。

### 3.6 必须明确回答：如果要引入 Workspace 概念，它是什么？

指令文档要求「不能含糊」。逐项定性：

| 候选定性 | 判定 | 理由 |
|---|---|---|
| **Semantic Model（真相源）** | **❌ 不是** | 真相源仍是**同一份 JSON 形状**（`types.ts:29-71` 的 `Project`，`projectFile.ts` 的信封）。workspace **持有一份** Semantic Model，但它不是"另一种模型"。不允许出现 workspace 专属的模型形态。 |
| **persistence entity（持久实体）** | **✅ 是** | 它有自己的 id、生命周期、落盘位置，与 `accounts.json` 同级。**这是它唯一的本体身份。** |
| **session projection（会话投影）** | ❌ 不是 | 它不随登录/登出消失，也不是从别处派生出来的视图。MCP 的 transport session 与它**无关**（§4）。 |
| **sync cache（同步缓存）** | ❌ 不是 | 缓存可以随时丢弃并重建；workspace 丢了就是**数据丢失**。 |

> **一句话定性**：**`Workspace` 是一个持久实体，它持有（而不是定义）一份 Semantic Model。
> 它是"服务端那一份文档"，与浏览器本地那一份是**并列的两份文档**，不是同一份的两个视图。**

**绝对禁止的两件事**（指令文档点名）：
- ❌ **偷偷把 `server Project` 和 `browser Project` 都当 Truth。**
  判据：任何时刻，**一份 workspace 只能有一个可写端点**。
  两边同时可写 = 已经违规，与有没有 merge 逻辑无关。
- ❌ **让 MCP 拥有自己的模型副本**。MCP 只发 Command（§6），
  它拿到的 `get_state` 结果必须是**投影**（只读快照 + version），不是可写的模型。

### 3.7 live / draft / version 的关系（明确回答）

| 概念 | 归属 | 语义 |
|---|---|---|
| **`liveModelVersion`** | **workspace 的**（服务端持久字段） | 每次 `apply_draft` 或合法写入 +1。**唯一的一致性凭据。** |
| **`draftModelVersion` / `baseModelVersion`** | **draft 的**（写在 draft 上） | draft 创建时快照的 `liveModelVersion`。`apply` 时比对，不等即 `DRAFT_STALE`。 |
| **`modelVersion`（浏览器）** | **浏览器 `bus` 的进程内计数器** | `commandBus.ts:788`。**与上面两个没有任何关系**，不可跨进程比较、不可传出去当凭据。 |
| **live** | workspace 当前 project | 只有 `apply_draft`（或等价的合法写路径）能改它 |
| **draft** | 服务端独立实体，挂在 workspace 下 | 一个 workspace 可有多个 draft；**draft 从不触碰 live** |

**浏览器修改后 server 怎么更新 version**：浏览器**只能通过显式的 save** 把模型写回 workspace，
`PUT /workspace` 带 `baseModelVersion` → 成功则 `liveModelVersion++`。
**没有自动同步**（Phase 1 无推送通道），因此不存在"浏览器悄悄改了而 server 不知道"的情形 ——
server 对它没收到的东西**没有意见**，一致性靠"写必须带 baseVersion"保证。

**MCP 修改后 browser 怎么发现 version 变化**：**Phase 1：发现不了**（无推送）。
浏览器下次 load/save 时拿到新 version，若本地有未保存改动 → **冲突必须显式返回给用户**，不自动解决。

## 四、MCP Transport

### 4.1 结论

| 项 | 结论 |
|---|---|
| 规范形态 | **Streamable HTTP**，单一端点 `POST /mcp` |
| 进程/容器 | **同一个 Node 服务、同一个 Docker 容器，不新增进程、不新增容器** |
| 实现位置 | 现有 `server.mjs` 的 `handleApi`（`server.mjs:385`）内新增 `/mcp` 分支 |
| 有状态性 | **transport 层 stateless / API-style** |
| ~~MCP session~~ | **MCP session ≠ CAD project session**（下面 4.3 是本节最重要的一句） |

### 4.2 两个必须写在代码里的约束

1. **`@modelcontextprotocol/sdk`（TS SDK v2）是新增运行时依赖。**
   现状：运行阶段 `npm ci --omit=dev`，而 `dependencies` 里**只有 `nodemailer`**；
   服务端是手写 `.mjs`（零依赖风格，`server.mjs:6-8/32-52`）。
   ⇒ 引入 SDK 是**本阶段第一个真正的新增运行时依赖**，会改变镜像的依赖面与攻击面。
   **两条路**（都要在实现时明确选定，不要含糊）：
   - **(i) 加进 `dependencies`**（简单，但打破了"服务端零依赖"的现状）；
   - **(ii) 手写极简 Streamable HTTP + JSON-RPC 处理**（保持零依赖，但要自己承担协议正确性）。
   本节**不替代你决策**，只登记这是一个**明确的分叉点**。
   ⚠ 无论选哪条：**必须确认 SDK 的 ESM/`.mjs` 互操作与 Node 22 `--experimental-strip-types` 不冲突**。

2. **协议兼容要写清楚，不要自己发明握手。**
   若需同时支持旧客户端，明确列出支持的协议版本与降级行为，**不得自造 `initialize` 变体**。

### 4.3 ★ `MCP session ≠ CAD project session`

指令文档明确要求「不要因为 MCP session 存在，就错误地把 MCP session = CAD project session」。

**为什么这条是硬约束**：MCP 的 transport session 是**协议层**概念（一次连接/一次会话的上下文），
生命周期由客户端连接决定；而 CAD workspace 是**持久实体**（§3.6），生命周期由用户决定。
**如果让 CAD 状态挂在 MCP session 上**：
- 客户端断开 = 用户文档消失；
- 换个 MCP 客户端看不到同一份文档；
- workspace 的持久性、并发控制、审计全部失去稳定锚点；
- stateless 的传输层会被迫变成 stateful。

⇒ **CAD 状态一律由 workspace store 管理（§3.5）；MCP transport 不持有任何 CAD 状态。**

## 五、机器鉴权：长期 API Token

### 5.1 现状（可复用的基础已存在）

| 事实 | 出处 |
|---|---|
| 唯一凭证 = **12 小时 session token** | `auth.mjs:50` `SESSION_TTL_MS = 12*60*60*1000` |
| token 形态 = **32 字节随机、非签名**（不透明串） | `auth.mjs:397` `randomBytes(32).toString('base64url')` |
| 落盘只存 **SHA-256 哈希**，明文只在登录响应回一次 | `auth.mjs:401`；`auth.mjs:397` 注释 |
| 校验 = 取 sha256 → 遍历账号 `sessions[]` 找匹配 → 查 `expiresAt`/`status='active'`/锁定窗口 | `auth.mjs:414-427` |
| 客户端存 **sessionStorage**（不跨标签、关页即失效） | `aiClient.ts:514-536`（键 `furniture-cad.auth.token`） |
| **不存在任何"长期凭证 / API token / PAT"概念** | 全仓库无第二类凭证；`auth.mjs:596-604` 的 `securityPolicy()` 自述"未实现"清单里也没有 |

⇒ **`AuthStore` 已经有哈希存储 + 撤销 + 审计的全部机制，MCP token 应当复用，不要另造账号体系。**

### 5.2 设计（按指令文档要求逐条落地）

| 要求 | 落地方式 | 为什么这样做 |
|---|---|---|
| 高熵随机 secret | 与现有 session 同源：`randomBytes(32).toString('base64url')`（`auth.mjs:397` 已有先例） | 复用同一随机源与编码，不引入第二套 |
| 明文只展示一次 | 创建响应回一次；此后任何 GET 只回**前缀短 id**（同 `auth.mjs:461` `listSessions` 只回前 8 位） | 与现有 session 纪律一致 |
| 只存 hash | `sha256(secret)`，与 `auth.mjs:401` 同法 | 不新增加密原语 |
| 日志绝不记完整 token | 审计只记**短 id 前缀**；**任何失败分支不得把 token 拼进错误消息**（现有 `requireAuth` 的错误里也不含 token，保持） | 防泄漏 |
| 可撤销 | `revokeToken(accountId, tokenId, actor)`，同 `auth.mjs:478` `revokeSession` 的形状 | 复用既有模式 |
| 可查创建时间/最后使用时间/标签 | 条目加 `{ createdAt, lastUsedAt, label }`；**`lastUsedAt` 的更新不能每次写整库**（§10.3 的并发缺陷要一并解决） | 指令文档明确要求 |
| **必须绑定具体账号** | `tokens[]` 挂在**账号记录内**（同现有 `sessions[]` 的位置，`auth.mjs:268/398`） | 天然带 `role`，无需另建映射 |
| **永不提升角色权限** | 见下 | 最关键的一条 |
| scope 只能收紧 | 见下 | |
| `owner/admin/designer/viewer` 的 `canManage/canDesign/canView` 仍由角色决定 | 有效权限 = `ROLES[role]`（`auth.mjs:33-38`）**∧** `scope` | |
| `manage` 仍需账号本身 `canManage=true` | 见下 | |

**★ 有效权限的计算（单一表达式，不允许有两处实现）**

```
effective(role, scope, need) =
      ROLES[role][need]                 // 角色闸：canManage / canDesign / canView
   && scopeAllows(scope, need)          // scope 闸：只能收窄，不能放宽
```

- `need ∈ {view, design, manage}`，与现有 `canView/canDesign/canManage` **逐字对应**（`auth.mjs:33-38`），
  **不引入第四种权限维度**。
- `scope` 取值 `read | design | manage`，**`manage` 只可被 `canManage=true` 的账号持有**；
  给 `viewer` 签一个 `manage` scope 的 token → **创建时即拒绝**（不是运行时才拦）。
- ⇒ **「机器 token 不允许变成另一套权限系统」** 这句话的工程判据就是：
  **权限判定的代码路径只有一条**（`requireAuth`，`server.mjs:360-381`），
  token 只是**多了一种来源**，判断逻辑一行不改。**若实现时出现了第二个 `if (token.scope …)` 分支做权限决定，就是走偏了。**

**评估三个问题（指令文档要求）**：
- **session token 是否继续只给浏览器** —— ✅ 是。12h session 的语义是"人在用界面"，机器不该用它。
- **MCP token 是否独立存储** —— 存**同一个账号库文件**，但独立数组（`tokens[]` vs `sessions[]`），
  字段与 TTL 语义不同（token 无 TTL / 长期）。**独立数组、同一存储**，不新建第三个库。
- **是否统一复用 AuthStore** —— ✅ 必须。`auth.mjs` 已有 `#load/#save/hashPassword/audit/listSessions/revokeSession`，
  MCP token 是它们的同类，不是新体系。

**审计（指令文档要求）**：`token.create` / `token.revoke` / `token.use.denied`（失败原因：无 token / 无效 / 已撤销 / 权限不足）
/ 高权限 MCP 操作本身（§12）。**绝不记录 token 明文**（只记短 id）。

## 六、MCP Tool 与现有 CommandBus 的严格映射

### 6.1 原则（不变）

> **MCP = 手，不是第二个 CAD 引擎。**
> 每个写工具最终必须进入 `bus.execute(command)`（`commandBus.ts:1058`）；
> **不得** `project.cabinets.push(...)`、**不得** `project.rooms[...] = ...`、**不得**直接改对象。

### 6.2 ★ 现有命令面比想象的完备，但有一个关键缺口

**实测：AI 契约白名单 `ACTIONS`（`shared/aiContract.mjs:173`）恰好 21 条**
（与项目记忆"动作清单保持 21 条"一致）：
`cabinet.resize / setBodyLift / setWidthMode / rename / move / nudge / rotate / place / setUnitWidth / setUnitParam / renameUnit / addUnit / removeUnit / setBoardMaterial / setBackMaterial / create / duplicate / delete / assembly.create / assembly.delete / project.rename`。

**但 `CommandBus` 的 op 面比 `ACTIONS` 大**。`STRUCTURAL_OPS`（`commandBus.ts:339-363`）里有 **23 条**，包括：

```
cabinet.create, cabinet.delete, cabinet.layout.addUnit, cabinet.layout.removeUnit, cabinet.mirror,
room.create, room.delete, room.resize,
wall.create, wall.delete,
opening.create, opening.delete, opening.update,
assembly.create/delete/addMember/removeMember/connect/disconnect/move/rename
```

并且 `commands.ts` 里**建造函数确实存在**：
- `drawWall(wall)` → `op:'wall.create'`（`commands.ts:456-459`）
- `createRoomCommand(room)` → `op:'room.create'`（`commands.ts:479-482`）
- `createCabinet(cab)`（`commands.ts:407`）、`placeCabinet(...)`（`commands.ts:70`）、`deleteCabinet`（`:419`）

⇒ **`cad.create_room` / `cad.draw_wall` / `cad.delete_object` 能直接复用现有命令，不需要新命令。**

**★ 关键缺口（必须登记）**：`room.create` 与 `wall.create` **存在但不在 AI 契约 `ACTIONS` 白名单里**。
也就是说：**命令层已有能力，但"AI 可以发什么命令"这条防线目前把它们关在外面。**
MCP 要用它们，就必须**明确地、一次性地**决定：
「`room.create` / `wall.create` 从此进入 AI/MCP 可发命令集」——
这是一个**权限面的扩张**，属于需要你确认的架构决定，**不能由实现顺手打开**。

### 6.3 ★ 已存在的越权防线必须复用，不得绕过

`commandBus.ts` 里已经有三道防线，**MCP 必须原样经过它们**：

| 防线 | 位置 | 作用 |
|---|---|---|
| **`STRUCTURAL_OPS`** | `commandBus.ts:339-363` | 结构性 op 走 payload 分支，不做路径校验（23 条） |
| ★ **`WRITABLE`（写路径白名单）** | `commandBus.ts:364-436` | **精确到字段的正则白名单**，注释自称"AI 越权防线 #3"。例：`'cabinet.update': [/^params\.(width\|height\|depth\|bodyLift\|…)$/, /^params\.backPanel\.(grooveDepth\|…)$/, /^params\.boardMaterial$/]`；`'wall.update': [/^thickness$/, /^height$/, /^name$/]` |
| **`DENY`** | `commandBus.ts:438` | 绝对禁改前缀：`/^panels/`, `/^geometry/`, `/^issues/`, `/^stats/`, `/^id$/`, `/^schemaVersion$/`, `/^ruleSetId$/` ——"即使白名单写错也拦一道" |

**这直接回答了指令文档的两个担心**：

1. **`cad.place_cabinet` 与 CommandBus 不是天然 1:1** —— ✅ **确认**。
   `cabinet.create`（造柜，`commands.ts:407`）与 `cabinet.place`（落位，`commands.ts:70`）是两条命令。
   **方案（二选一，必须明确，不许口头说 1:1）**：
   - **(a) 拆成两个工具**：`cad.create_cabinet`（→`cabinet.create`）+ `cad.place_cabinet`（→`cabinet.place`）。
     **推荐**：与现有命令面完全 1:1，语义干净，失败回滚简单（各自原子）。
   - **(b) 保持一个工具，内部为"一个原子 draft transaction 中顺序执行两条已有命令"**：
     在**同一 draft** 上顺序 `execute` 两条；失败则整个 draft 作废（draft 本就不碰 live，天然可回滚）。
     缺点：一个工具两种失败模式，错误归因更难。
   > **注意 `cabinet.place` 的特殊性**：注释（`commandBus.ts:368-374`）说明它是 P8.1 的"确定性落位"，
   > **x/y/rotation 由 `core/placement.ts` 这个纯函数引擎算出**。
   > ⇒ **MCP 绝不能自己算坐标**（这正是 §15 要防的）。`cad.place_cabinet` 若接受 `x/y/rotation`，
   > 它只能是**显式指定**（走 `cabinet.move`+`cabinet.rotate` 语义），
   > 而"按语义关系自动落位"必须走 `placement` 引擎 —— **两者是不同的工具，不要合一个**。

2. **`cad.update_object` 是通用 patch** —— ✅ **确认，但已有安全解法**：
   现有 `cabinet.update` / `cabinet.layout` / `wall.update` / `room.rename` / `project.rename`
   都是**路径化 patch**，且**已被 `WRITABLE` 正则白名单逐字段约束**，另有 `DENY` 兜底。
   ⇒ **方案**：`cad.update_object(targetId, field, value)` 里
   **`field` 必须在 `WRITABLE` 内命中**，由服务端映射到对应的具体 op。
   **绝不新增 `mcp.updateAnything`**（指令文档点名禁止）；
   **绝不接受调用方传来的任意路径字符串**（那等于把 `WRITABLE` 这道防线整体绕过）。

### 6.4 ★ 绝对不要新增万能命令

指令文档：「不要为了满足 MCP API 名字而新增 `mcp.updateAnything` 之类的万能命令。」

**工程判据（可检验的判据，不是口号）**：
> **`commandBus.ts` 的 `WRITABLE` 表在 P10.0 里只允许"新增具体 op 的具体字段正则"，不允许新增任何匹配宽泛路径的正则。**
> 出现 `/^params\./`、`/^layout\./`、`/.*/` 这类宽正则 ⇒ 违规。

**验收里要有一条断言：`WRITABLE` 的每个正则必须"锚定到字段级"**（§17 M11）。

## 九、Proposal 字段完整性（升为正式原则）

### 9.1 现状

P9.9 已修过三处静默丢字段：`doorMaterial`、`rodHeight`、`doors.material`

→ `PROPOSAL-UNIT-FIELD`（WARNING）进 `issues` 且进 `compileProposal.notes`。

### 9.2 升为正式原则（指令文档要求）

> **任何 AI / MCP Proposal 投影，输入可选字段存在 ⇒ 输出必须存在。
> 若该字段不被支持 ⇒ 显式 WARNING / unresolved / reject。
> 禁止 silently drop。**

**这一条要成为"原则上不许违反"，而不是"这次记得检查"。** 判据：
- **投影层一律白名单显式逐字段赋值**，禁止 `{...src}` 展开（P9.9 已在 `snapshot.ts` 建立该纪律）；
- **表外字段必须走 `PROPOSAL-UNIT-FIELD`（已有码），不允许新增第二个拒绝通道**；
- **新增 `UnitSpec` 可选字段时，同一个提交里必须同时更新**：① 投影白名单 ② `UNIT_INTENT_ITEM` 来源集 ③ 字段覆盖回归。

### 9.3 ★ 回归范围要扩到"全部可选 UnitSpec 字段"，不是只测这 3 个

指令文档：「至少保留 full-populated projection regression：`doorMaterial`、`rodHeight`、`doors.material`、
**其他现有可选 UnitSpec 字段**。不要只测本次发现的 3 个字段。」

**落地方式（可检验）**：
```
以 UnitSpec 类型定义为唯一来源，自动枚举其"可选字段"全集
  → 构造一个"全字段填满"的 unit
  → 过完整投影链（proposal → stripUnit → compile → snapshot）
  → 断言：每一个填过值的字段，都在输出里以相同值出现
  → 断言：字段全集的数目 == 断言覆盖到的字段数（防止将来新增字段而测试不知道）
```
> **最后一条是关键**：只断言"这 3 个字段在"是不够的 ——
> 它对新字段**恒真**，属于"测试通过本身可错"。必须让**字段计数**参与断言，新增字段而未更新测试时**会红**。
> （这是本项目"断言不可信比失败更危险"纪律的又一次应用。）

## 十、版本冲突设计

### 10.1 三个 version 的归属（指令文档要求逐条明确）

| 问题 | 回答 |
|---|---|
| **`modelVersion` 属于谁** | **workspace**（服务端持久字段 `liveModelVersion`）。**唯一的一致性凭据。** |
| **workspace version 属于谁** | 同上 —— workspace 自己没有第二套版本，它就是 `liveModelVersion` 的宿主 |
| **draft version 属于谁** | draft 自己，字段名建议 `baseModelVersion`（含义 = 创建时的 `liveModelVersion`）。**draft 不维护自己的递增版本**，它只有"基于哪个 live 版本" |
| **浏览器修改后 server 怎么更新 version** | 只有一条路：**显式 save**（`PUT /workspace`，带 `baseModelVersion`）。成功 ⇒ `liveModelVersion++`。**没有隐式同步。** |
| ★ **浏览器自己的 `modelVersion` 不能当凭据** | `commandBus.ts:788` 那个计数器是**进程内**的，跨进程无意义。协议里**不得出现**用它做的比较（§17 M06） |

### 10.2 冲突行为（指令文档明确要求）

`write draft` 时记录 `baseModelVersion`；`apply` 时：

```
if (liveModelVersion !== draft.baseModelVersion) → 拒绝，返回结构化 DRAFT_STALE
```

**严禁**（指令文档点名）：
- ❌ **自动 merge**
- ❌ **静默覆盖**
- ❌ **"最后写入者赢"**

**结构化错误形状**（按指令文档）：
```json
{
  "ok": false,
  "code": "DRAFT_STALE",
  "baseVersion": 12,
  "currentVersion": 17,
  "draftId": "draft_ab12",
  "hint": "这份草案基于模型版本 12，模型已更新到 17。请重新出草案，或放弃这份。"
}
```
**由用户决定重新出草案还是放弃** —— 服务端**不做任何自动修复**。

### 10.3 ★ 一个必须先解决的并发缺陷（不修则 workspace 会坏）

`auth.mjs:600` 自述：「账号库是本地 JSON 文件，**没有并发写保护，多进程会互相覆盖**」。
实测机制：`AuthStore.#load()` 读进内存 `this.data`，**请求中原地改**，`#save()`（`auth.mjs:111-118`）**整份覆写**；
`server.mjs` 用 `createServer`（:1713）异步并发处理，**在 `await` 边界上多个请求可以交错**。

⇒ 现状下 `recordUsage` / `login`（写 session）/ `create` 都可能在并发下**丢写**。
MCP 会**大幅提高写频次**（每个工具一次 draft 写 + `apply` 写 workspace），
**在这个并发模型上直接加 workspace 存储，等于把"偶发丢写"变成"经常丢写"。**

**这是 P10.0 必须一并处理的隐藏阻塞项**（§20 阻塞项 #6）。最小方案：给**文件写**加一个进程内串行队列
（或 `proper-lockfile` 式互斥），**不改存储格式**。注意：`audit` 是 `appendFileSync`（`auth.mjs:126`），
**单行追加相对安全**，不要一并改坏。

## 十一、权限矩阵

**权限来源**：`ROLES`（`auth.mjs:33-38`）+ MCP token `scope`（§5），有效权限 = 两者**相与**（§5.2）。

| Tool | viewer | designer | admin | owner |
|---|---|---|---|---|
| `cad.get_state` | ✓ | ✓ | ✓ | ✓ |
| `cad.validate` | ✓ | ✓ | ✓ | ✓ |
| read drafts (`cad.list_drafts`) | ✓ | ✓ | ✓ | ✓ |
| write draft（`create_room`/`draw_wall`/`place_cabinet`/`update_object`/`delete_object`/`submit_proposal`） | ✗ | ✓ | ✓ | ✓ |
| `cad.submit_proposal` | ✗ | ✓ | ✓ | ✓ |
| export（`export_dxf`/`export_bom_csv`/`export_roombook`） | 按现有角色规则 | 按现有角色规则 | ✓ | ✓ |
| `cad.apply_draft` | ✗ | ✗ | ✓ | ✓ |
| `cad.discard_draft` | 按最终设计/管理边界明确 | ← 同上 | ← | ← |

**"按现有角色规则"是什么意思（不许含糊）**：
实测当前三个导出路由**只要求"已登录 token"**（不在 `managePaths`/`designPaths`，见 `server.mjs:395-402`）——
即 **`viewer` 现在就能导出**。MCP 的导出工具**必须与这条现状一致或更严**，不能因为"MCP"就悄悄放宽。
⇒ **建议**：导出归入 `read` scope + `canView`，与现状一致（不让 MCP 成为更宽的入口）。

### 11.1 ★ `cad.discard_draft` 的边界（指令文档留白项，需你定）

指令文档在矩阵里把它写成"按最终设计/管理边界明确"，**没有给结论**。三种合理取向：

| 取向 | 理由 | 风险 |
|---|---|---|
| **(a) 与 write 同级（designer+）** | draft 不碰 live，丢弃自己的草案是"放弃未提交改动"，与写草稿同一层级 | 一个 designer 可丢弃**共享 workspace 里**别人创建的草案 |
| **(b) 与 apply 同级（admin+）** | 丢弃是不可逆（草案内容消失），按"管理"层级处理 | designer 自己建错草案后无法自行清理，体验差 |
| **(c) 按 draft 归属**（`ownerAccountId` 匹配才允许） | 最精确：丢自己的随时可丢；丢别人的需 `manage` | 多一层逻辑 |

**倾向 (c)**：与 §8.3 的 `ownerAccountId` 隔离一致，且不需要在"能力"上做取舍。
**但这是需要你确认的一项**（登记在 §20 待定项）。

### 11.2 验证方式（指令文档要求）

**不要只测 UI。** 必须用真实 token 发真实 HTTP 请求：

```
准备 4 个账号：viewer / designer / admin / owner（`auth.mjs:237` create，`ROLES` 决定权限）
为每个账号各签一个 MCP token（scope 分别 read / design / manage）
对每个 (tool × token) 组合发真实 POST /mcp
断言：允许的组合 2xx 且生效；禁止的组合 403 且 **模型一字节未变**（用 get_state 前后比对）
```
> **"禁止的组合"必须同时断言"没生效"，不能只断言状态码** ——
> 只断言 403 会漏掉"先改了再返回 403"这种最坏的实现错误。

## 十四、MCP Export 返回方式

### 14.1 问题

| 大文件 resource link | ✅ | ✅ | ✅ | 需自己定 |

### 14.3 建议

**按大小分流**（指令文档列的两条都要用，不是二选一）：
- **小文件（如 BOM CSV、小户型 DXF）直接 embedded**：省一次往返，且**天然不暴露路径**。
- **大文件（RoomBook HTML、大图 DXF）返回内部下载 URL**：路径形如
  `GET /api/export/download/<ticket>`，`ticket` 为**一次性、短时效（建议 ≤10 分钟）、绑定账号**的随机串，
  服务端记录 `{ticket → 临时文件路径, expiresAt, ownerAccountId}`。

**四条必须满足（指令文档）**：
1. **鉴权继续有效** —— 下载端点必须过 `requireAuth`，并校验 `ticket.ownerAccountId === account.id`。
2. **不暴露真实服务器路径** —— 响应里**只出现 ticket**，绝不出现 `mkdtempSync`（`server.mjs:1568`）产出的绝对路径。
3. **文件可下载** —— 返回可用 URL（且是**同源相对路径**，便于前置反代）。
4. **生命周期明确 + 临时文件最终清理** —— 现状 `server.mjs` 已有 stream end 清理（P1-5，`ab9a4c2`）。
   **ticket 机制必须继承这个清理**：`ticket` 过期/下载完成/ticket 被撤销 ⇒ 删临时文件；
   **并且要有一个兜底的定期清扫**（否则进程崩溃会留下孤儿临时文件——**这正是 P1-5 修过的那类问题，不要在 MCP 上重新引入**）。

## 十五、MCP 不做浏览器自动化

**严格保持**：

```
MCP = 手（只操作 semantic command）
浏览器截图 = 眼睛
```

**明确不做**：
- ❌ Playwright / Puppeteer 操作 UI
- ❌ 模拟鼠标、模拟点击画图
- ❌ **从截图反推 CAD 坐标再直接写 model**

**为什么不只是"风格偏好"**：
1. 从像素反推坐标 = **第二套几何真相**（绕过 `core/geometry` 的唯一出口）；

3. 与本项目"派生数据永不写回模型"的根原则直接冲突。

**验收判据**：MCP 相关代码**不得 import** `src/ui/**` 或 `src/viewport/**`，**不得出现**任何浏览器自动化依赖（§17 M09）。
