# P9.7 架构审查 — Multi-Cabinet Coordinated Candidate Layout

审查基线：P9.6 完成后（`38c3830`）。回答主指令 §二 的 7 问。

## 1. P9.3 单柜 candidate 的真实边界

- `CandidateLayout`（`candidateLayout/model.ts:118-129`）：`{ id, status:'draft', sourceIntent[], placements[], explanations[], unresolved[] }`。`status` 字面量只有 `'draft'`（:38），evaluated 由 P9.4 `EvaluatedCandidate` 外层承载，adopted 在类型层写不出。
- `CandidatePlacement`（model.ts:92-103）：`targetId`（引用已有柜 id，非 Cabinet 本体）+ `intent: PlacementIntent` + `resolved: ResolvedPlacement`（整数 mm 唯一坐标出口）+ `issues[]` + `satisfies[]`。
- 生成器入口 `generateCandidateLayouts(project, request?)`（generate.ts:251）：activeDesignIntents → 过滤 CONSTRUCTIVE_GOALS（仅 `wall-contact`/`standalone`，generate.ts:52）→ 逐意图×逐柜 `candidatesForTarget`（:191）→ `evaluateSpot`（:114-138）内部调单条 `resolvePlacement`（:130）+ `cloneWithPlacement`（:82-89，单柜克隆）跑 detectCollisions/deriveSpatialFacts/deriveContacts。
- **`placements.length===1` 的假设分布**：生成器（makeCandidate 硬编码单元素 :155）、plan.ts:124-132（书面声明逐柜）、AIPanel.previewCandidate（:597 只取 placements[0]——UI 侧最硬的假设）、若干 verify 取样。**designScore 与 candidateCompare 渲染层没有该假设**（逐项遍历/`placements.map`）。

## 2. P9.5 多柜 PlannerRequest 当前状态

- `PlannerRequest`（planner/model.ts:96-106）：`scope/'room'|'project'`、`intentIds?`、`cabinetIds?`、`generationGoals?`、`maxCandidates?` + `PlannerGeometryForbidden`（`x?: never`、**`placements?: never`**——类型层禁几何）。
- `planCandidates`（plan.ts:46-141）：normalize（cabinetIds≤24、intentIds≤12、maxCandidates 夹取 [1,3]）→ 选意图（空则整份拒，不退回全屋）→ 组装 CandidateRequest 转发生成器 → `scoreCandidateLayoutSet` → PlannerPlan。
- **多柜现状 = 逐柜各自生成再并列**；plan.ts:124-132 明文"不生成整体联动方案"并主动记 unresolved。maxCandidates 已真实实现（generate.ts:73-76/216），非摆设。
- `PlannerPlan`（model.ts:148-154）：request/unresolved/candidates/scores/explanations，无 winner/adopt 字段。

## 3. 为什么目前不能产生"整体候选"——断点清单

| 环节 | 结论 |
|---|---|
| 请求形状 | 不是断点（cabinetIds 已允许多个） |
| 编排 planCandidates | 不是断点（纯转发） |
| **生成器 generate.ts** | **★ 核心断点**：逐意图×逐柜双循环；makeCandidate 硬编码单元素 placements；cloneWithPlacement 单柜 |
| 落点枚举 snapPlace | 断点之一：`candidateSpots` 只枚举贴墙点，无"贴柜"枚举 |
| **Resolver** | **不是断点**：`resolvePlacements`（placement.ts:654-719）已实现批量解析 + 依赖拓扑排序 + PLACEMENT-CYCLE 环检测，**从未被候选生成调用** |
| Validation | 不是断点：`validateDesign(project)` / `deriveSpatial(project)` / `deriveContacts(project)` 全是整项目入口 |
| Score | 不是断点：`cloneWithLayout` 按 placements 逐项整体克隆（score.ts:77-86）；gate 遍历全部 placement issues |
| 预览/落地 | 断点之一：previewCandidate 只挪 placements[0] |

## 4. Resolver 是否允许候选间形成依赖链

**允许，且引擎现成**。`PlacementScene = sceneFromProject(project)` 全柜快照；`referenceId` 可指向 scene 中任何柜体 → `attach/align` 可"贴另一柜体的面"。P8.2 attach 是**贴任意相对面**（targetFace 与 referenceFace 平面重合、法线相对，法线不相对报 FACE-NOT-OPPOSING），不是"贴墙"；贴墙走 snapPlace。`WallAttachDecl` 无 wallId（designValidation/interpret.ts:319，防第二真相）。柜贴柜的运行时命令 = `cabinet.place`（compile.ts:500-588 构造 attach PlacementIntent → resolvePlacement）；`cabinet.move` 是 authored 绝对坐标、不解析关系。`resolvePlacements` 批内依赖：intent[i] 依赖 intent[j] ⇔ intents[j].targetId === intents[i].referenceId；成环报 PLACEMENT-CYCLE。

## 5. relation/attach/adjacent 可否作候选条件

可以。`deriveContacts(project)`（relations.ts:194-267）输入是**几何**（Cabinet.placement 派生的 footprint），纯函数——先构造"假设已落位"的克隆副本即可在 resolver 之后跑（P9.3 evaluateSpot 与 P9.4 score 都已在克隆副本上这么用）。对"未 resolved 的意图"直接跑不可能也不应该。注意：**意图词表刻意不收 adjacent-to/align-with**（designIntent/vocabulary.ts:277 DESIGN_INTENT_NOT_HELD——落位指令已在 PlacementIntent，加同义词=第二真相）→ 多柜协调的目标表达应走 CandidateRequest/PlannerRequest 扩展，不动 DesignIntent 词表。

## 6. 是否需要运行态协调候选模型

**不需要新结构**。`CandidateLayout.placements` 类型天然允许多项（单柜只是生成器习惯）；`scoreCandidateLayout` 对 placements 逐项遍历+整体克隆，多柜语义恰好正确；`PlannerPlan.candidates[]` 放多柜整体候选与单柜同构。**需要改的只有**：生成器（组合枚举 + resolvePlacements 接线）、previewCandidate（逐 placement 产动作）、plan.ts 文案条件化。**禁止** `CandidateLayout.cabinets: Cabinet[]`（候选不得持有 Cabinet 本体，model.ts:79-83 已有 variants 对比注释）。

## 7. 无第二真相源的保障

候选坐标只存在于运行态 DTO；唯一写模型链路 = previewCandidate（resolved 抄成 cabinet.move/rotate 的 AiAction，authored 语义）→ dryRunPlan（沙盒总线）→ 用户确认 → commitPlan（版本一致校验 + 同批 Command）。候选 DTO 永不进 Model；`candidateLayout/index.ts` 导出面无 adopt/apply/commit/persist。多柜落地必须保持同一模式（逐 placement 产动作、一批 dryRun、一批 commit），不给候选层开 adopt 通道。

## 8-12. 补充事实

8. `scoreCandidateLayout(project, layout, entries)`（score.ts:399）依赖 placements（targetId/resolved.rotation/issues）、status；**不读** sourceIntent/explanations/unresolved/satisfies（:40-45 明文）。`compareDesignScores`（:490-504）：gate > total（null 当 -1）> hitRank 字典序；不返回 winner。
9. `deriveSpatial(project)` / `deriveSpatialFacts(project)` / `validateDesign(project, opts?)` / `deriveContacts(project)` 均整项目入口，现成多柜就绪。
10. `dryRunPlan({bus, actions, gate, selection})` 吃 AiAction[]，与候选形状解耦。契约 `PLANNER_REQUEST_KEYS`（aiContract.mjs:559）已含 cabinetIds/maxCandidates；几何键黑名单含 placements/wallId 等。**发现一处落差**：`validatePlannerRequest` 目前只被 verify 调用；模型真输出 plannerRequest 时 server/aiClient 会静默丢弃（提示词承诺了一条不存在的通道）——P9.7 不接线（避免扩 scope），如实报告为已知缺口。
11. `VariantDraft` 是"新柜体"的候选语义方案（携带完整 Cabinet 占位对象、adoptVariant 换 id），与 CandidateLayout（"已有柜换摆法"，只持 targetId）刻意不同；两条通道明文禁止混用。P9.7 不合并。
12. `src/ai/planner/` 目录不存在；AI 侧仅有 plannerContext 纯视图。planCandidates 目前唯一运行时调用方是前端 generateCompare 按钮。
