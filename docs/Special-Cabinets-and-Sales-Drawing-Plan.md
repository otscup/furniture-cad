# 异形柜体与销售图纸输出方案

> 基于《测试样板间.pdf》（世园润府 18-1502，12 页矢量销售图纸）实测语义 + 本应用现有架构，回答五个问题：
> ① 异形柜体怎么生成（模板 / AI / 户型图）；② 材质（玻璃）与五金件怎么落；③ 门板开向怎么标；
> ④ 能否导出按房间排序的 PDF；⑤ 正视图为什么应该是门板图（已实现）。
>
> 日期：2026-09-24 ｜ 状态：⑤ 已落地（views.ts + views-acceptance 62 项），①–④ 为方案分析

---

## 0. 结论速览

| 问题 | 结论 |
|---|---|
| 异形柜体生成 | **三层合一**：柜型预设库做结构骨架 + AI 做"参数化填空"（只输出 Command）+ 户型图做布局约束。不靠海量模板，更不让 AI 生成几何 |
| 材质（玻璃） | 语义字段 `doors.material` 进模型；门板图斜线填充（PDF 同款黑框灰玻）；板件清单里玻璃件**单独归类，不进板式开料清单** |
| 五金件 | 规则集里的五金目录（铰链/滑轨/反弹器/拉篮/灯带…），位置规则写在 RuleSet，内部图自动标注；不硬编码 ID（docFactory 动态选型） |
| 开向标注 | **已落地**：`hingeSide` 语义字段 + 门板图开向对角线（双扇 X 跨门缝 / 单扇按铰链侧 / 3+ 同向） |
| 按房间 PDF | **可行且代价小**：模型已有 `rooms` + `cabinets.roomId`，复用逐柜图幅派生链，按房间分组 + 封面 + 每柜三图组合即可 |

## 1. PDF 实测语义盘点（我们要对齐的"行业标准长什么样"）

12 页销售图纸（世园润府样板间），**每一柜一页**，结构高度一致：

- **三图组合**：平面结构图 / 立面外观图 / 立面结构图。
  本应用对应关系：外观图 = **正视图（门板图）**（本轮已实现），结构图 = **内部图**，平面图 = 俯视图。同一语义参数化模型派生，天然同源对齐。
- **左表头**：材质勾选（掩门 / 移门 / 线条）+ 工艺标准（背板 9 / 板件 18 / 门板 25 / 抽 5 规格带）。
- **底部**：客户确认表（签字栏）。
- **异形件实例**（这些决定了"复杂柜体"到底复杂在哪）：
  - R36 圆弧见光板（见光面工艺，不是结构问题）
  - L 型免拉手档条（G 型槽免拉手）
  - 门板下延扣手（门板几何 + 五金二选一的表达）
  - 玻璃门（黑框 + 灰玻，立面图斜线填充）
  - 灯带三安装位（层板居中 / 靠前 / 45° 斜光）
  - 反弹器、托底抽、带锁抽、活动层板、碗碟拉篮
  - 石材台面（甲购）、嵌入式电器（洗衣机位）、挡水条

**核心洞察**：销售图纸里的"异形"分两类——
1. **结构异形**（L 型衣柜转角、榻榻米地台、吊柜斜切、酒柜斜层板）：真正的几何/分区问题；
2. **表达异形**（见光板、免拉手、玻璃、灯带、甲购）：几乎全是**材质 + 五金 + 标注**问题，结构还是那些板。

这两类必须分开处理，否则会把规则集搅成一锅粥。

## 2. 异形柜体生成策略：模板 / AI / 户型图，怎么选？

### 2.1 三种纯方案为什么都不行

| 方案 | 致命伤 |
|---|---|
| **海量模板库** | 组合爆炸。L 型衣柜 × 层高 × 梁位 × 左右向 × 门型 = 模板数失控；且用户需求"差 50mm"就得手改，模板沦为摆设 |
| **AI 直接生成几何** | 违背架构铁律（**AI 只输出 Command，永不输出几何**）；几何不可复现、不可验收、不可进生产；AI 幻觉直接变成切错的板子 |
| **户型图直出柜体** | 户型图只给边界（墙/梁/柱/管线），给不了内部结构；"这个位置放什么柜、分几格"是设计决策不是几何推论 |

### 2.2 结论：三层结构，各干各的

```
┌─ 第 1 层：柜型预设库（结构骨架，人写/一次性导入）──────────┐
│  鞋柜 / 吊柜 / 电视柜 / 餐边柜 / 榻榻米 / L 型衣柜 / 酒柜…  │
│  每个预设 = 语义参数表 + 分区规则 + 默认五金/材质           │
│  ★ 是参数化骨架，不是几何块（与真相源原则一致）             │
└──────────────────────┬───────────────────────────┘
                       ▼
┌─ 第 2 层：AI 参数化入口（填空题，不是作图题）───────────────┐
│  AI 读模板参数表 → 输出 Command 序列                        │
│  （cabinet.create / unit.split / door.set / shelf.move…）  │
│  dry-run 出 diff + 规则检查 → 用户确认 → commit             │
└──────────────────────┬───────────────────────────┘
                       ▼
┌─ 第 3 层：户型图约束（软约束 + 硬检查）────────────────────┐
│  房间边界/梁柱 → 可摆放域；规则引擎做碰撞/避梁/靠墙检查      │
│  不合法 → 硬阻断；不美观 → AI 软建议（两者严格分离）         │
└───────────────────────────────────────────────────────────┘
```

- **模板的粒度**：预设只管"骨架"（几个分区、抽屉在哪、门怎么分、默认深度），落点是 `ruleset/templates/` 目录下的配置文件，docFactory 从模板构造柜体——换预设 = 换文件，跟换工厂规则集同一哲学。
- **AI 的粒度**：AI 做的是"这个衣柜宽 2400，左半做挂衣右半做叠放，上面加一排顶柜" → 翻译成 Command 序列。几何由派生管线现算，AI 的输出 100% 可 dry-run、可回滚。
- **户型图的粒度**：户型图导入是**约束来源**不是生成来源。L 型衣柜的"L"来自墙角，但转角柜怎么分（90° 叠柜 / 斜切 / 圆弧）由模板决定，规则引擎检查转角处两柜是否干涉。

### 2.3 特殊图元的落点（酒柜斜层板为例）

酒柜斜层板、圆弧见光板这类"非矩形板件"：
- 几何层：派生图元本来就是任意 poly（Canvas 2D 渲染器 + DXF 都支持），加 `panelShape: 'slanted' | 'arc'` 类参数化图元即可，**不破坏"语义参数 → 几何"管线**；
- 清单层：板件清单跟着派生走，斜层板自动带真实尺寸（长边/短边/角度），开料软件能吃；
- 优先级放后（Phase E）：先把矩形世界的柜型做扎实。

## 3. 材质与五金件的落点

### 3.1 材质（玻璃门为例）

- **数据模型**：`UnitSpec.doors` 加 `material?: 'wood' | 'glass' | 'mirror' | ...`（默认 wood，显式覆盖——吸取 dimlfac=100 的教训）。材质是语义字段，进模型、进版本管理、进 CommandBus 白名单。
- **渲染**：门板图上玻璃门画斜线填充（PDF 同款：黑框 + 灰玻斜线）；派生管线加一条 fill 规则即可。
- **清单**：玻璃门板在板件清单**单独归类**——它不走开料机，是甲购/外采件。这是"派生视图按用途分流"的又一个实例。
- **见光面**：靠墙侧不见光、外侧见光 → 规则集给默认（`visibleFace` 策略），R36 圆弧见光板属于这个体系的延伸。

### 3.2 五金件

- **落点 = 规则集的五金目录**：`hardware: { hinge_110: {...}, slide_3fold: {...}, push_open: {...}, led_strip: {...}, basket: {...} }`，每项带名称、规格、默认安装位置规则。
- **关联方式**：语义字段引用五金 ID（如 `doors.hinge: 'HW_HINGE_110'`——docFactory 已如此），清单和内部图标注都从这一个字段派生，不重复表达。
- **灯带**是典型例子：`ledStrip: { position: 'center' | 'front' | 'angled45' }`，三个安装位对应 PDF 里三种画法，标注位置由派生管线决定。
- **红线**：五金不硬编码 ID、不允许 AI 改目录（规则集修改不在 MCP 白名单里）。

## 4. 门板开向标注（已落地 ✅）

本轮已实现并验收（views-acceptance C7c–C7f + G7 负样本，62/62 全绿）：

- **语义字段**：`UnitSpec.doors.hingeSide: 'left' | 'right'`——只影响图面表达，**不影响板件清单**（一块门板两个铰链位，开向是安装信息不是下料信息）。
- **门板图画法**（与销售图纸同款）：
  - 双扇对开：整个门洞一个大 X，两条线**跨过门缝交叉**（实测修正：最初把 X 画在每扇门内部，被门缝切成两个小 X，断言抓出后改为门洞级）；
  - 单扇：按 `hingeSide`——铰链左 → 对角线左上到右下；
  - 3+ 扇：全部同向简画（行业惯例），逐扇铰链标注待数据细化。
- **边界澄清**：PickLine 不受对角线影响（点的是门缝/外轮廓），对角线只是表达符号，不参与拾取。
- **后续**：移门（`doors.type: 'sliding'`）画箭头表达推拉方向，同一套语义字段思路。

## 5. 按房间排序导出 PDF：可行，方案如下

**结论：可行，且不需要新架构**——项目模型已有 `rooms` 与 `cabinets.roomId`，派生链已能逐柜出图幅（buildProjectViews），缺的只是"编排层"。

### 5.1 生成管线（复用现有思路）

```
model.json（rooms + cabinets.roomId + 版本三件套）
   │  TS 派生（同一条几何管线，零新几何代码）
   ▼
按房间分组 → 房间内按柜体 x/y 排序
   │
   ▼
PDF 编排：
  · 封面：项目名 + 客户信息表 + 版本三件套（模型/生成器/规则集）
  · 每房间一节：房间名标题
      · 每柜一页：左表头（材质/门型勾选）+ 三图组合（平面/外观/结构）+ 柜体编号
  · 尾页：汇总清单（板件/五金/玻璃件，按柜归类）
   │
   ▼
输出：浏览器打印 CSS（@page 分页）或 pdf 库直接产出
```

### 5.2 关键设计点

1. **排序即语义**："按房间排序"是 `rooms` 数组顺序 + 房内 `cabinets` 按 (y, x) 排序，全部来自模型，不由导出器临时发明。
2. **三件套强制**：导出件必须携带模型版本 + 生成器版本 + 规则集版本，可完整复现——这是生产数据交付的红线，PDF 与 DXF 同等对待。
3. **每柜一页 vs 每房间一页**：销售场景每柜一页好签单（对齐 PDF 样板），施工场景可加"房间总览页"。两页型都从同一派生数据出，只是排版差异。
4. **实现顺序**：先做 HTML 打印版（零依赖、样式灵活、验收容易），需要服务端 PDF 时再上 pdf 生成库。Phase D 做。

## 6. 正视图 = 门板图（已落地 ✅）

用户指出的问题属实：旧正视图把层板/中立板/门板叠画一张图，小隔层的门被内部线切成"多块板件"——客户会以为门是拼的。本轮修正（`views.ts drawFrontLike` 重写）：

- **有门分区**：只画整块门板（doorWidths 同源尺寸）+ 开向对角线，内部一概不透；
- **有抽分区**：画抽面（抽屉本来就是一格一面）；
- **开放分区**（无门无抽）：透出层板/挂衣杆——外观上真的可见；
- **中立板**：只画在两侧都开放的分区之间（被门挡住的不画）；
- **内部结构图**：维持原样（去门板、结构全画）——与 PDF"外观图 + 结构图"双图组合完全同构。

验收断言（62 项全绿）：C7c 整块门板存在（doorWidths 同源）/ C7d 开向 X 线存在且跨门缝 / C7e 门区层板 0 块出现 / C7f hingeSide 方向正确（单扇左右铰链双向验证）/ G7 负样本（删光对角线必须被检出）。

**实测踩坑记录**：
1. 双扇 X 最初画在每扇门内部（循环内 left/right 是扇叶边界）——行业画法是门洞级大 X，被 C7d 断言抓出；
2. 断言里 zTop/zBot 语义反了——views.ts 画布 y 向下，`zTop` 是数值小的"图面顶部"，不是"z 较大"。教训：**图元坐标系的 y 方向要在断言注释里写死，不许靠猜**。
