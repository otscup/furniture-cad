## 一、当前源码事实

### 1.1 候选侧（`CandidateLayout`）—— 已存了什么

`candidateLayout/model.ts:147-158`：

```ts
interface CandidateLayout {
  id: string;                       // cl_001…（nextId('cl', taken)，taken 每轮从空集开始）
  status: 'draft';                  // 类型层只有 draft（写不出 evaluated/adopted）
  sourceIntent: string[];           // 驱动的 active 意图 id
  placements: CandidatePlacement[]; // P9.7 起允许多项（整体候选）
  explanations: string[];           // 人话：为什么生成它
  unresolved: CandidateUnresolved[];// 本候选没解决的事
}
```

`CandidatePlacement`（`model.ts:116-127`）：

```ts
{ targetId; intent: PlacementIntent; resolved: ResolvedPlacement; issues: Issue[]; satisfies: CandidateSatisfies[] }
```

`explanations` 的两处生产者：

- **单柜路径** `generate.ts:237-241`（`makeCandidate`）：3 条 —— 策略+落点坐标 / 有无冲突 / `对目标「X」：满足|不满足`（**来自 `satisfies`**）。
- **协调路径** `generate.ts:535-540`：`explain[]` + `搜索族：${family}` + `对目标「X」：n/m 只柜满足`（**来自 `satisfies`**）+ 整体验证说明。

### 1.2 评分侧（`DesignScore`）—— 已存了什么

`designScore/model.ts:177-196`：

```ts
{ status: 'valid'|'infeasible'; total: number|null; totalKind; weights;
  components: DesignScoreComponent[]; hardFailures: DesignScoreHardFailure[];
  preferenceMatches: DesignScorePreferenceMatch[]; explanations: string[] }
```

三条关键事实：

1. **`DesignScoreComponent`（`model.ts:71-99`）本身就已经是一个"解释 token"**：
   `{ id, kind, label, source: 'fact'|'rule'|'preference', fact?, rule?, intentId?, goal?, preferenceId?, isPreference, weight: null, weightSource, hit: 'yes'|'no'|'unknown', why }`。
   六个"答得出"的问题（来自什么 / 依据哪个 fact / 依据哪个 rule / 是不是 preference / 权重 / 为什么）**已经全部结构化存在**。
2. **`hardFailures`（`model.ts:107-117`）带 `code` / `severity:'ERROR'` / `target`（柜 id）/ `message` / `source: 'candidate-issues'|'design-validation'`**
   ⇒ **"为什么不可行"已经可以按 code + 按柜归属**，`score.ts:100-124` 的 Gate 是唯一入口。
3. **Gate 前置**（`score.ts:399-417`）：有 ERROR ⇒ `infeasible` + `total:null` + `components:[]`，不进入软评分。

### 1.3 房间级意图下，评分层**没有**条件命中（重要）

`score.ts:247-263`：`conditionComponents` 只对 `intent.scope.kind === 'cabinet'` 的意图读事实；
`scope.kind === 'room'` ⇒ 产出 `kind:'unavailable', hit:'unknown'` 一条，文案是
"这条意图的作用对象是房间，而条件类事实是逐柜读的 —— 房间级结论判不出来，不进评分"。

**后果**：P9.8 真实厨房回归用的就是**房间级** `wall-contact` 意图
（`verify/multi-candidate-search-acceptance.ts:107-110` 的 `roomIntent`，§5 全节用它搭夹具）
⇒ 那份 plan 里 `components` 只有一条 `unavail:di_001`（`hit:'unknown'`），`total = 0`，
而候选自己的 `explanations` 里写着"对目标「抵墙」：3/3 只柜满足"（`generate.ts:538`，来自 `satisfies`）。
**同一屏会出现两个口径的"满足了什么"—— 这是既存事实，不是假设。**（详见 §4.1）

### 1.4 验证侧 / 空间侧

`DesignValidationReport`（`designValidation/model.ts:146-167`）= `{ status, placement, spatial, doorSwing, findings[], counts, wallContacts[], cabinets[] }`；
`DesignValidationFinding` 带 `layer: 'placement'|'spatial'|'semantic'` + `status: 'warning'|'error'` + `code` + `cabId?` + `sourceCode?`。

⚠ **但评分层只把 ERROR 级搬进 `hardFailures`（`score.ts:118-122`）**，`validateDesign` 的 **WARNING 级结论在候选链路上被整体丢弃**，
既不在 `CandidateLayout` 里也不在 `DesignScore` 里。

### 1.5 生成统计（set 级，不挂单候选）

`CandidateGenerationStats`（`candidateLayout/model.ts:176-199`）：
`requested / generated / returned / truncated / generationLimited` + P9.8 追加
`explored / rejected{resolve,collision,duplicate} / budget / budgetExhausted`。
挂在 `CandidateLayoutSet.generation` 与 `PlannerPlan.generation` —— **是"这一轮搜索"的账，不是"这一个候选"的账**。

## 四、第二 Truth 风险（最重要的一节）

### 4.1 ★ 已存在的一处口径分裂：`satisfies` vs `components`

`generate.ts:178-189` 的 `satisfiesGoal` 是**生成期的粗信号**：

```ts
case 'wall-contact': return facts.cabinets.find(...)?.walls.some(w => w.relation === 'touching') ?? false;
case 'standalone'  : return !contacts.some(...);
default            : return false;   // ← opening-clear / door-swing-clear / room-inside … 一律 false
```

而 `score.ts:146-210` 的 `readGoalFact` 是**评分期的对账**：

```ts
case 'wall-contact': kinds.some(k => spec.satisfiedValues.includes(k))   // satisfiedValues = ['back-wall-contact','side-wall-contact']
case 'opening-clear': rels ⇒ yes / no / unknown
case 'door-swing-clear': 含 unknownDoors 修正（unknown ≠ clear）
```

两者**在三种情形下发散**：

1. **门脸朝墙**：`relation==='touching'` ⇒ `satisfies.ok = true`；评分层 `kind='front-wall-contact'` ∉ satisfiedValues ⇒ `hit='no'`。
2. **房间级意图**：`satisfies` 按柜给出 true/false；评分层给 `unavailable/unknown`（§1.3）。
3. **非 wall-contact/standalone 的目标**（`opening-clear` 等）：`satisfies` 恒 `false`；评分层会真判。

而且界面**当前就把两者摆在相邻位置**：
`candidateCompare.tsx:158-163`（components + 命中矩阵，来自 score）紧挨着
`:172-178`（`layout.explanations`，内含"对目标「X」：满足/不满足"，来自 satisfies）与
`:180-186`（`unresolved`，同样来自 satisfies）。

**这就是 P9.9 的头号陷阱**：如果解释层把 `satisfies` 当"满足了什么"的真相源，
就会在同一张卡片上出现"意图矩阵 = 判不出来"与"未满足：本候选未满足「抵墙」"并存的自我矛盾，
并且会**事实上建立起第二套意图判定**（因为 `satisfiesGoal` 已经是第二套）。

**建议（红线）**：
- 「可行性」唯一真相源 = `DesignScore.status` + `hardFailures`；
- 「意图命中」唯一真相源 = `DesignScore.components`；
- `placements[].satisfies` 在解释层**只能以"生成期信号"身份出现**，且必须与 components 分区、加明确标签（例如"生成期粗判（不用于评分）"），
  **不得**被 formatter 合并成"满足了 X"这一类结论句。

### 4.2 其它第二 Truth 风险清单

| 风险 | 触发方式（反例） | 防线 |

## 五、Explanation 架构建议

### 5.1 结论：**需要 `CandidateExplanation` 类型，但它是 derived/read-only projection，不是新的运行态结构**

理由：
- 需要一个**稳定形状**给 UI 与验收同时消费（否则 UI 里会长出散落的 `row.score.xxx` 取值，验收抓不住）；
- 但它**不持有任何新事实**：每个字段都是对既有对象的引用/重塑；
- 它**不需要生命周期**（P9.4 的 `EvaluatedCandidate` 已经承担"评过没评过"，P9.9 不该再造一个"解释过没解释过"）。

### 5.2 建议形状（全部引用，无重算）

```ts
// app/src/core/candidateLayout/explain.ts  —— 纯函数，无 React、无 JSX、不 import 判定层
export interface CandidateExplanationItem {
  /** 解释码：直接引用既有 id / code，不自造新码表 */
  code: string;              // component.id（'cond:di_001' / 'pref:c1:kn_003'）或 hardFailure.code
  kind: 'condition' | 'preference' | 'unavailable' | 'blocking';
  source: 'fact' | 'rule' | 'preference';   // 引自 component.source；blocking 时引自 hardFailure.source
  hit: 'yes' | 'no' | 'unknown';            // blocking 恒 'no'（已证明非法，不是"看起来不好"）
  label: string;             // 人话标签（引自 component.label / hardFailure.message）
  why: string;               // 引自 component.why / hardFailure.message
  /** 归属：能追到柜就追到柜（引用 targetId，不复制坐标） */
  targetId?: string;
  intentId?: string;
  goal?: DesignIntentGoal;
  preferenceId?: string;
}

export interface CandidateExplanation {
  candidateId: string;                       // 引用
  status: 'valid' | 'infeasible';            // 引用 score.status（唯一）
  /** 按 placement 组织（多柜候选按柜分组；blocking 按 hardFailure.target 归因） */
  placements: Array<{
    targetId: string;
    items: CandidateExplanationItem[];       // 只含 targetId 命中这一柜的项
  }>;
  /** 不归属任何单柜的项（如房间级 unavailable） */
  crossCutting: CandidateExplanationItem[];
  blocking: Array<{ code: string; target?: string; message: string; source: 'candidate-issues' | 'design-validation' }>;
  /** 生成侧自述：原样透传，不解析、不改写字面 */
  generationNotes: string[];
  generationFamily?: string;                 // 仅当 M1 落地
  unresolved: CandidateUnresolved[];         // 原样引用
  /** 归一化码表，供验收与 UI 角标使用（不改变任何判定） */
  codes: string[];
  /** 确定性自然语言：由 formatter 从上面这些字段拼出（见 §8） */
  summaryZh: string;
  /** 生成期信号（★ 与 facts 分区，禁止混入 summaryZh 的结论句） */
  generatorSignals: Array<{ targetId: string; goal: DesignIntentGoal; ok: boolean }>;
}

export function buildCandidateExplanation(
  layout: CandidateLayout, score: DesignScore, project?: Project
): CandidateExplanation;

export function explainCandidateSummaryZh(e: CandidateExplanation): string;   // 确定性 formatter
```

### 5.3 各字段的"必须引用、不得重算"约束

| 字段 | 必须引用 | 严禁 |
|---|---|---|
| `status` | `score.status` | 不得由 `hardFailures.length>0` 自己推（那是复制 Gate） |
| `blocking[]` | `score.hardFailures` | 不得调 `validateDesign` / `detectCollisions` |
| `placements[].items` | `score.components`（按 `intentId→intent.scope.cabinetId` 或 `label` 里的柜名？) | ⚠ 见下方注 |
| `preference` 项 | `score.preferenceMatches` | 不得调 `resolveKnowledge` |
| `generationNotes` | `layout.explanations` | 不得正则解析、不得重排 |
| `unresolved` | `layout.unresolved` | 不得"补一条更好听的" |
| `summaryZh` | 上述字段 | 不得引入任何新变量 |

> ⚠ **注（实现时须解决，本轮不定案）**：`DesignScoreComponent` 没有 `cabinetId` 字段，
> 条件组件的"柜"只能通过 `intentId → intent.scope.cabinetId`（需要 project）间接得到。
> 两条可选路：① `buildCandidateExplanation(layout, score, project)` 收 project 做一次 id 映射（只读，不算判定）；
> ② 给 `DesignScoreComponent` 加**可选** `cabinetId?`（改 P9.4 模型，属"扩展既有事实结构"，**建议留待实现阶段裁决**）。
> 本轮只记录：**必须有一条明确归因口径，且不得靠解析 `label` 中文串**。

### 5.4 是否保存 rule/fact/preference 来源 —— **必须保存**

`source` / `fact` / `rule` / `preferenceId` 是"这条解释凭什么成立"的追溯链，
与 P9.4 §五"三条来源纪律（闭集，没有第四种）"同源。丢了它，解释就退化成"系统说不行"。

### 5.5 是否保留 explanation code —— **必须保留**

`component.id`（`cond:di_001` / `pref:c1:kn_003`）与 `hardFailure.code` 都是**稳定 id / 既有码**：
- 验收要断言"因对的原因红"，靠的就是 code（项目既有教训：只断言 `ok===false` 会假绿）；
- UI 要能点开"这条依据哪一层"，靠的是 `source` + `code`；
- 自然语言只是**最外层皮肤**，不能是唯一表示。

### 6.1 结论：**A —— compare session 里的运行态状态**

## 八、LLM 是否需要参与 —— **不需要**

### 8.1 结论：deterministic tokens → formatter，本阶段**完全不接 LLM**

理由（全部是源码事实）：

1. **事实已经结构化且带 code**：`components[].{id,hit,why,fact,rule,source}` + `hardFailures[].code`
   已经能把"该方案贴合南墙，但与门洞区域发生冲突，因此不可用"这句话的每个词都追到一个字段。
   用户举的那个例子，正好是 `hardFailures[].code ∈ {SPATIAL-CABINET-OPENING, DESIGN-CABINET-DOOR-SWING}` + `wall-contact` component `hit:'yes'`。
2. **评分层明确排除 LLM**：`DesignScoreSource = 'fact'|'rule'|'preference'` 是闭集，注释写明"LLM 判断不在三者里，类型层写不出"（`designScore/model.ts:49-53`）。解释层若接 LLM，就会在评分层旁边开一个"模型觉得"的口子。
3. **AI 契约已限定**：`candidateScore` 块是 `readOnly:true`，提示词明写"你不能据此选择方案、也不能宣布哪个更好"（`aiContract.mjs:1255`）。让 LLM 写解释等于给它一条绕回候选语义的路。
4. **候选根本不进对话通道**：`buildCandidateScoreContext` 只给 6 条摘要、零坐标、零坐标反推（`:37-38, :14-16`）。模型手上没有足够事实，"自然"只能靠编。
5. **确定性是可断言的**：`verify/candidate-compare-acceptance.ts:42` 已经断言"同 plan 两次 build 逐字节相同"。接 LLM 就永久失去这条。

### 8.2 若将来确实要接（**本阶段不做**），必须同时满足

- LLM 只能**改写已有事实的自然语言**，输入集 = `CandidateExplanation` 的字段全集，不得引入任何新名词；
- 输出**必须**可被校验回 `codes[]`（模型说到的每一个 code 必须在 `codes` 里，多一个即拒）；
- 不得改变 `status` / `hit` / `total` / 任何 component；
- 不得产出"更好/更差/建议/推荐"类措辞；
- 不得参与 selection，不得写 Knowledge；
- 且必须仍然保留 deterministic `summaryZh` 作为**唯一强制可用**的解释（LLM 版本只能是附加层，可关）。

## 九、Candidate Identity / Selection 稳定性

### 9.1 Candidate ID 的性质：**位置性 id，不是内容键**

- `generate.ts:802`：`const taken = new Set<string>()` —— **每轮从空集开始**；
- `generate.ts:311 / 527`：`candidateLayoutId(taken)` → `nextId('cl', taken)` → **`cl_001`、`cl_002`…**（`ids.ts:13-18`）。

⇒ **任何两轮生成的 `cl_001` 指的不是同一份布局**（除非枚举过程完全一致）。

### 9.2 已存在的**真实错指风险**（源码级确认）

`AIPanel.tsx:561-579` 的 `generateCompare` 重新生成 `comparePlan` 时**不清** `selectedCandidateId`，
而 `selectedCandidateId` 持久化在 `sessionStorage['p96:selectedCandidate']`（`:530-541`）。

场景：
1. 用户生成对比 → 选了 `cl_003`（某份贴东墙的候选）→ sessionStorage 写入 `cl_003`；
2. 用户改了模型（挪了一只柜 / 加了一个意图）→ 再点"生成对比"；
3. 新 plan 里 `cl_003` 依然存在（id 是位置性的），但**是完全不同的另一份布局**；
4. UI `:123` `row.layout.id === selectedCandidateId` ⇒ **高亮在一份用户从没选过的候选上**，
   按钮显示"✓ 已选择此方案"。

这正是用户 §八 担心的"错误地指向一个看起来类似的新候选"。**它是既存缺陷，不是 P9.9 引入的**，
但 P9.9 既然要"记录用户选择"，就必须先把地基修平，否则会把错误的选中状态做得更显眼。

### 9.3 内容键已经存在 —— `candidateSignature`（`generate.ts:341-344`）

```ts
`${placements.length}|` + placements.map(p => `${p.targetId}@${p.resolved.x},${p.resolved.y},${p.resolved.rotation}`).sort().join('|')
```

它由**内容**（柜 + resolver 输出）决定，与枚举顺序无关，且已经是去重键（P9.7 §十、P9.8 §一.3 都在用）。
⚠ 但它**当前是模块私有函数**，未导出 —— P9.9 若要复用，**必须导出既有实现**，
**严禁**在 session 层另写一份"看起来一样"的签名（那就是第二份判定键，迟早分家）。

### 9.4 建议（P9.9）

```
selection = { candidateId: 'cl_003', candidateKey: '<candidateSignature>' }
```

- 存：`sessionStorage` 同一个 key，值改为 JSON（`{ id, key }`）；
- 读：**每次渲染时经 `resolveSelection(plan, stored)` 校验** ——
  `plan.candidates` 里必须存在 `c.id === stored.id && candidateSignature(c) === stored.key`，否则
  **判定为失效 → 清除选中 + 移除 sessionStorage**（明确失效，而不是错指）；
- 「重新生成 / 刷新快照 / 重跑 Planner」后：旧的 `{id,key}` 若对不上 ⇒ **selection 失效**；
  用户需要重新点一次 —— 这是**正确**行为（诚实 > 方便）；
- 不引入时间戳（会破坏逐字节确定性断言；`verify:multi-candidate-search` §6 已断言逐字节一致）。

> 备选：`candidateSignature` 不含 `intent`（attach vs absolute）与 `generationFamily` ——
> 两份"结果相同、来路不同"的候选会共用一个 key。对 selection 语义（"我选的是这个结果"）而言这是**正确**的；
> 若将来要区分"来路"，应扩展签名而不是另起一套。

1. 解释层源码不 import `detectCollisions` / `validateDesign` / `deriveSpatialFacts` / `deriveContacts` / `resolveKnowledge` / `scoreCandidateLayout`（只 import 类型）。
2. 同 `(layout, score)` 两次 `buildCandidateExplanation` 逐字节相同（确定性）。
3. `explanation.status === score.status`（恒等，不是自己推的）。
4. `blocking[]` 与 `score.hardFailures` 逐条一致（code/severity/target/message/source 五项）。
5. `placements[].items + crossCutting` 的 code 集合 **等于** `score.components.map(id)`（不多不少）。
6. `generationNotes` 与 `layout.explanations` 逐字节相同（不改写、不排序）。

**B. 不造 winner**
7. 解释对象**没有** `winner` / `best` / `recommended` / `rank` / `score:number` 字段（按 JSON 键集断言）。
8. `summaryZh` 不含"最好/最优/推荐/建议选"。
9. 多候选时，各份解释的 `codes[]` 允许不同，但**不存在**跨候选的比较结论字段。

**C. satisfies 分区（§4.1 红线）**
10. `generatorSignals` 与 `items` 是两个数组，`summaryZh` **不出现** satisfies 导出的"满足/不满足"结论句（可用"生成期粗判"标签 + 断言 summaryZh 不含 `对目标「` 前缀串）。
11. 构造"门脸朝墙"夹具：断言 `satisfies.ok === true` 与 `components.hit === 'no'` **同时存在且不互相覆盖**（即：解释层不把两者合并成一个 hit）。

**D. unavailable / unknown 如实**
12. 房间级意图 ⇒ `crossCutting` 含一条 `kind:'unavailable'` / `hit:'unknown'`；`summaryZh` 出现"判不出来"。
13. `hit:'unknown'` **不得**被 formatter 写成"未满足"。

**E. 多柜组织**
14. `placements.length === 3` 的候选 ⇒ `explanation.placements.length === 3`，且每块只含该柜的 items。
15. blocking 按 `hardFailures[].target` 归入对应 placement；无 target 的进 `crossCutting`。
16. 房间级 unavailable 项**不**被硬塞进任一 placement。

**F. Selection（S3）**
17. `resolveSelection(plan, {id:'cl_001', key:'<不存在>'}) === null`（失效，不回退到"id 相同就认"）。
18. 只有 id 匹配、key 不匹配 ⇒ **失效并清除**（断言 sessionStorage.removeItem 被调用/返回 null）。
19. 重新生成一份不同 plan 后，旧 `{id,key}` 失效（用真实厨房改一只柜的坐标造出新 plan）。
20. `selectCandidate` 体内仍无 `bus.execute` / `commitPlan` / `dryRunPlan`（沿用既有 19/20 项）。
21. selection 不进 `project.json`：调用前后 `JSON.stringify(project)` 逐字节相同。
22. `previewCandidate` 仍以入参 `candidateId` 为准，**不读** selectedCandidateId。

**G. 不写模型 / 不持久化**
23. 全流程前后 project 逐字节不变；解释层源码无 `serializeProjectFile` / `projectFile` / `saveKnowledge`。
24. `placements[].items` 不含任何 x/y/rotation（零坐标外泄到解释层是没必要的）。

**H. 上游回归**

    `design-score` 133/133、`candidate-compare` 42/42、`ai-planner` 96/96 全部保持通过（零删除零放宽）。
26. `verify:all` EXIT=0，含 `verify:ui` 全绿、零 console error。

## 十五、与 P9.8 的边界

| 维度 | P9.8（已封板） | P9.9（本轮定界） |
|---|---|---|

| 是否动 Resolver / Spatial / Validation | 否 | **否** |
