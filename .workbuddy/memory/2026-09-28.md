## Bug 修复：AI 规划接口忽视 AI_MAX_TOKENS（"调到无限也没用"真凶）
- **症状**：用户在 .env 改 `AI_MAX_TOKENS` 想给推理模型更大输出预算，但自然语言"生成 L 形橱柜"仍报"输出预算用完（4096），正文为空"。
- **根因两重**：
  1. `/api/ai/plan`（自然语言→动作清单通道）调用 `buildChatRequest(...)` 时**没传 maxTokens，也没读 `env.AI_MAX_TOKENS`**，永远吃死 `DEFAULT_MAX_TOKENS=4096`。聊天接口 `/api/ai/chat` 虽读 env 但仅作 fallback。前端 `requestPlan`/`chat` 都不带 `maxTokens`，所以 env 本应生效——但 plan 压根没读。
  2. `Number("无限")` = NaN、`Number("0")`=0，发到 API 等于无效/默认。裸 `Number()` 解析不可靠。
- **修复**（`shared/aiContract.mjs` + `server/server.mjs`）：
  - 新增 `resolveMaxTokens(raw, fallback=4096)`：undefined/空→fallback(4096)；`无限/unlimited/inf/0/乱写`→`UNBOUNDED_MAX_TOKENS=8192`（推理模型安全上限）；具体正数原样生效。
  - `/api/ai/plan` 现传 `maxTokens: resolveMaxTokens(env.AI_MAX_TOKENS)`；`/api/ai/chat` 与 `/api/settings` 的 maxTokens 显示也改用它。
  - 预算耗尽提示文案改为明确"写具体数字（如 8192），别写'无限'"。
- **实测**：`resolveMaxTokens` 单测 10 例全过；`tsc --noEmit` 干净；已部署 NAS 并验收（health ok / dataWritable true / accountCount=1 不变 / 容器 Recreated）。
- **配置落地**：NAS `data/.env` 原本是 `AI_MAX_TOKENS=4096`（并非用户以为的"无限"），已用容器内 node 改写为 `8192`（属主 node:node 可写，readEnv 每次请求重读，无需重建镜像）。
- **给用户的结论**：重试"房间2生成L形橱柜"应不再空正文；若个别复杂请求仍不够，把 `AI_MAX_TOKENS` 调到 16384（前提模型支持，否则 API 会 400）。"无限"现在=8192，不是真·无限。
- **注意**：代码改了必须重建镜像才生效（已 rebuild）；但改 `data/.env` 的数值不用重建，重启容器即可（readEnv 每请求重读）。

## Bug 修复 3：AI 调用超时（上一轮把「无限」映射到硬上限 65536 造成的）
- **症状**：修完 400 后用户再试，报"调用超时"。
- **根因（我上轮的设计错误）**：把「无限」映射到硬上限 65536，而 `AI_TIMEOUT_MS` **根本没设**（走默认 120000ms）。实测 4096 的规划请求要 19–66 秒 → 65536 需要好几分钟，必然超时。
- **教训**：`max_tokens` 与 `AI_TIMEOUT_MS` 是联动的 —— 预算给得越大模型写得越久，"能设的最大值"不等于"能跑完的值"。把"无限"映射到硬上限等于制造超时。
- **修复**：
  - `aiContract.mjs` 新增 `PRACTICAL_MAX_TOKENS = 16384`（"能跑完的最大实用值"），「无限/unlimited/0/非法值」改为映射到它；**显式的具体数字仍夹到 65536**（不 400），即"用户自选档位后果自负"。
  - 提示文案与后台 hint 都加上"别一味顶到 64K，会超时，建议 8K/16K"。
  - `data/.env` 落地：`AI_MAX_TOKENS=8192`（够装推理+计划 JSON 且能跑完）+ `AI_TIMEOUT_MS=300000`（新增，原缺失走 120 秒默认）。
- **配置改完立即生效**：`readEnv` 每请求重读，`AI_TIMEOUT_MS` 数值改动**不需要重建镜像/重启容器**；只有代码改动才要 rebuild。
- **验收**：容器内实跑 `8192→8192 / 无限→16384 / 65536→65536 / 819200→65536`；`PRACTICAL_MAX_TOKENS` 已进镜像；health ok、dataWritable true、accountCount 1 不变。

## 根治：推理模型把预算吃光 → 从 reasoning_content 救援计划（不再调数字）
- **用户质疑**（该认的账）："一个问题为什么搞这么多次？" —— 前面几轮一直在调 max_tokens（4096→8192→65536→超时→回到 8192 空正文），**这是治标**。
- **真正的根因**：推理模型把**整个输出预算**都花在 `reasoning_content` 上，一个字 `content` 都没写就被截断（finish_reason=length）。预算永远追不上思考长度 → 调数字是 treadmill，且调大了就超时。
- **根治方案**（`/api/ai/plan`）：正文为空时，**先试着用 `extractJson(reasoning)` 从思考过程里把计划抠出来**，抠出来照样走 `validatePlan` 完整校验；成功则标记 `salvagedFromReasoning: true` 返回前端与审计（result:'salvaged'）。抠不出来才报错。
  - 为什么安全：救援内容仍过 `extractJson` + `validatePlan`，等于"不受信任的 AI 输出仍在边界被拦"，不是"尽力理解"。
  - 诚实性：响应带 `salvagedFromReasoning`，前端类型已透传（`PlanResponse` 加该字段），因为它是"边想边写的草稿"，可信度低于正式正文。
- **错误文案改为不再建议调大预算**：改为"不建议靠调大 AI_MAX_TOKENS 解决（预算追不上思考长度、调大了会超时）—— 最可靠是换非推理模型，或把需求说短"。
- **验证**：用真实契约形状模拟"计划写在思考里"→ `extractJson.ok=true`、`validatePlan.ok=true`，两条 cabinet.create（2200/rot0、1500/rot90）零拒绝。**不需再调任何数字**。
- **部署**：已推包重建并验收（镜像含 salvagedFromReasoning×3、新文案×1；配置仍 8192+300000；health 正常）。
- **附带发现**：契约 `cabinet.create` 的 `backUnits` 就是"双面柜（岛台）：前后两排背靠背、共用中板、无背板"，正对应用户"中间镂空/类似岛台"的需求；必需字段是 `params.name`（不是 target.cabinetName）。
