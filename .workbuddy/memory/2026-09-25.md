## 交付②：AI 按描述生成柜体（一句话长出内部结构）

用户原话：「目前 ai 功能太少，只能修改长宽高等一些基础参数……能不能利用 AI 根据描述生成」
（master 反馈五件事里的第 2 件，用户点名"下一步"先做这件）。

**根因判定：能力没开，不是模型不行。** `createCabinet` 本来就收 `units`、模板里也有"分区意图"
词汇，但 AI 契约把它挡在外面 → AI 只能走 `create → removeUnit×N → addUnit×N`，
既破坏性又超 12 步上限。**这次开的是契约，不是模型。**

**改动**（commit `f1ebf61`）：
- `shared/aiContract.mjs`：新参数类型 `unitIntents`（最多 8 个分区；每项只有
  kind / width / count / rodHeight / doorCount / nickname —— 全是语义，没有坐标/板件/图元）。
  `width` 是**期望值**，总和不必等于柜宽（AI 不做加法，摊派交给 `allocateWidths`）。
  新增 `unitIntentsSemanticError()`（挂衣区给 count → 告诉他用 rodHeight；层板区给 rodHeight → 拒；
  空区给 count → 提示改用 shelves），**校验器与编译器共用同一份**。
  `cabinet.addUnit` 补 `doorCount`。提示词由词汇表生成 → 新能力自动进提示词，不会漏。
- `src/ai/compile.ts`：`unitsFromIntents`（语义校验 → makeUnit → doors 由 doorCount 决定；
  缺省 = 开放格不带门）；**分区 id 累加去重**（否则都叫 unit_001 → 板件撞 id → 清单少一块 → 下错料）；
  不给 atX/atY 时用 `pickFreeSpot`（复用唯一的 `detectCollisions`，不写第二份 AABB）自动落位，
  放不下时说人话 + 说清怎么改。
- `src/ai/planRunner.ts`：修「字段自带假信息」缺陷 —— 成功步骤也带上了"被拒绝（总线没给原因）"文案。
- `src/core/geometry/project.ts`：`detectCollisions` 改 export（并写死注释：再写一遍 AABB = 第二份真相源）。

**验收**：`verify/ai-generate-acceptance.ts` 43 项（A 契约 11 / B 编译 12 / C 宽度恒等式 6 /
D 多步计划 6 / E 提示词 4 / F 缺陷回归 3）；浏览器探针新增 **B37**（真敲一句话 → 生成 →

## 交付①：复杂柜型能力矩阵（餐边柜 / 岛台 / 洗衣机柜）

用户原话：「如果遇到一些复杂的柜子怎么添加……如果是餐边柜以及岛台橱柜洗衣机柜应该怎么添加」
（master 反馈五件事里的第 1 件，优先级最高）。

**三种柜型的语义落点**（都不是新画法，是往同一份语义模型里加字段）：
- 餐边柜 = 现有分区语义的**模板组合**（sideboard：抽 2 / 开放格 / 对开门层板）。
- 岛台 = `layout.type:'double'` + `backUnits`（前后两排背靠背、共用中板、**没有背板**，
  排深 = 前后对半，前排 +1mm 保证 Σ=depth 严格成立）。
- 洗衣机柜 = `kind:'appliance'` + `appliance:{name, openingWidth/Height/Depth, topDrawers}`。
  洞口是"机器尺寸 + 安装余量"的**合成结果**；机器走甲购件，不进开料清单。

**关键架构决定**：
- **中板即背**：double 柜不产生背板板件；中板 + 后踢脚板替代。背板派生段整体 `if (!DB)` 跳过。
- **两排共用同一套派生函数**：generate 的 `buildRow`、views 的 `drawRowSide`、bodies3d 的 `drawRow`
  —— 前后排只差净宽表/层板深/脸的 Y 区间，绝不写第二份。
- **电器格净高口径**：洞口上方抽屉只拥有 `innerH − openingHeight − 过梁板t`；
  过梁板位置 = 距柜内底 openingHeight；电器格带门 → ERROR（RULE-APPLIANCE-DOOR，编译器与校验器双拦）。
- **矛盾模型不静默画**：type:'double' 无 backUnits / row 带 backUnits → ERROR；派生按 row 兜底保持可画。
- AI 三层防线全部延伸：契约 +5 个电器格字段、语义校验（count→topDrawers 互斥等）与编译器同调一份、
  提示词由词汇表生成自动覆盖。镜像语义：mirrorUnits 前后排一起 reverse。

**验收**：`verify/complex-cabinets-acceptance.ts` 64 项（A 契约 8 / B 三模板零 ERROR /
C 岛台派生+3D+镜像 / D 洗衣机柜过梁板+甲购件分流+洞口硬规则 / E AI 端到端 / F 负样本回归）；
浏览器探针新增 **B38**（AI 一句话建洗衣机柜：洞口三尺寸落地 / 甲购件分流 / 无新 ERROR / undo 一笔收回，
照 B37 教训自带现场存/还原）。`verify:all` EXIT=0，599 项全绿（`verify:cabinets` 已接入全量链）。
截图 `verify/out/ai-laundry-preview.png`、`ai-laundry-applied.png`。

## 新增经验（本轮血泪）

6. **mock 分支顺序也是契约**：B38 的原话"帮我生成一个洗衣机柜…"同时命中"生成一个"和"洗衣机"

## #4 报错人话化（fixHint 30%→100% + 一键修复）—— 已交付，621/621 全绿

**交付形态**：
- `src/core/rules/issueCatalog.ts` = 报错文案的**唯一真相源**（33 张卡：title / message / hint / fix / manual / severity）。
  `buildIssue()` 是唯一出口，**未登记的码直接抛错** —— 于是"新规则忘了写人话"在跑验收时就炸，
  "fixHint 100% 覆盖"是结构性保证，不是靠人记得写。
- 界面 `IssuesPanel` = 「主体按钮 + 可选一键修复」：有 `fix` 且传了 `applyFix` 才渲染按钮，
  否则渲染 `card.manual`。
- 修复走总线：`applyFix` 把 plan 还原成带 id 的命令走 `bus.execute` —— 与手动编辑同权同位，
  一次修复 = 一条命令 = 一次撤销，同样过记忆闸门、同样记审计。
- 验收 `verify/fixhint-acceptance.ts` 25 项（A 目录完整性 / B 人话质量分档 / C 一键修复清单 / D 真跑几何复核），
  已接入 `verify:all`。

**分档口径（写进验收，别再摇摆）**：
- 设计类报错必须给具体数字（差多少、改到多少）；
  程序缺陷类（恒等式 / 缓存 / 悬空板件）必须明说"**这是程序缺陷**"，而且一律不给一键修复 —— 一键修只会把 bug 盖住；
  **语义/结构矛盾类**（电器洞口本就不该有门、双面柜本就该有背面）本就报不出 mm，
  对它们硬要数字是塞水，改成要求"明说是你要定的事"。

**本轮抓到的最严重一类缺陷：「假按钮」**
- 「门板太宽」原来只给"加一扇门"：2200mm 的门格加一扇还是 1100mm，照样超 600 上限 —— 点了没反应。
  改成按 `enoughDoorCount()` 算出**真能压到上限的门扇数**（2200 → 4 扇，每扇 538mm）。
- 「门板太高」原来给"改门扇数"：**门高只由柜高与踢脚决定**，和门扇数无关 —— 点了门高纹丝不动。
  直接**去掉按钮**，改为给两条带数字的路径（降柜高 X mm / 抬踢脚 X mm）+ manual。
  判据始终是「预览 === 提交」：用修复后的真实几何复核，而不是信按钮上写的那句话。

**踩坑（新增第 10~13 条经验）**：
10. **断言退化比断言失败危险**：验收里写成 `BUILD(c).autoFix`（真名是 `fix`），取到恒 undefined，
    "有几条能一键修"永远是 0、"都没偷偷加按钮"永远绿。→ 过滤类断言必须配一条
    **反退化断言**（"目录里确实有 ≥3 条可修规则"，为 0 就是这条断言已经死了）。
11. **NaN 静默过关**：验收探针从 `proto.layout.boardT` 取板厚（boardT 是派生量，在 `geom.layout` 上），
    undefined 把整柜宽度算成 NaN → 本该报错的柜子静默过关。→ 板厚只认规则集材质厚度这一份来源，
    并在探针加"拿到了板厚"前置闸门。
12. **CommandBus 构造参数写反照样能跑**：`new CommandBus(rules)` → 把规则集当项目存进去，
    直到某句"读 .materials 炸了"才露馅、离调用点很远。→ 构造函数加防呆（Project 要有 cabinets 数组 / RuleSet 要有 materials），
    参数顺序对不对就该在构造函数里一眼看出来。
13. **浏览器里的结论不能外推到 node，反之亦然**：node 侧 bus 没装记忆规则，所以 node 侧
    "能建出 2700 高柜子"不代表浏览器里也能 —— mem_004_max_height_2400 会**连创建一起拦下**。
    造记忆门下的负样本时别跟记忆硬顶，改用同一路径上真实会触发的另外一条 ERROR。

**值域夹紧不是缺陷**：把进深设 60mm 命令返回 ok 但值变 100 —— `sanitize` 的 `clamped` 提示
由 `App.tsx` toast 出来，不是静默改数（"预览 === 提交"在输入环节也对）。

**B39 浏览器探针最终形态**（23 项）：造一台 2200×900×600 单门柜 → 一放下就同时挂两条硬错
（`RULE-DOOR-MAX-WIDTH` 有按钮 / `RULE-PANEL-OVER-SHEET` 门板 780×2160 放不进 2440×1220 无按钮），
**真去点 DOM 上的按钮** → 版本 +1、两条一起消失（同源连带，不是顺手改别的）、没冒新错；
再两次 undo 逐步对账（修 → 建），最后 `replaceProject` 还原现场。
