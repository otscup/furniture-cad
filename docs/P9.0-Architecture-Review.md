## 1. 当前架构总结

### 1.1 分层（自下而上，箭头 = 依赖方向）

```
types.ts                       authored 语义模型 —— 唯一真相源（无几何、无派生）
   │
   ├─ allocate.ts              尺寸分配 / 余量归属（整数保证 Σ 相等）
   ├─ layoutModel.ts           units(单行)/rows(分层) 两形的**唯一**判据
   ├─ geometry/                transform(唯一旋转实现) → generate → layout/assembly/project/views/bodies3d
   ├─ relations.ts             两柜怎么挨着（deriveContacts 唯一实现，声明 vs 推断分离）
   ├─ spatial/                 model(形状判定 + SPATIAL_TOL 唯一出处) · derive(事实) · door(P8.9 门扇) · validate(空间 issue)
   ├─ placement.ts             落位意图 → ResolvedPlacement（纯函数，唯一确定性解析器）
   ├─ placementDesign.ts       P8.3 设计语义（只判断、只提示、不改几何）
   ├─ designValidation/        P8.8/P8.9 组合层（**只组合不重判**，逐字节透传下层输出）
   ├─ rules/                   validate + corner + issueCatalog（**文案唯一真相源**）
   └─ manufacturing/           从最终几何派生制造信息（最下游）
        │
   commandBus.ts               唯一写入口：plan → dryRun(strict) → 确认 → execute → log/undo/redo（+ provenance 旁路）
        │
   ai/                          snapshot(白名单投影) → 契约(shared/aiContract.mjs) → compile → planRunner(沙盒)
        ├─ knowledge/           建议性知识（永不写模型）
        ├─ import/              adapter → NormalizedDesign → compileImport（走同一条链）
        └─ vision/              图片 → 结构化识别结果（带 confidence / source / notVisible）
        │
   ui/                          与 ai/ 同权同位，只能经 CommandBus 写模型
```

**实测的依赖方向证据**（全仓 grep）：

| 检查项 | 结果 |
|---|---|
| `core/**` 是否 import `ai/**` | 仅 `commandBus.ts` → `ai/memory.ts`（`Gate` 类型 + `formatGateError`，硬规则门，非"AI 设计"） |
| 谁 import `core/manufacturing/**` | **只有** `ui/panels/ManufacturingPanel.tsx` |
| 谁 import `export/**` | 只有 `manufacturing/bridge.ts` + `ui/panels/ExportPanel.tsx` |
| `designValidation` 是否进主规则链 | **否**（`commandBus.deriveFor` 里没有它；主链 = generateProject + validateCabinet + validateCornerInterference + validateAssemblies + deriveSpatial.issues） |

### 1.2 已经结构性地成立的六条不变量

1. **唯一写入口**：UI / AI / MCP / 脚本都只能经 `CommandBus.plan → execute`；写路径白名单 `isWritablePath(op, path, isProjectTarget)` 一视同仁地拒绝一切派生字段。
2. **预览 === 提交**：`planRunner.commitPlan` 提交的是**预览时那一批 Command 对象**（不是重新编译），且提交前比对 `baseVersion`；不一致即拒绝。
3. **AI 只出语义**：契约是有限动作清单（`ACTIONS` 21 条）+ 参数白名单 + 区间校验；模型**没有语法**能表达路径、坐标数组、板件清单。
4. **一种形状只许一处判断**：`layoutModel.ts`（units/rows）、`relations.ts`（接触）、`spatial/model.ts`（容差）、`issueCatalog.ts`（文案）。
5. **未知不伪造**：`unknown` 在 provenance / spatial / door swing / knowledge 四处都如实表达，且都不产生结论。
6. **下游不可反写**：derived（几何/清单/空间事实/设计结论）没有任何一条回写路径；`core/manufacturing` 与 `export` 位于最下游。

### 1.3 三层判定的现状（这是 P9 要接的地方）

| 层 | 输入 | 输出 | 能否阻断 | 归口 |
|---|---|---|---|---|
| 硬规则 | authored 模型 | `Issue`（102 条码中 **69 ERROR / 28 WARNING / 5 INFO**） | **能**（strict 模式） | `rules/validate.ts` + `rules/corner.ts` + `spatial/validate.ts` |
| 空间事实 | authored 模型 | facts（柜↔房间/墙/洞口/门扇）+ 净空判定 | 能（`SPATIAL-*` ERROR）/ 不判对错 | `spatial/` |
| 设计语义 | 已落位模型 | `designValidation`（三层组合，只提示） | **不能** | `placementDesign.ts` + `designValidation/` |

### 2.4 两条登记在案的风险（不是缺陷，是纪律要守住的地方）

**R-1（低）`placementProvenance` 与 `placement` 是"同一件事的两份记录"。**
`placement` 是位置，`provenance` 是"这个位置是怎么来的"。它们**永远不能互相反推**——P8.5-B 的纪律是"派生层零读取 provenance"，实测确实只有 `commandBus.ts` + `App.tsx` 读它。保住这条，两份记录就是"事实 + 解释"，不会变成第二真相；一旦有人允许"从 provenance.intent 反推坐标"，当天就会分裂。

**R-2（低-中）AI 会话里的语义副本是"未受模型校验的 Project 形状"。**
它不是缺陷（P3 的设计就是如此：中间产物是**候选语义方案**，不是派生视图），但它有一个真实后果：**同一份语义在"会话态"与"模型态"下，校验规则不同**（会话态过 `validateProposal`，模型态过 `Rules Engine` + `CommandBus` 白名单）。P9 引入候选布局后，这个差异会放大（N 个候选 × 每个候选都要过一遍）。建议：**候选一律沿用"会话态校验只做形状与语义，最终判定一律用同一份 Rules Engine"**，绝不在候选层新写一套判定。

## 3. 是否需要 Constraint Graph

### 3.1 结论：**当前不需要新增 `ConstraintGraph` / `DesignGraph`。不新增任何图结构。**

### 3.2 理由（不是"嫌麻烦"，是三条结构性理由）

**① 现有三层已经足够表达"什么被违反了"，因为它们是函数而不是图。**
`f(Project) → facts / findings / issues` —— 每次调用都从真相源现算，**没有缓存、没有增量、没有反向索引**。图结构要解决的问题是"多约束耦合下的传播与回溯"；当前系统只做**前向判定**（给一个位置，判它行不行），不做**反解**（给一堆约束，求位置）。

**② Resolver 的"反解"是单点局部的，天然不需要图。**
`resolvePlacement` 支持 absolute / adjacent / align / attach，四者都只依赖**一个参照柜**，且 `resolvePlacements` 已用 Kahn 拓扑排序解决"参照链"，成环则结构化拒绝（`PLACEMENT-CYCLE`）。这是一条**无耦合的依赖链**，不是约束网络。

**③ 图一旦被缓存或持久化，立刻违反两条核心不变量。**
- 进 Semantic Model ⇒ 模型里出现"计算出来的约束节点"，派生数据落盘（违反原则 2）；
- 被缓存 ⇒ 与 Project 漂移，出现"改了柜宽但图没更新"，而**这种不一致不报错**——正是本项目最怕的一类事故（"改一次全体失效"）。

### 3.3 现有能力是否足够（逐条对照）

| 未来的问题类型 | 现有能力 | 是否足够 |
|---|---|---|
| "这个柜贴的是哪面墙？" | `spatial/derive.classifyCabWall` + `designValidation` 的 `WallContactKind` | ✅ 足够 |
| "这两个柜挨着吗？怎么挨的？" | `relations.deriveContacts`（唯一实现） | ✅ 足够 |
| "这个位置合法吗？" | `ResolvedPlacement` + `Rules Engine` + `CommandBus` | ✅ 足够 |
| "门打开会撞柜吗？" | `spatial/door.classifyDoorClearance` | ✅ 足够 |
| "这个设计合不合理？" | `designValidation` | ✅ 足够（只提示） |
| "整面墙 3600，三个柜怎么分？" | **无** | ❌ 缺（见 §7-9） |
| "同时满足 A/B/C 三个耦合目标，求最优" | **无** | ❌ 缺（但见下） |

### 3.4 什么条件下才允许引入图 / 求解器（明确判据，避免以后拍脑袋）

**三条同时成立**才考虑：
1. 出现**真正的耦合约束**（一个约束跨 ≥2 个对象且不能逐条独立满足，例如"整墙总宽 = 墙长"且"各柜宽可调"）；
2. 需要**回溯 / 搜索**（存在多个可行解且要挑一个，或需要试探-失败-回退）；
3. 现有前向判定**无法在有限步内**给出答案（不是"写起来麻烦"，而是"根本没答案"）。

若成立，形态硬性要求：
- **derived**：每次从 Project 现算，不缓存或缓存必须由 `modelVersion` 严格失效（沿用 `geomCache` 的模式）；
- **临时运行对象**：只活在会话/一次计算里，**不进 Semantic Model、不进项目文件、不进 Knowledge**；
- **不产生第二真相**：图只能在"输入模型"的方向上读，任何写回都必须走 CommandBus 变成模型字段。

### 3.5 折中方案：把"耦合约束"放进候选枚举器，不要放进 Resolver

"整墙平分"这类耦合是**候选生成**问题，不是**落位解析**问题。它应当住在 P9.3 的候选枚举器里（可以枚举、可以失败、可以报告为什么这个候选不成立），而**不是**被塞进 `resolvePlacement` 把单点解析变成求解器。这条边界必须在 P9.2/P9.3 的设计里写死。

## 4. AI Planner 推荐架构

### 4.1 结论：**以方案 A 为骨架；方案 B 只作为 A 内部的一个"确定性候选枚举 + 筛选"子步骤，且 B 的产物不落地。**

```
                    ┌─────────────────────────────────────────────┐
 用户需求（自然语言）  │ ① Planner（LLM）—— 只出语义，无坐标           │
                    │    输出 DesignProposal（复用 P3 现有形状）    │
                    └───────────────────┬─────────────────────────┘
                                        ↓
                    ┌─────────────────────────────────────────────┐
                    │ ② Candidate Enumerator（确定性，纯函数）      │
                    │    对一个语义方案枚举出 N 个候选布局           │
                    │    枚举依据：贴墙段 / 对齐关系 / 洞口避让 /    │
                    │    组合关系 / 用户偏好（只做筛选，不做设计）    │
                    │    每个候选 = 语义方案 + 待解析的落位意图集合   │
                    └───────────────────┬─────────────────────────┘
                                        ↓
                    ┌─────────────────────────────────────────────┐
                    │ ③ Resolver（唯一几何 owner）                 │
                    │    resolvePlacements(...) → 坐标              │
                    │    然后：dryRunPlan（沙盒总线）→ 硬规则判定    │
                    │    然后：deriveSpatial → 空间事实与净空        │
                    │    然后：validatePlacementDesign/designValidation│
                    └───────────────────┬─────────────────────────┘
                                        ↓
                    ┌─────────────────────────────────────────────┐
                    │ ④ Ranker（确定性评分，**不是 LLM**）          │
                    │    LayoutCandidate{ 语义, 解析结果, 验证, 分数 }│
                    └───────────────────┬─────────────────────────┘
                                        ↓
                    ┌─────────────────────────────────────────────┐
                    │ ⑤ 用户对比 N 个候选 → 选定一个                │
                    └───────────────────┬─────────────────────────┘
                                        ↓
                    compileProposal → AiAction[] → planRunner（沙盒）
                    → 预览（同源）→ 用户确认 → commitPlan → 真 CommandBus
```

### 4.2 为什么不是纯方案 B

纯 B（`AI → Candidate Layout → Optimizer → CommandBus`）有三个结构性问题：

1. **"Optimizer 直接产候选"意味着候选的坐标由优化器产生**——那就出现了**第二个几何来源**（除 `placement.ts` 之外）。任何第二份旋转/坐标实现，迟早在某个角度上给出与主实现不同的答案，而且**不报错**。
2. **纯 B 无法复用 "预览 === 提交"**：优化器若自己维护一份项目副本并修改，就必须自己实现版本校验、原子性、审计——这正是 `planRunner` 已经解决的，重做一遍即分家。
3. **纯 B 把 AI 放在评判位上**：候选好坏由谁定？如果模型自己给候选打分，就出现了黑箱裁判（见 §6）。

### 4.3 AI 明确**不应该**产生什么（逐条，含理由与现有护栏）

| 禁止 AI 产出 | 为什么 | 现有护栏（已生效） |
|---|---|---|
| `x / y / rotation` 作为最终位置 | 模型看不见墙坐标，猜必撞墙 | `PlacementIntent.absolute` 要求 `origin:'authored'`，AI 传 `authored` 会被语义校验拒绝；`cabinet.move` 是 authored 兼容路径，不进 AI 方案 |
| `polygon` / `pts` / `path` 任何坐标数组 | 一给就同时产生第二份几何与"模型输出它拿不到的东西" | 契约参数白名单（多一个键整条丢）+ 快照不变量 I3（快照里不许出现长度 2/6 的坐标数组） |
| **墙贴合（wall attachment）的坐标** | 贴哪面墙、贴哪一侧（室内/室外）、贴哪一段是**派生事实**，不是模型可输入的参数 | 目前 AI **完全没有**"贴墙"动作（`cabinet.place.reference` 只能是 cabinet）。P9.2 若开放，必须开放成**语义**（`against-wall { wallId }` 或连 wallId 都不给，由系统选最近墙），**绝不开放坐标** |
| **门净空结论** | "门会不会撞柜"是判定结果，不是可指定参数 | 门扇事实只由 `spatial/door.ts` 产出；AI 无法写 `Opening.hinge`（契约未开放空间实体） |
| 门开启方向 / 铰链侧 | 用户的设计意图，系统不许替选 | `Opening.hinge/swingDirection` 不在 AI 契约里（P8.9 明确不扩大契约） |
| 直接改模型 | 绕开规则与审计 | 唯一写入口 CommandBus + `AiAction` 只是动作名 |

**一处需要精确区分（避免误伤）**：`attach`（面贴合）是**允许**的形态，因为它给的是**面名**（`targetFace`/`referenceFace`，来自 P2 的 `ConnectionEdge` 词汇表），不是坐标——AI 说"我的背面贴你的右端"，坐标由 Resolver 算。**面名是语义，坐标是几何**，这条分界就是"AI 能说什么"的准绳。

### 4.4 现有链路上必须补的两件事（P9.1 / P9.2 的内容，本阶段只指出）

**缺口 1（阻塞级）：AI 现在看不见空间。**
`AiSnapshot.rooms` 只有 `{ index, id, name, wallCount }`——**没有墙坐标、没有墙 id、没有厚度、没有洞口、没有门扇、没有房间形状、没有任何空间事实**。也就是说，AI 目前**在完全看不见房间的情况下被要求做室内设计**。这不是算法问题，是输入问题：任何"AI 空间规划"在这条补齐之前都不可能成立（它只能靠幻觉或靠用户口述）。

**缺口 2：契约动作上限 `MAX_ACTIONS = 12`。**
一个 6 柜布局（6 × `cabinet.create` + 6 × `cabinet.place`）= 12 条动作，正好触顶；整屋布局必然超限。这不是 P9.0 要改的东西，但它是 P9.3 必须正面回答的设计约束（要么分批计划，要么新增"批量语义动作"，两者都是契约变更，需要单独阶段与验收）。

## 5. Candidate Layout 是否需要新模型

### 5.1 结论：**A —— 临时运行对象。不进 Semantic Model、不进 Project 文件、不进 Knowledge。**

### 5.2 建议形态（设计，不实现）

```ts
/** 会话内候选布局 —— 不是模型，选定才成为模型 */
interface LayoutCandidate {
  id: string;                    // 会话内序号（如 cand_1），**不是模型 id**
  semantics: DesignProposal;     // 无坐标的语义方案（复用 P3 形状，不新造）
  resolution:
    | { ok: true; resolved: Array<{ intent: PlacementIntent; placement: ResolvedPlacement }> }
    | { ok: false; error: PlacementError };
  /** 硬规则阻断（为空才可能是"可采用的候选"） */
  blocked: Issue[];
  /** 原样引用 spatial 层输出，**不重判** */
  spatial: SpatialReport;
  /** 原样引用 P8.3/P8.8 输出，**不重判** */
  design: DesignValidationReport;
  score: DesignScore;            // 见 §6；每项必须可追溯到计算它的代码
  summary: string;               // 给界面的一行对比摘要（人话）
  notes: string[];               // 系统替它定的默认值（沿用 compileProposal 的诚实纪律）
}
```

### 5.3 为什么不进模型 / 项目文件 / Knowledge

| 选项 | 若选它的后果 | 裁定 |
|---|---|---|
| **A 临时运行对象** | 无副作用；候选与模型彻底隔离 | ✅ **推荐** |
| B Semantic Model | 模型里出现"没被选中的方案"⇒ 所有派生层（几何/清单/DXF/空间校验）都必须判断"哪些柜是真的"——**一种形状两处判断**，直接违反项目第 23 条原则 | ❌ |
| C Project 文件 | 派生数据 + 未确认事实落盘，违反原则 2；且候选分数/验证结论是**当次计算**的结果，落盘后必然与模型漂移 | ❌ |
| D Knowledge | 候选是"这次设计"，不是"可复用知识"。混进去会退化成一次性记录（踩过"偏好 scope 挂具体对象名"的坑），且 Knowledge 的门槛是"用户确认过的可复用命题" | ❌ |

### 5.4 现成的先例，直接沿用纪律

**`core/variants.ts` 已经是一个"候选"实现，而且纪律已经踩实**：

> 「**中间产物是「候选语义方案」，不是「正面图」**」；「候选柜体**不在任何 Project 里**。它是纯产物，落盘/入栈之前不是真相源」；「选定之后才走 CMD.createCabinet 落地 —— **候选不是模型，选定才成为模型**」。

`VariantDraft` 的形态 = `cabinet(语义) + front(派生视图) + issues + stats + summary + error`，就是 `LayoutCandidate` 的柜内版。**P9.3 应当把 `LayoutCandidate` 设计成"`VariantDraft` 的房间级推广"，而不是另起一套。**

同样可复用的还有 `adoptVariant`：**候选里的占位 id（`variant__xxx`/`unit_001`）在采用时全部换成真 id**——因为项目里可能已有同名 id，而**撞 id 不报错，只会静默共用一条记录**。`LayoutCandidate` 落地时必须走同一条"全部换 id + takenIds 累积"的路径。

### 5.5 持久化边界（建议明确写进 P9.3 验收）

- 候选**不落盘**；
- 只有"这一轮生成了几个候选、用户选了哪个、每个候选的评分摘要与验证计数"可以作为**审计/对话历史**落 sessionStorage —— 沿用现有纪律（整份会话一起落、落盘前剪重：`thinRun` 已经在剪 `draft`）；
- **不留完整候选 Project**（N 个候选 × 整份 Project = sessionStorage 立刻爆，且会把"未确认候选"变成可恢复状态）。

## 6. Design Score 架构

### 6.1 结论：**LLM 不作最终评分器。评分必须完全确定性的、可追溯的、可复算的。**

### 6.2 评分三源（全部来自已有确定性输出，不新增判定）

```
DesignScore = Blocking(一票否决/排除)  ⊗  Facts(可判定项)  ⊗  PreferenceMatch(偏好命中)
```

| 来源 | 具体内容 | 现有出处 | 作用 |
|---|---|---|---|
| **Validation Facts（硬）** | `RULE-*` ERROR（69 条中与布局相关者）、`SPATIAL-*` ERROR（`CABINET-OPENING` 等）、`DESIGN-CABINET-WALL-CONFLICT`、`DESIGN-CABINET-DOOR-SWING`（P8.9，ERROR） | `Rules Engine` + `spatial/validate` | **不参与打分**，直接**排除候选**或标为不可采用 |
| **Validation Facts（软）** | `DESIGN-*` WARNING 计数与按码分组（门脸朝墙 / 离墙有缝 / 没靠墙 / 门前余量 / 窗被挡 / 门扇贴边 touch）、`CabWallRelation`、`CabOpeningRelation`、`WallContactKind` | `spatial/derive` + `designValidation` | 扣分项，**每项带出处** |
| **User Preference** | `resolveKnowledge(...).applicable` 里 op=`prefer` 的谓词命中（含 `PlacementContext` 上下文匹配） | `knowledge/resolver` | 加分项 |

### 6.3 LLM 的角色：**只解释，不裁判**

允许：把评分明细讲成人话（"A 更省空间，因为……"），或者在用户追问时解释某个候选为什么被排除。

禁止：
- 覆盖确定性排序（若 LLM 的推荐与排序不一致，必须**显式标注"与系统评分不同"**，不能悄悄替换）；
- 产生新指标（"为了看起来专业"造一个"美观度 82 分"——与 P8.8 §16 同一条纪律）；
- 影响 `blocked` 判定（硬规则一票否决不可被 AI 翻案）。

### 6.4 三条硬性设计约束

1. **分数必须可展开**：`DesignScore` 不是 `number`，而是**条目化的**（`items: Array<{ code, kind:'good'|'bad', weight, detail, source }>` + 派生的总分/排序键）。"为什么 78 分"必须能逐条读出来。理由：黑箱总分在下一个阶段就会变成"谁也不知道为什么 A 比 B 好"，而这种不可解释性会在真出问题时无法 debug。
2. **不新建判定**：每个条目必须指向一个已有的 `Issue` / fact / predicate，**不许在评分层新写"这里应该留 900mm"**。若某个评分维度真的需要新判定，那就是一个**新的 issue 码**（经 `buildIssue`），不是评分层的私有规则。
3. **权重要当"工厂偏好"对待**：权重若可配，应进 `RuleSet`（工厂级）。但要明确警告：**可配权重会让评分隐式变成硬规则的替代品**（用户会以为"低分就放不下"）。因此界面上必须始终并列显示"阻断项"（硬）与"评分项"（软），绝不用一个总分掩盖两者区别。

### 6.5 一处需要补的小缺口（登记，不在本阶段实现）

`preferredOrientation` / `preferredAlignment` 现在都是"**返回第一条命中**"（`for (const { entry } of res.applicable) { ... return }`）。评分需要的是**全量命中计数 + 每条命中带 why**。这是从"取一条建议"到"评估匹配度"的真实差异，需要一个并行的 `matchOrientations(res, ctx): ResolvedKnowledge[]` 之类的只读扩展。**不影响任何现有行为**（新增函数，不改旧函数）。

## 7. Constraint 优先级

### 7.1 现状核查

| 层 | 归口实现 | 等级 | 能否阻断 |
|---|---|---|---|
| Hard Rule | `rules/validate.ts`（`RULE-*`）+ `rules/corner.ts` + `spatial/validate.ts`（`SPATIAL-*`）+ 记忆门 `ai/memory.Gate` | ERROR | **能**（strict） |
| Design Validation | `placementDesign.ts`（P8.3）+ `designValidation/`（P8.8） | ERROR（声明与事实不符 / 穿墙）+ WARNING | **不进主链**，不阻断 |
| Knowledge | `knowledge/model.ts`，三层 `hardRule > designKnowledge > userPreference` | 建议 | **不能**（`hardRule` 层只是引用，执行体仍在 Rules Engine / 记忆门） |
| Preference | 同上（`userPreference` 层），被硬规则压制时进 `suppressed` + `conflicts`（双向登记，不静默覆盖） | 建议 | 不能 |
| AI Suggestion | `DesignProposal` → 编译 → 沙盒干跑，失败即拒 | 提案 | 只能"被拒绝"，不能提升等级 |

### 7.2 建议的优先级（**需要一处修正**）

用户给出的链：

```
Hard Constraint → Geometry Truth → Design Rule → User Preference → AI Proposal
```

**修正建议**：把"Geometry Truth"从"链条上的一级"改为**"事实层"与"判定层"的分割线**：

```
┌─ 事实层（无优先级，不判对错）───────────────────────────────┐
│  spatial facts · contacts · footprint · wallPolygon · 门扇包络  │
│  —— 它们只是"是什么"，天生没有等级，也永远不能"压过"任何规则     │
└───────────────────────────┬────────────────────────────────┘
                            ↓ 判定层读事实
┌─ 判定层（有优先级）────────────────────────────────────────┐
│  Hard Constraint   （ERROR，能阻断：RULE-* / SPATIAL-* /      │
│                       DESIGN-CABINET-WALL-CONFLICT / DOOR-SWING）│
│        ↓ 压制                                                  │
│  Design Rule       （DESIGN-* WARNING，只提示）                 │
│        ↓ 让步                                                  │
│  User Preference   （Knowledge userPreference，可被硬规则压制）  │
└───────────────────────────┬────────────────────────────────┘
                            ↓
┌─ 提案层（最弱，只能被拒绝）─────────────────────────────────┐
│  AI Proposal —— 不能提升等级、不能翻案、不能覆盖偏好            │
└────────────────────────────────────────────────────────────┘
```

理由：把"Geometry Truth"当成链条上一级会导出两个错误结论——"几何事实可以压过设计规则"（错：事实无所谓压过）和"几何事实比硬规则更基础所以更优先"（错：硬规则正是关于几何的判定）。**事实与判定分开，是 P8.7/P8.8 已经确立的纪律（facts / findings 分离），优先级一节必须与它一致。**

### 7.3 另外两处需要登记的优先级问题

**（a）"门"的两种含义在等级与命名上撞车。**
系统里现在有**三处**"门"的概念：

| 概念 | 码 / 类型 | 层 | 等级 |
|---|---|---|---|
| 柜内门板（图面开向表达） | `UnitSpec.doors{ count, hinge, hingeSide }` | authored 语义 | — |
| **房间门扇开启扫过柜体** | `DESIGN-CABINET-DOOR-SWING` | `spatial/`（P8.9） | **ERROR** |
| **柜门打开扫到邻柜** | `CORNER-DOOR-SWING` | `rules/corner.ts` | **WARNING** |

后两者说的是**完全不同的事**（房间门 vs 柜门），但共用了 `DOOR-SWING` 这个后缀，且等级一个 ERROR 一个 WARNING。**风险**：以后改一处会顺手改错另一处；用户看到"门会扫到"也不知道说的是哪扇门。
**建议**：P9 里做一次**纯命名校准**（不改任何行为、不改判定）：例如把 `CORNER-DOOR-SWING` 改为 `CORNER-CABINET-DOOR-SWEEP`（柜门扫邻柜），把 P8.9 的保留为"房间门扇 / DOOR-SWING"。这属于文案与码名变更，需要一次独立的、带迁移考虑的小任务（**本阶段不改**）。

**（b）Knowledge 的 `hardRule` 层必须保持"只是引用"。**
`hardRuleEntries(ruleCodes, corrections)` 把规则码与 active Correction 变成知识条目，供 Resolver **提前暴露**。这条不能变味：一旦 Planner 拿这条知识去"自己判断硬规则"，就会出现硬规则的两个执行体。**保持"引用 id、不复制实现、最终拦截仍在原执行体"。**

## 8. 全屋布局需要哪些缺失能力（只列缺口，不设计实现）

### 8.1 已有

`Cabinet footprint` · `Room` · `Wall`（中心线+厚度+高度）· `Opening`（door/window + offset/width + 铰链/朝向）· `Door Swing`（90° 包络 + 净空判定）· `Placement Resolver`（absolute/adjacent/align/attach）· `PlacementIntent + Provenance`（四态权威）· `relations`（接触）· `spatial facts`（三类关系）· `designValidation`（设计语义）· `Knowledge`（三层 + 上下文 + 冲突）· `candidateSpots`（贴墙/拼接候选点）· `buildVariants`（风格候选）· 硬规则 102 码。

### 8.2 缺少（按 P9 的阻塞程度排序）

**A. 输入可见性（阻塞级）**

1. **AI 快照里完全没有空间信息**（只有 `rooms[].wallCount`）——看不见墙、洞口、门扇、空间事实。**这是"AI 空间设计"的第一阻塞**，优先于任何算法。
2. 没有"**墙上的可用段**"派生（一面墙被洞口切开后剩下的可贴区间）。做整墙排布必然需要，现在只有 `openingRect` 的局部矩形。
3. `Opening` **没有高度 / 窗台高 / 门洞高**（只有 offset/width）——影响"柜会不会挡窗/挡门楣"的判定精度（P8.8 目前用"窗在柜后"的近似）。

**B. 家具与功能语义**

4. **没有家具类别**（`UnitSpec.kind` 是**柜内分区**类型，不是家具类别）——"这是冰箱位 / 洗衣机位"现在靠 `ApplianceSpec`（柜内嵌入洞口），不是独立功能实体。
5. 没有**功能分区**（备餐区/洗涤区/烹饪区/储物区）。
6. 没有**家电语义**（尺寸族、散热/开门/接管需求）。
7. 没有**厨房动线 / 工作三角**。
8. 没有**收纳容量/功能规则**（"这个衣柜够不够两个人用"）。

**C. 空间关系规则**

9. **没有"柜与柜之间通行净宽"的通用判定**——`SPATIAL_TOL.OPENING_ZONE=600` 是**洞口**的通行带（针对单个洞口），不是"两台柜体之间的通道宽度"。这是最直接的缺口：现在 `cabinet ↔ cabinet` 只有 `RULE-CABINET-OVERLAP`（重叠）与 `relations`（接触），**没有"离得太近/太远"的语义**。
10. 没有**人体工学 / 作业面高度**规则。
11. 没有"**多洞口联动**"（转角两扇门同时开）。
12. 没有**楼面/天花/Z**（明确不在范围内，因此"吊柜/通顶"只能靠柜体高度 + `bodyLift` 表达——这是一个已知的表达上限，不是缺陷）。

**D. 组合与整墙**

13. **没有整墙排布**（N 个柜平分一面墙、总宽 = 墙长、余量归属）——只有单柜的 `allocateWidths`，没有跨柜分配。
14. 没有**主次/优先级**（"主柜必须居中，其余填充"）。
15. 没有**家具组合的自动补全**（`assembly.create` 之后要手动"按当前落位补全连接"）。

**E. 求解与候选**

16. 没有**全局耦合约束**求解（见 §3.4）。
17. 没有**多柜候选枚举器**——`candidateSpots` 只生成**单个柜体**的落点候选（贴墙段 + 与已有柜拼接角点），`buildVariants` 只枚举**柜内风格**。二者都是雏形，都不做组合枚举。

**F. 需求侧**

18. 没有**设计需求的模型**（"6 人餐桌"这类目标只能变成自由文本讲给 LLM）——`DesignProposal.title/summary` 是自由文本，`assumptions`/`questions` 是字符串数组。
19. 没有**目标/约束声明的入口**（用户想表达"这里必须留 900 通道"，系统里没有地方放它——放 Knowledge 会退化成不可判定命题，放模型会变成新字段）。

### 8.3 明确不在本阶段（也不在 P9 主体）设计的

自动布局 · 自动移柜 · 自动选开门方向/铰链 · 人流模拟 · 多人协作 · BIM/IFC · DXF 建筑导入 · 图片户型识别（见 §11 路线，属 P10）· Z 轴 · 3D 动态开门 · Door Swing Preference 自动学习 · 全屋布局求解器。

## 9. 图片户型识别边界

### 9.1 现状：用户要求的链路**架构上已经存在**，而且比要求更严

已实现的 Vision→Import 链路（P4/P5）：

```
图片
 ↓  VisionProvider（可换服务商，core 不硬编码任何厂商）
VisionResult：每个尺寸都是 { value, confidence, source: annotation | reference | estimate }
 ↓  凡看不见的（深度 / 板厚 / 内部隔板 / 连接关系 / 真实尺寸）→ notVisible
visionResultToNormalized → NormalizedDesign
   · 每个柜体带 confidence / uncertainty（**阻断应用**）/ caveats（不阻断，需用户「已知晓」）
 ↓  compileImport → AiAction[]（与 P3 走完全同一条链）
契约门 → dryRunPlan（沙盒 + 硬规则 + 记忆门）→ 预览（用户逐条确认）→ commitPlan
 ↓
Cabinet.origin{ source, label, batchId, confidence, uncertainty }   ← 留痕跟着柜体进项目文件
```

对照用户建议的 `Vision → Imported Hypothesis → User Confirm → Semantic Model`：**已支持，且更严**——`estimate`（纯视觉估计）类尺寸不能直接当生产尺寸；`uncertainty` 非空即阻断；`origin` 让"这是估的"永久可查。

### 9.2 但户型识别（图片 → CAD）**尚不存在**，且不应复用现有通道

现有 Vision 的输入是**家具照片/效果图**，产物是**家具语义**（`NormalizedDesign` 的 cabinets/units）。它**没有任何墙/房间的识别通道**（`VisionResult` 里没有 wall/room 概念）。

要做户型识别，建议**新增一种假设对象**，而不是复用 `NormalizedDesign`：

```ts
/** 户型识别假设 —— **不是 Project，不是 Semantic Model** */
interface FloorplanHypothesis {
  /** 全部是 hypothesis，不是 Wall[]；每条都带 confidence 与 source */
  walls: Array<{ start: Vec2; end: Vec2; thickness: number; confidence: Confidence; source: DimSource }>;
  rooms: Array<{ name: string; vertices?: Vec2[]; confidence: Confidence }>;
  openings: Array<{ wallRef: number; kind: 'door' | 'window'; offset: number; width: number; confidence: Confidence }>;
  /** 图片看不见的东西（层高 / 墙厚实测 / 承重属性 / 是否有梁） */
  notVisible: string[];
  issues: Issue[];          // 经 buildIssue，不自己拼文案
}
```

**为什么必须新增而不用现有 NormalizedDesign**：NormalizedDesign 的形状是"柜体的语义副本"，它的下游编译路径（`compileImport`）会产出 `cabinet.create`。若把墙塞进去，就会出现"AI/Vision 产出的墙坐标"——**用估计值污染了尺寸真相源**，而墙是**所有空间判定的地基**：墙错 100mm，`wallInteriorSide`、洞口影响带、门扇包络、柜↔墙关系会**全部系统性出错，且一条都不报错**。

### 9.3 必须禁止的形态 + 建议路径

**禁止**（用户已禁止，架构上同样必须堵死）：
```
Vision → 直接生成最终墙坐标 → Semantic Model
```

**建议**：
```
图片 → Vision（VisionProvider）
     → FloorplanHypothesis（含 confidence / notVisible / issues）
     → 用户在图上**校核并修改**（这一步不可省；不是"确认对话框"，是要能改坐标）
     → 逐项确认 → 生成 wall.create / opening.create 命令
     → CommandBus（plan → dryRun → 预览 → 确认 → execute）
     → Semantic Model
```

与现有纪律的一致性：**"不确定就问，不替用户猜"**（与 `ImportOrigin.uncertainty` 阻断同源）；**落地必须走 CommandBus**（可 undo、进审计、可被记忆门拦）。

### 9.4 两处要一起决定的小事（登记）

1. **来源标签**：`ImportSource` 现为 `'json' | 'dxf' | 'kujiale' | 'imageVision'`。户型识别的来源不宜复用 `imageVision`（审计会分不清"照片识别家具"与"图片识别墙"）——建议新增 `'floorplanVision'`，或让 `label/batchId` 承担区分并在码文案里说清。**不要在 P9 主体里顺手改枚举**（会牵动 `Cabinet.origin` 语义与迁移）。
2. **墙的"新建"命令族**：现在有 `Wall.openings` 的命令（opening create/update/delete），但墙本身的创建/编辑命令需要确认是否齐备（`RoomsPanel` 里有房间/墙的编辑路径）。这是 P10 的前置调研项，不是 P9 的。

## 10. Manufacturing 与 AI Design 的分层

### 10.1 结论：**当前是单向的，且 Manufacturing 处于最下游。P9 必须保持。**

### 10.2 实测证据

| 检查 | 结果 |
|---|---|
| `core/manufacturing/*` 的 import 面 | `../types.ts`、`../allocate.ts`、`../layoutModel.ts`、`../relations.ts`、`../geometry/project.ts`、`../../export/neutralSheet.ts` + manufacturing 内部 |
| 谁引用 `core/manufacturing/*` | **只有** `ui/panels/ManufacturingPanel.tsx` |
| Manufacturing 是否读 provenance / spatial / designValidation | **不读**（import 面里没有它们） |
| 谁引用 `export/*` | 只有 `manufacturing/bridge.ts` + `ui/panels/ExportPanel.tsx` |
| `core/**` → `ai/**` | 只有 `commandBus.ts` → `ai/memory.ts`（`Gate`，硬规则门） |

所以链路是：

```
Design（authored 语义模型）
   ↓
Semantic Model（types.ts）
   ↓
Derivation（geometry / spatial / designValidation —— 全部只读）
   ↓
Manufacturing Derivation（manufacturing/*，从最终几何派生）
   ↓
Export（export/*，DXF）
```

**单向、无回环。** `Cabinet.placementProvenance`、`UnitSpec.doors.hingeSide` 之类"设计意图"字段也**不进** manufacturing 的读取面。

### 10.3 P9 必须守住的三条

1. AI 设计阶段产生的任何新字段/对象（候选、评分、空间意图、需求模型）**都不许进 manufacturing 的 import 面**。
2. **不要把"制造可行性"做成评分项**。它已经是硬约束（快照 `limits` + `RULE-PANEL-OVER-SHEET` / `RULE-DOOR-MAX-WIDTH` / `RULE-SHELF-SPAN` / `RULE-RUNNER-TOO-LONG` 等）。做成评分项 = 同一件事两处判断，且会让用户以为"低分就能做"。
3. 建议在 P9.x 增加一条**常驻架构断言**（本条是护栏建议，不是 P9.0 的实现项）：
   `core/manufacturing/**` 不得 import `core/spatial/**`、`core/designValidation/**`、`ai/**`。
   理由：这三者都是"关于设计的判断"，一旦制造层开始读它们，"制造"和"设计"就互相渗透，而这条线一旦模糊就再也画不回来了（P7 的全部工作就是在建立"制造语义从几何派生"这条单向线）。

## 11. P9 推荐路线（**建议，不执行**）

### 11.1 路线

```
P9.0 Architecture Review                        ← 本次（只审查，输出即止）
P9.1 Spatial Context for AI                     ← 让 AI 看见空间（输入侧，纯投影）
P9.2 Spatial Design Intent Vocabulary           ← 让 AI 能说空间语义（语义侧，不产坐标）
P9.3 Candidate Layout Foundation                ← 候选语义方案 + 确定性枚举 + 落地路径
P9.4 Deterministic Design Score                 ← 确定性评分（LLM 不参与打分）
P9.5 AI Planner                                 ← 把上面四件串成"需求 → N 候选 → 排序"
P9.6 Multi-Solution Compare UI                  ← 对比与选定
P10.x Vision Floorplan Import                   ← 户型识别（独立阶段，见 §9）
```

### 11.2 为什么是这个顺序（而不是先接 LLM）

**先补"AI 能看见什么"（P9.1），再补"AI 能说什么"（P9.2），然后才是"系统怎么造候选并排序"（P9.3/P9.4），最后才把 LLM 接上去（P9.5）。**

理由就是 P8.1 之前的旧病：**让一个看不见墙坐标的一方去谈布局，它只能猜**。P8.1 的全部工作（Deterministic Placement Engine）就是在纠这一个病——"AI 只表达想怎么放，最终 x/y 必须由纯函数算出来"。如果 P9 先从"接 LLM"开始，就会得到**一个看不见房间却在谈室内设计的规划器**，于是要么回退到让模型猜坐标（推翻 P8.1），要么不断加提示词去打补丁（治不了根）。**输入可见性必须最先解决。**

### 11.3 各阶段的红线与主要风险（一句话版）

| 阶段 | 一句话目标 | 主要红线 | 主要风险 |
|---|---|---|---|
| P9.1 | AI 快照补空间语义 | **纯投影**：不新增判定、不新增模型字段；派生事实必须与 authored 明确分开（建议独立 `spatialContext` 块，不混进 authored 快照） | 派生事实被 AI 当成"可改的对象"；快照与草案漂移 |
| P9.2 | 新增柜↔墙的**语义**落位意图 | 坐标只能由 `placement.ts` 产出；新意图必须是**面名/目标**，不是坐标；`Resolver` 不变成求解器 | 新意图绕过 Resolver 自算坐标（出现第二份几何） |
| P9.3 | 候选语义方案 + 枚举器 + 落地 | 候选**不是模型**；落地必须换 id（takenIds）；耦合约束放枚举器不放 Resolver | 候选落盘 = 第二真相；枚举器变成"第二套判定" |
| P9.4 | 确定性评分 | 评分条目化可追溯；不新建判定（缺维度就加 issue 码）；LLM 不裁判 | 黑箱总分；权重隐式变硬规则 |
| P9.5 | Planner | 复用 dryRun/commit；`MAX_ACTIONS` 上限要正面回答；LLM 只出语义 | 模型被要求输出它拿不到的几何 |
| P9.6 | 对比 UI | 2D/3D 显示的必须是**同一个 deterministic 派生结果**（P8.9 已立的规矩） | "图上没撞、报告说撞了"——最不可信的情况 |

### 11.4 明确不做（延续既有禁止清单）

自动布局 · 自动移柜 · 自动选门开启方向 · 自动选铰链 · AI 自动改布局（不经确认）· 人流模拟 · 多人协作 · BIM/IFC · DXF 建筑导入 · 图片户型识别（P10 才谈）· Z 轴 · 3D 动态开门 · 门开启动画 · Door Swing Preference 自动学习 · 全屋布局求解器。

## 附：本次审查的一句话结论

**当前架构已经具备承载 AI Design Planner 的骨架**——唯一写入口、预览===提交、AI 只出语义、三层判定分离、未知不伪造、下游不反写，这六条不变量都在，且都有实测证据与常驻断言。

**缺的不是算法，是两样东西**：
1. **输入**：AI 现在看不见空间（快照里只有 `wallCount`）；
2. **载体**：候选布局与评分还没有自己的运行对象与纪律。

**因此建议的下一步是 P9.1（Spatial Context for AI），而不是直接接 LLM。** 先让规划器看得见房间，再让它说话。
