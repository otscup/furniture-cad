## 一、架构审查报告（编码前）

### 1.1 通读对象与结论

| 通读对象 | 它在评分里扮演什么 | 审查结论 |
| --- | --- | --- |
| `core/candidateLayout/{model,generate,index}.ts` | **被评分的对象**：`CandidateLayout{id,status:'draft',sourceIntent[],placements[],explanations[],unresolved[]}`；`CandidatePlacement{targetId,intent,resolved,issues,satisfies}` | 评分**只读**它，一个字段都不改；评分结果**不是** CandidateLayout 的一部分（不写回候选） |
| `core/designIntent/{vocabulary,model}.ts` | **设计规则的唯一出处**：`DESIGN_INTENT_GOALS[goal]{class,fact,satisfiedValues,expect}`；读侧唯一入口 `activeDesignIntents()` | "什么算满足"**不在这里重定义** —— 逐条读 spec 的 `fact` + `satisfiedValues` |
| `core/spatial/{derive,validate,model,door}.ts` | **空间事实**：柜↔房间 `inside/outside/crossing/unknown`；柜↔墙 `touching/near/crossing/none`；柜↔洞口 `clear/overlap/unknown`；门扇净空 `clear/touch/overlap/unknown` | 评分**只读这些枚举**，绝不重算（§八） |
| `core/designValidation/{index,validate,interpret,model}.ts` | **门槛与设计语义的唯一消费口**：`validateDesign()` → `findings(status:error/warning)` + `wallContacts(kind)` + `cabinets(room)` + `doorSwing` | 硬约束等级**不自定** —— 直接读 `findings[].status`（等级真相源仍是 issueCatalog） |
| `core/relations.ts` | `deriveContacts(project)` → 柜↔柜接触（`standalone` 的唯一依据） | 只读 |
| `core/geometry/project.ts` | `detectCollisions(project)` → `RULE-CABINET-OVERLAP` / `RULE-CABINET-IN-WALL`（均 ERROR） | 候选已带 `issues`；评分不重跑、不重写 AABB |
| `ai/knowledge/{model,resolver}.ts` | **偏好维度的唯一入口**：`resolveKnowledge(ctx, entries)` → `{applicable, conflicts, suppressed}`；`preferredOrientation(res, ctx)` | 只消费 `applicable`；不产生候选偏好、不升级、不覆盖硬规则（§六） |
| `core/variants.ts` | `VariantDraft.stats/summary` = 柜体**派生统计**（板件数/面积/重量） | **不可复用**为"方案好坏"评分 —— 它是"这只柜要多少板"，不是"这个摆法好不好" |
| `core/rules/issueCatalog.ts` | severity 唯一真相源（ERROR / WARNING / INFO） | 门槛等级从这里来（经 `validateDesign` 的 status 透传），不在评分层另写 |
| `core/placement.ts` | Placement Resolver（候选已过它） | **不碰**（红线） |
| `core/ruleset/factory-default.json` + `types.ts#RuleSet` | 权重配置的候选归属地 | **当前没有任何评分配置**（只有 `limits/policy/materials/edgebanding/hardware/stylePresets`）→ 见 §1.8 |

### 1.2 P9.3 CandidateLayout 当前结构（评分的输入）

```
CandidateLayoutSet { status:'draft', candidates: CandidateLayout[], unresolved: CandidateUnresolved[] }
CandidateLayout   { id, status:'draft', sourceIntent: string[], placements: CandidatePlacement[],
                    explanations: string[], unresolved: CandidateUnresolved[] }
CandidatePlacement{ targetId: string,           // 引用既有柜体（不是 Cabinet 本体）
                    intent: PlacementIntent,     // 语义落位（absolute）
                    resolved: ResolvedPlacement, // Resolver 的输出（唯一坐标出口）
                    issues: Issue[],             // detectCollisions 的结果（已按该柜过滤）
                    satisfies: CandidateSatisfies[] }  // 事实层对 sourceIntent 的满足情况
CandidateSatisfies{ goal: DesignIntentGoal, ok: boolean }
```

三个要点（决定评分怎么接）：
1. **候选里没有 Cabinet**，只有 `targetId` 引用 —— 评分想拿"当前状态"必须回 `project` 按 id 找。
2. `resolved` 是 Resolver 输出，**可直接拿来重建一份"把该柜按候选摆好"的项目副本** ——
   评分层据此调用既有 `validateDesign`，而**不需要**自己算任何几何。
3. `satisfies` 只覆盖 P9.3 能构造的两个目标（`wall-contact` / `standalone`），
   其余目标的满足性是 `false`（表示"没被问过"）。**评分不能拿它当"不满足"的证据** ——
   必须自己按意图词表去读对应事实维度（见 §1.3）。

### 1.3 已有 facts 能提供哪些评分依据

| 建议指标 | 读哪个既有事实（维度） | 读哪条既有规则 | 判得出吗 |
| --- | --- | --- | --- |
| 1. 无 blocking error | `candidate.placements[].issues`（ERROR）+ `validateDesign(clone).findings`（`status==='error'` 且挂在目标柜上） | severity = issueCatalog | ✅ 判得出 |
| 2. 满足 `wall-contact` | `cabinets[].contacts`（`interpret.describeWallContacts` 的 `WallContactKind`） | spec `satisfiedValues = ['back-wall-contact','side-wall-contact']` | ✅ |
| 3. 满足 `opening-clear` | `facts.cabinets[].openings[].relation` | spec `satisfiedValues = ['clear']` | ✅（`unknown` 归 unknown） |
| 4. 满足 `door-swing-clear` | `spatial.clearances[].status`（`DoorClearanceStatus`） | spec `satisfiedValues = ['clear']` | ✅（`unknown` 归 unknown） |

| 取舍方向三类（`kitchen-workflow` / `storage-priority` / `circulation-priority`） | **无 `fact`**（`fact === null`） | spec `class:'priority'` | ❌ **判不出来 → 记 `unavailable`，不进 score**（§七硬要求） |

### 1.4 Hard Rule / Design Rule / Preference 当前如何表达

- **Hard Rule（可阻断）**：三处执行体，**评分一处都不重写** ——
  `geometry/project.ts#detectCollisions`（`RULE-CABINET-OVERLAP` / `RULE-CABINET-IN-WALL`，ERROR）、
  `rules/validate.ts`（生产硬规则，ERROR/WARNING）、`spatial/validate.ts`（`SPATIAL-*`）。
  三者的等级统一由 `rules/issueCatalog.ts` 裁定，并经 `designValidation/validate.ts#statusOfIssue`
  折成 `findings[].status`。→ **评分层的门槛直接读 `status`**，不自己判"这条算不算硬错"。
- **Design Rule（设计语义，不阻断）**：`designIntent/vocabulary.ts` 的 goal spec
  （`class` / `fact` / `satisfiedValues` / `expect`）+ `designValidation/interpret.ts` 的
  设计语义分类（`back-wall-contact` 等）。这是"什么算满足"的规则 —— 评分**逐条读 spec**。
- **Preference（加权偏好，命令是"建议"不是"约束"）**：`ai/knowledge/{model,resolver}.ts`。
  三层优先级 `hardRule > designKnowledge > userPreference` 已由 resolver 算好：
  与硬规则冲突的偏好在 `suppressed` 里、**不进 `applicable`**。→ 评分只读 `applicable`，
  天然满足"未被 Hard Rule 压制"。

### 1.5 是否已存在可复用的评分 / 比较基础

**没有。** 全仓检索 `score|rank|weight|compare|best|winner|recommend`（排除注释）只命中两类：
① `weightKg` —— 板件**重量**（`geometry/generate.ts`、`commandBus.ts`），与"方案好坏"无关；
② `best` —— 局部变量（"离墙最近的那一面" `designValidation/interpret.ts:116/361`、
   `geometry/transform.ts:130`、`relations.ts:143`），是**几何最近**，不是**方案择优**。
`VariantDraft.stats/summary` 是柜体派生统计。→ **不存在任何评分/排序实现**，本层是**新增**。

但**可复用的"事实与规则消费口"齐全**：`validateDesign`（门槛 + 语义）、`deriveSpatial` /
`deriveSpatialFacts`（facts）、`deriveContacts`、`cornerTurnSide`、`activeDesignIntents`、
`resolveKnowledge` + `preferredOrientation`。→ 评分层是**纯组合层**（与 P8.8 组合层同构）：
**不产生任何新判定，只把既有结论翻译成"命中/未命中 + 为什么"**。

### 1.6 哪些"评分指标"其实会偷偷变成第二套规则

这是本阶段最容易走偏的地方。以下写法**一律禁止**（违反 §八，且都已在别处有过结论）：

| 危险的"评分指标" | 为什么是第二套规则 / 第二套真相源 |
| --- | --- |
| "离墙 ≤300mm 加分、>300mm 扣分" | 发明**新阈值**，与 `SPATIAL_TOL.TOUCH/NEAR`（唯一容差出处）打架 |
| "门扇扫过的面积越大越差" | 要自己算扇区面积 → **第二套几何**，§八明禁（`door.ts` 的 8 段折线近似只归它自己） |
| "柜间距离越近越好" | P9.2 已判定：柜↔柜**只有接触/不接触**（`deriveContacts`），**没有距离这个量** —— 定义它 = 发明一个永远返回"不知道"的词 |
| "储物量 = 板件数 × 重量 → 高分" | 把**产品口径**当设计规则（P9.2 `storage-priority` 已明确拒绝） |
| "L 型必须 270° → 加分" | P8.3 已明确拒绝的"设计习惯冒充规则"（左右转角、镜像都可能有别的合理朝向） |
| 自己判 corner/butt 与左右转来算朝向偏好 | **第二套接触/转角判定** —— 必须读 `deriveContacts` + `cornerTurnSide`（P8.3 唯一实现） |
| 用 `class:'priority'` 的词凑一个"动线分" | `fact === null` = 判不出来；补启发式 = 把设计习惯冒充可判定事实 |

**唯一安全的写法**：读一个**已算好的枚举值**，与 **spec 里声明的 `satisfiedValues`** 比一比。
比对本身不是判定，是"对账"。

### 1.7 用户边界逐条确认

| 用户要求 | 本层如何落实（可机器验证） |
| --- | --- |
| §二 纯函数：不重判穿墙/挡门/靠墙/房间关系/柜间关系/Door Swing | 评分层**不 import 任何几何原语**（无 `polyDistance`/`polysOverlapInterior`/`segInteriorCross`），只 import `validateDesign` / `deriveSpatialFacts` / `deriveContacts` / `activeDesignIntents` / `resolveKnowledge` |
| §三 每个 component 必须能回答 6 问 | `DesignScoreComponent{ source, fact?, rule?, isPreference, weight, why }` + `intentId`/`goal`/`preferenceId` —— **没有** `{score: 82}` 这种裸数字 |
| §四 硬错误不是"扣很多分" | **Hard Constraint Gate 前置**：有 blocking error ⇒ `status:'infeasible'`、`total:null`、`components:[]`（**valid 才进入软评分**） |
| §五 评分来源只有三类 | `source: 'fact' | 'rule' | 'preference'`（**闭集类型**）；评分层**不 import** `ai/aiClient`（无第四种来源） |
| §六 严格复用 Knowledge Resolver | 调 `resolveKnowledge()`，只读 `applicable`；`suppressed`/`candidate` 天然被排除；**不写 store**、不升级、不新建偏好 |
| §七 判不出就 unavailable | `class:'priority'` 的意图 → `kind:'unavailable'` 组件（`hit:'unknown'`），**不计入 total** |
| §八 不在 score.ts 出现新空间判定 | 断言：源码里无 `Math.sin`/`Math.cos`/`Math.hypot`/`Math.atan2`、无新 tolerance 常量字面量、无 `bbox`/`polygon` 算法 |
| §九 权重有归属、不写死 magic number | `RuleSet` 当前**无**评分配置 → **不强行扩展**（见 §1.8）；`weight: null` + `weightSource:'unassigned'`；`total` = **命中数**（确定性、可解释、无权重） |
| §十 compare 只做确定性比较 | `compareDesignScores(a,b) → -1|0|1`；导出面**不含** `winner`/`best`/`recommended`/`adopt`/`apply` |
| 不把 score 写进 project.json | 评分是纯临时对象；断言：评分前后 `serializeProjectFile` 逐字节不变、`schemaVersion` 不变 |
| 不修改 Semantic Model / Resolver / Spatial Truth / Manufacturing | 不 import `commandBus` / `export` / `manufacturing`；不改 `placement.ts`/`types.ts` |

### 1.8 本阶段结论：做什么、不做什么

**做**（严格限定在用户 §一~§十 的范围内）：

1. 新增纯临时层 `core/designScore/`（`model.ts` + `score.ts` + `index.ts`），形状：
   ```
   DesignScore { status:'valid'|'infeasible', total:number|null, totalKind:'hit-count'|'none',
                 weights:{assigned:false, note}, components[], hardFailures[],
                 preferenceMatches[], explanations[] }
   ```
2. **Hard Constraint Gate**：`status:'infeasible'` ⟺ 存在 blocking error（ERROR 级）。
   infeasible 时 `total:null`、`components:[]` —— **不假装它是一个有效候选**。
3. **条件命中统计**：逐条 active 意图 → 按词表 spec 的 `fact` 读既有事实 → `hit: yes|no|unknown`；
   `priority` 类 → `unavailable`。
4. **可解释 component**：每条都带 `fact` / `rule` / `why`；`total` = 命中数（**无权重**，如实标注）。
5. **Preference**：经 `resolveKnowledge` → `applicable` 的 `userPreference` + `orientation` 谓词 → 命中判定。
6. **确定性 compare**：`compareDesignScores`，只回答"好/差/平"，**不选 winner**。
7. 验收 `verify:design-score`（含变异测试：评分写回模型 / score.ts 里出现新几何判定 / 出现自动 adopt —— 三项**必须变红**）。

**不做**（明确留给后续，或红线）：

- ❌ **权重系统**：`RuleSet` 现无评分配置；强行扩展会动到被 `factory-default.json` + 解析 +
  迁移锁定的结构（为一个"完整"的评分引擎改动生产配置 = 用错归属地）。→ `weight: null`，
  `total` = 命中数，**如实说明"权重留到后续"**。
- ❌ P9.5 AI Planner、LLM 自动布局、自动选 winner、自动 adopt。
- ❌ 改 Placement Resolver / Semantic Model / Spatial Truth / Manufacturing；写 `project.json`。
- ❌ 把 `class:'priority'` 的取舍方向编出一个分数（§1.6）。

### 2.6 本次踩到的坑

1. **源码级判据必须先剥注释**：文件头恰恰会写"本层不 import `commandBus` / 不用 `SPATIAL_TOL`" ——
   那是**纪律声明**不是违规。首轮两条假红（35 / 49）都出自拿全文扫（`knowledge/store`、`SPATIAL_TOL`
   出现在 JSDoc 里）。修法：`stripComments()` 只扫代码，并给剥注释本身配哨兵自检（0.7 / 0.8）。
2. **哨兵要用"故意写坏的样本"自检**：`hasForbiddenExport` / `hasGeometrySmell` / `coordKeysIn`

### 3.1 候选生命周期：`draft → evaluated`（§十一）

- `CandidateLifecycle = 'draft' | 'evaluated'`（`core/designScore/model.ts`）。
  **`'adopted'` 在类型层写不出来** —— 与 P9.3 把 `CandidateStatus` 定成字面量、
  P9.2 把 `'system'` 从 `origin` 拿掉是同一手法。
- `EvaluatedCandidate { candidateId, fromStatus:'draft', lifecycle:'evaluated', score }`
  —— **运行态包装**。`scoreCandidateLayoutSet` 返回它，新增 `evaluateCandidateLayout` 单条入口。
- **为什么不让 `CandidateLayout` 自己带 `evaluated`**：`CandidateLayout` 是"枚举产出物"
  （P9.3，状态恒 `draft`）；"评过没评过"是**评估这件事**的属性，不是候选本身的属性。
  包在外面，P9.3 的对象仍然干净可复现，`fromStatus` 又保留了"这一步是推进而非重造"的痕迹。
- `evaluated` **不持久化**：不进 `project.json`（序列化里既无 `evaluated` 也无候选 id）、
  不进 Semantic Model、不进 Knowledge。

### 3.2 AI 只读候选评分块（§十二）

> 判读依据：P9 的阶段惯例是"每阶段给模型加一块**能读、不能写**的上下文"
> （P9.1 `spatialContext`、P9.2 `designIntent`，见 plan §23.20 "提示词里只给『能读』，
> 并明说『本阶段不能写』"）。§十二 的"AI 可以读取 … Candidate Score / 但本阶段不让 AI 决策"
> 是同一句式，因此**新增一块只读投影**，而不是仅写一条边界声明。

- 新增 `ai/candidateScoreContext.ts`：`buildCandidateScoreContext(project)` **纯投影**
  （枚举走 P9.3 `generateCandidateLayouts`，评分走 P9.4 `scoreCandidateLayoutSet`，
  本文件一次判定都不做）。
- 快照新顶层键 `candidateScore`：`{ readOnly:true, note, preferencesApplied:false,
  counts{evaluated,feasible,infeasible,truncated}, evaluated[{id,lifecycle,status,total,
  unavailable,hardFailures[]}] }`。
- **零坐标**：没有任何 x/y/rotation/resolved/多边形（与 I3 一致，逐条断言）。
- **`preferencesApplied: false`**：偏好要经 `resolveKnowledge(entries)`，而快照构建这条路上
  **没有** Knowledge 条目（读 store 会把存储/环境耦合进快照，且在无浏览器的验收环境里会假失败）。
  → **如实标注**，免得模型把"没列出来"读成"没命中"。
- **`note` 明说"看到评分 ≠ 可以据此选择"**；动作清单**仍 21 条**，没有任何"选方案/落地"的动作。

### 3.4 未知处理（§十四）：`unknown ≠ failed ≠ clear`

- `hit: 'unknown'` + `kind: 'unavailable'`（取舍方向类、房间级条件类）—— **不计入 total**。
- **★ 本轮修掉一处真缺陷（M4 的由来）**：`door-swing-clear` 原先只读
  `doorSwing.clearances`，而**判不出开启方向的门根本不产出净空行** →
  空数组被读成"让开了"。这正是"把 unknown 当 clear"。
  修法：再看本柜所在房间里有没有 `doors[].status === 'unknown'` 的门，有则 `unknown`。
- `room-inside`：房间不闭合（`SPATIAL-ROOM-OPEN` 是 WARNING，不阻断）⇒ `unknown`，
  候选仍 `valid`，所以这个 `unknown` 是**看得见**的。

### 3.7 本次踩到的坑（P9.4 续）

1. **★ 自己的断言可能是瞎的**：M5 首轮只让 108 变红，98（"评分不修改 Candidate"）竟然没抓到 ——
   因为它在**已经被评过**的候选上取快照。修法：另起一份**全新、从未评分过**的候选来钉这一条
   （新增 100b）。**"断言不可信比失败更危险"** 又一次被印证。
2. **"判不出来"往往表现为"这一行根本不存在"**：P8.9 对判不出开启方向的门**不产出净空行**，
   而不是产出 `status:'unknown'` 的行。只看净空行 = 把缺席读成"没问题"。
   凡消费"逐条事实列表"的地方，都要问一句：**这一条为什么不在列表里？**
3. **某条能力"事实层只给一半"**：`door-swing-clear` 能拿到 `clear/touch/overlap`，
   但 `overlap` 同时是 **ERROR** ⇒ 该候选进不了软评分，"未命中"在软评分里根本不可观测。
   这类情况下**不要硬造一个 'no'**，而应断言"它被闸门拦住了"（硬错误不降级为软失败）。
4. **AI 边界的"可以读取"要落到可验证的块**：只写一句"AI 可以读评分"无法被机器检验；
   落成一块**只读、零坐标、无 winner** 的投影后，才可以用断言钉住（零坐标 / 无 winner 字样 /
   `preferencesApplied:false` / 无 apply·adopt 字段）。
