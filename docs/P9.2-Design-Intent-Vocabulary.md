# P9.2 Spatial Design Intent Vocabulary —— 审查 + 实施记录

> 阶段目标：把"用户到底想要什么"从**自然语言**抬升为一层**封闭的、可判定的、不含坐标的**语义词汇。
>
> 本阶段**只定义语言**：不生成候选布局、不摆柜、不搜索、不接 LLM Planner、不动 Placement Resolver、不动 Spatial Truth。
> 链路里 `Intent → Candidate Layout(P9.3) → Placement Resolver → Spatial Validation` 只在**第一个箭头之前**做事。

# 一、审查结果（实现前）

## 1.1 现在已有哪些"语义表达能力"（逐层核对）

| # | 已有能力 | 位置 | 它表达什么 | 有没有坐标 |
|---|---|---|---|---|
| 1 | `Cabinet.placement{x,y,rotation}` | `core/types.ts` | 柜体**在哪**（背面左角 + 逆时针角） | **有**，Geometry Truth 本体 |
| 2 | `PlacementIntent`（P8.1/P8.2） | `core/placement.ts` | 落位**指令**：`absolute / adjacent / align / attach` + `side / alignment / face / offset` | 无（`absolute` 除外，且强制 `origin:'authored'`）；**输出**坐标 |
| 3 | `PlacementIntentDecl`（P8.5-C1） | `core/placement.ts` | 第 2 项的 `Omit<…,'targetId'>`，作为 provenance 随命令走 | 无 |
| 4 | `PlacementContext{contact,turnSide}`（P8.4） | `ai/knowledge/model.ts` | 偏好**在什么情形下**成立（角接/并排 × 左/右转角） | 无 |
| 5 | `Connection{kind:corner\|butt\|stack, origin:authored\|inferred}`（P2） | `core/types.ts` | 两柜**怎么连**（语义关系） | 无 |
| 6 | `FurnitureAssembly`（P2） | `core/types.ts` | 一组柜 + 它们的关系 | 无 |
| 7 | `Opening{kind,offset,width,hinge?,swingDirection?}`（P8.7/P8.9） | `core/types.ts` | 洞口怎么开、门扇往哪开 | 无（世界坐标纯派生） |
| 8 | `KnowledgeEntry{layer,predicate,scope,evidence,confidence,status}`（P6） | `ai/knowledge/model.ts` | **建议性**知识；`candidate/active/rejected`；**不进模型**（独立 localStorage JSONL） | 无 |
| 9 | `Correction`（记忆门） | `ai/correctionStore.ts` | **拦阻性**记忆（编译成可执行检查挂总线上） | 无 |
| 10 | `ImportOrigin{source,confidence,uncertainty}`（P4） | `core/types.ts` | 这只柜**怎么来的**、可信到什么程度 | 无 |
| 11 | `AiSnapshot.spatialContext`（P9.1） | `ai/spatialContext.ts` | **派生**空间事实（只读投影） | 无 |
| 12 | `VariantDraft` | `core/variants.ts` | 候选语义方案（"候选不是模型，选定才成为模型"） | 有 `placement`（候选柜体自带） |

**核对结论**：系统已经有四种"语义表达"——**落位指令**（2）、**关系声明**（5/6）、**建议性偏好**（8/9）、**派生事实**（11）。
缺的那一种，是"**用户的设计目标**"：不是"放在哪"、不是"和谁连着"、也不是"我习惯这样"，而是"这个房间我想要什么效果"。
**这是本阶段要补的那一层，且它与已有的四种都不重叠。**

## 1.2 需求逐项 vs 现状 vs 唯一确定性来源

| 需要表达的设计目标 | 现状 | 既有唯一确定性来源 | 能否判定 |
|---|---|---|---|
| 储物优先 / 动线优先 / 通行优先 | 无 | 无（这是**取舍方向**，不是事实） | ❌ 不可判定（如实标注） |
| 希望柜体贴墙 | 无 | P8.8 `WallContactKind`（`back-wall-contact` / `side-wall-contact` / `front-wall-contact` / `wall-near` / `wall-conflict` / `floating`） | ✅ |
| 希望洞口影响带净空 | 无 | P8.7 `CabOpeningRelation = 'clear' \| 'overlap' \| 'unknown'` | ✅ |
| 希望门扇开启区净空 | 无 | P8.9 `DoorClearanceStatus = 'clear' \| 'touch' \| 'overlap' \| 'unknown'` | ✅ |
| 希望靠近门窗 | 无 | P8.8 `DESIGN-CABINET-NEAR-DOOR` / `DESIGN-WINDOW-BEHIND-CABINET`（阈值 `DESIGN_TOL.APPROACH = 600`，**唯一出处**） | ✅ |
| 希望留在房间内 | 无 | P8.7 `CabRoomRelation = 'inside' \| 'outside' \| 'crossing' \| 'unknown'` | ✅ |
| 希望独立摆放（不与柜相接） | 无 | P2 `deriveContacts()`（全项目唯一一处"两柜怎么挨着"） | ✅ |
| 希望与某柜对齐 / 相邻 / 贴合 | 无 | **已经是 `PlacementRelation`**（第 2 项） | — 见 §1.3 |
| 希望"靠近某柜" | 无 | **没有**：事实层只有柜↔**墙**的 `near`（`SPATIAL_TOL.NEAR`），柜↔柜只有"接触/不接触" | ❌ 无来源 |
| 希望面朝某方向 | 无 | 无（"朝向"就是 `rotation` 本身） | — 见 §1.3 |

**结论**：13 项里 6 项在既有派生层里**每一项都有唯一确定性来源**，可以直接定义成词；
另外 4 项**已经有主人**（`PlacementIntent` 的封闭词表），再定义第二份就是造第二套对齐/相邻真相源；
剩下 2 项**今天判不出来**（"储物优先"是取舍方向；"靠近某柜"没有柜间距离这个量）。
词表必须**按这三档分别处理**，不能混成一个"用户想说什么就收什么"的自由文本。

## 1.3 用户举例逐条裁决（本阶段最关键的判断）

| 举例 | 裁决 | 理由 |
|---|---|---|
| `room: kitchen-workflow` | ✅ **收**（priority 类） | 通用设计语言。不指向任何实体、不指向任何几何，只影响后续取舍方向 |
| `room: storage-priority` | ✅ **收** | 同上 |
| `room: circulation-priority` | ✅ **收** | 同上 |
| `cabinet: prefer-wall` | ✅ **收**，改名 `wall-contact` | 它是"**对既有事实的期望**"，不是位置。名字用**事实维度**而不是祈使句 —— 祈使句会诱导下一个人顺手把"多近算贴墙"写进去（那是 `SPATIAL_TOL.TOUCH` 的事，不是每条意图各写一个数） |
| `cabinet: avoid-opening` | ✅ **收**，改名 `opening-clear` | 依据 P8.7 的洞口影响带（600mm 通行带 = 人流，与柜间通道不是一回事） |
| `cabinet: near-window` | ✅ **收**，改名 `near-opening`（带 `openingKind` 可选值） | 依据 P8.8 的 `WINDOW-BEHIND` / `NEAR-DOOR`，阈值取 `DESIGN_TOL.APPROACH`（**不另写一个数**） |
| `cabinet: keep-clearance` | ✅ **收**，改名 `door-swing-clear` | 依据 P8.9 的门扇开启包络净空。"留多少"是 P8.9 的规则（90° 扇区），不是意图里的参数 |
| `cabinet: align-with` | ❌ **不收** | **已经属于 `PlacementIntent.relation === 'align'`**（P8.1 封闭词表），P8.5-C1 又把它登记成 Knowledge 的 `alignment` 维度。再定义一份 = 第二个对齐真相源，迟早出现"声明的 center"与"几何的 center"各指一条轴（`placement.ts` 的类注释已经为此写过一次警告） |
| `relationship: adjacent-to` | ❌ **不收** | 同上：`PlacementRelation.adjacent` 已经存在，且"相邻本身就是面贴合"，P8.2 明确拒绝再设第四个同义词 |
| `relationship: near`（两柜靠近） | ❌ **不收** | **判不出来**：事实层里柜↔柜只有"接触/不接触"（`deriveContacts`），没有"两柜距离"这个量；`SPATIAL_TOL.NEAR` 是柜↔**墙**的。定义它等于发明一个谁都算不出来的词 —— 违反本层"每一条要么给出事实依据、要么明说不判定"的纪律 |
| `relationship: avoid` | 🟡 **收成 `standalone`** | "不要和别的柜相接"有依据（`deriveContacts()` 零接触）；"不要挡住门窗"已由 `opening-clear` / `door-swing-clear` 覆盖，不重复设词 |
| `relationship: face`（面朝） | ❌ **不收** | "面朝"= 朝向 = `rotation` 的语义化说法 → 会变成第二条旋转真相源。而它**想说的那件事**（门脸别怼着墙）已经能由 `wall-contact` 的**期望取值集合**表达：只认 `back-wall-contact` / `side-wall-contact`，不认 `front-wall-contact` |

**一句话规则（写进词表注释）**：
> 凡是**已经能由 `PlacementIntent` 表达**的（放在哪、和谁对齐、和谁贴合），一律**不属于**设计意图；
> 凡是**今天算不出来**的（柜间距离、储物优先度量），一律**不进词表**，宁可少一个词也不给一个假词。

## 1.4 哪些不能进入 Model

| 不能进 | 原因 |
|---|---|
| 坐标 / 朝向 / 尺寸 / 阈值 | 会变成第二套几何真相；且"靠北墙"一旦能写成数，`{x,y,rotation}` 就只差一步 |
| `wallId` / `openingId` 等**几何实体引用** | 引用哪面墙 = 该贴哪面 = 落位决定。**在类型层就让它写不出来**（`scope` 只允许 `room` / `cabinet` 两种） |
| AI 推断出来的候选（`candidate`） | P8.5-B 的教训：**未确认与已确认是真实语义差异**。写进 model 就破坏"预览===提交"与"干跑===提交逐字节"两条不变量 |
| 判定结果（这条意图满没满足） | 派生，永不落盘。今天它满不满足要现算 |
| 事实 / 几何（包络、距离、间距） | 派生（同 P8.9：绝不存 swingArc / leafPolygon） |
| "system 提出"的意图 | §4 明令系统不产生偏好。**在类型层把 `'system'` 从 origin 闭集里去掉** —— 写不出来比校验拦住更彻底 |

## 1.5 载体与生命周期的审查结论

**载体**：`Project.designIntents?`（authored，可选，与 `assemblies` 同构的顶层扁平数组）。

为什么它是 model 的一部分，而 Knowledge 不是：
- Knowledge = **跨项目仍成立的习惯**（"我习惯背面齐"）→ 换个项目也成立 → 独立存储（`store.ts` 已写明"知识不进 project.json"）；
- Intent = **这份设计当前的目标**（"这个厨房要优先储物"）→ 换个项目就不成立 → **属于这份设计的真相源**。

**生命周期**（照抄 P6 Knowledge 的三态 + P8.5-B 的旁路纪律）：

```
用户明说 ──────────────► active（进 model）
AI 推断 ──► candidate ──► 用户确认 ──► active（进 model）
                   └────► rejected（不进 model）
系统 ──► 什么也不产生（类型层就没有这个 origin）
```

**模型只装 active**。candidate 只活在"意图提案"对象里（AI 输出 → 闸门 → 用户确认）。
理由与 P8.5-B 同源：**未确认的东西一旦落盘，下次打开就分不清"用户要的"与"AI 猜的"** ——
而 `preview === commit`、`dryRun === commit` 两条逐字节不变量都建立在"模型里只有已确认的事"之上。

**scope 挂具体对象名会不会重演 P6 的坑？**
P6 的坑是：把**可复用的偏好**挂在某个柜名上（`scope.cabinet=柜名`），换个对象就被 `scopeMatches` 挡掉，退化成一次性记录。
但设计意图**本来就只有本项目的意义**——"这个房间要优先储物"换个房间就不成立。
所以这里挂 `roomId` / `cabinetId` 是**本质**，不是复用。代价是**悬空引用**：柜/房间被删掉后意图还指着它。
处理照 P8.9 对 `hinge` 的口径：**注解类数据非法/悬空 → 丢弃并给出可见警告，绝不因为一个坏字段让项目打不开**；
同时只丢弃、不"猜一个最近的柜顶上"。

## 1.6 与 `PlacementIntent` 的同名风险（必须写清）

本层叫 `DesignIntent`，已有的叫 `PlacementIntent` —— 两个 "intent" 必须一句话分得开：

| | `PlacementIntent`（P8.1/P8.2，已有） | `DesignIntent`（本阶段，新增） |
|---|---|---|
| 回答 | "**怎么**放"（贴谁、对齐谁、哪两个面贴合） | "**想要什么效果**"（贴墙 / 让开门口 / 别挡住开门） |
| 形态 | 指令，进 Resolver | 目标，**不进 Resolver** |
| 输出 | **坐标**（`ResolvedPlacement`） | 什么也不输出（今天只被读） |
| 下游 | `Resolver → cabinet.place` | P9.3 候选枚举器（未来） |
| 能否互相表达 | 不能：一条 `DesignIntent` 对应**许多**合法落位 | 不能：`adjacent` 只说关系，不说"为什么" |

**两者是上下游**：`DesignIntent`（想要什么）→ P9.3 枚举 → `PlacementIntent`（怎么放）→ Resolver → 坐标。
本阶段**只做左边那个**。

## 1.7 本阶段结论

**做**：
1. `core/designIntent/`：封闭词表（含**事实维度**的闭集）+ 记录模型 + 生命周期 + 闸门（纯语义层，零几何、零坐标、零判定）。
2. `Project.designIntents?` 载体 + 文件往返（**只装 active**，悬空/非法条目丢弃并警告）。
3. AI 只读投影 `ai/designIntentContext.ts` + 快照顶层块 `designIntent`（**与 `spatialContext` 分离**，两块键集合不相交）。
4. **意图提案的语法与闸门**（"AI 推断只能产生 candidate"编译成代码）。
5. `verify:design-intent`。

**不做**（严格停在 P9.2）：
- 不接线的部分：AI 提示词里的意图提案通道、候选落地的写入口 —— 因为**不让模型说一件系统接不住的事**比先说出去再静默丢掉更重要（契约文件的"静默忽略是最危险的行为"）。
  本阶段提示词只告诉模型"**能读**、不能改"，与 P9.1 对 `spatialContext` 的口径一致。
- 候选布局 / 自动摆柜 / 优化搜索 / LLM Planner / Constraint Graph / Resolver 改动 / Spatial Truth 改动。

## 2.2 词表本体（9 个词）

```
取舍方向（priority，fact === null —— 唯一允许没有判定依据的一类）
  kitchen-workflow      动线优先（洗—切—炒顺序顺手）        scope=room
  storage-priority      储物优先                              scope=room
  circulation-priority  通行优先（留出走得开的通道）          scope=room

空间条件（condition，必须指向一个既有事实维度）
  wall-contact        希望贴着墙            fact=cabinet.wallContacts      scope=cabinet
  opening-clear       希望让开门窗洞口       fact=cabinet.openingProximity  scope=cabinet
  door-swing-clear    希望让开门扇开启范围   fact=cabinet.doorClearances    scope=cabinet
  near-opening        希望靠近门窗           fact=cabinet.openingProximity  scope=cabinet
  standalone          希望独立摆放           fact=cabinet.contacts          scope=cabinet
  room-inside         希望留在房间里         fact=cabinet.roomRelation      scope=cabinet
```

命名的三条纪律（写进了 `vocabulary.ts` 的文件头，且被验收逐条钉住）：

1. **用事实维度名，不用祈使句**：`wall-contact` 而不是 `prefer-wall`。
   祈使句会诱导下一个人把"多近算贴上"写进意图里 —— 那是 `SPATIAL_TOL.TOUCH` 的事。
2. **词表里不含任何数字**：验收递归扫整个词表对象，`typeof === 'number'` 一个都不许有。
   阈值是**规则**，只有一个出处；否则同一个词在两条意图里意思不同。
3. **每条词必须指名"将来对账时读哪一项既有事实"**，且该维度的**产出文件与信号串**要能在真实源码里逐字找到
   （`producer: { file, signal }`）。指向不存在的事实的词 = 判不出来的词 = 不许进词表。

**唯一例外是三个取舍方向**：它们没有判定依据，必须显式标 `class: 'priority'`。
验收的核心断言是：**`fact` 为空的词恰好就是 priority 这一类** —— 防住"随手加一个判不出的词"。

### 2.2.2 不收的词与理由（机器可读，`DESIGN_INTENT_NOT_HELD`）

| 词 | 已归属 | 一句话理由 |
|---|---|---|
| `align-with` | `PlacementIntent.relation === 'align'` | 对齐是**落位指令**、已进 Resolver 并输出坐标；再定义就是第二/第三套对齐真相源 |
| `adjacent-to` | `PlacementIntent.relation === 'adjacent'` | 同上；P8.2 已写明"相邻本身就是面贴合，不再设同义词" |
| `near`（两柜靠近） | **无 —— 今天判不出来** | 事实层柜↔柜只有"接触 / 不接触"，**没有"两柜距离"这个量**；`SPATIAL_TOL.NEAR` 是柜↔**墙**的 |
| `face`（面朝） | `Cabinet.placement.rotation` | "面朝"就是朝向；它想说的"门脸别怼墙"由 `wall-contact` 的**期望取值集合**表达（只认 back/side，不认 front） |
| `prefer-wall` 里的"多近算贴墙" | `SPATIAL_TOL.TOUCH` | 阈值是规则，只有一个出处 |

**一句话规则**：凡是已经能由 `PlacementIntent` 表达的，不属于设计意图；凡是今天算不出来的，不进词表。

## 2.3 数据模型与生命周期

```ts
type DesignIntentStatus    = 'candidate' | 'active' | 'rejected';
type DesignIntentOrigin    = 'user-stated' | 'ai-inferred';          // ← 没有 'system'
type DesignIntentConfirmedBy = 'user-stated' | 'user-confirmed';
type DesignIntentScope =
  | { kind: 'room';    roomId: string }
  | { kind: 'cabinet'; cabinetId: string };                           // ← 写不出 wallId / openingId

interface DesignIntent {
  id; status; goal; scope; openingKind?; statement?;
  origin; confirmedBy?; evidence[]; createdAt; updatedAt;
}
```

```
用户明说 ──────────────────────────► active（进 model）
AI 推断 ──► candidate ──► 用户确认 ──► active（进 model）
                    └────► rejected（不进 model；**不能靠再确认复活**）
系统 ──► 什么也不产生（`'system'` 在类型层就不存在）
```

三条关键决定：

1. **`'system'` 从类型里去掉，而不是靠校验拦住**。写不出来比"写得出但被拦"彻底一档。
   验收对 `origin:'system'` 做运行时负样本，并**只扫代码行**（不扫注释）确认源码里没有它 ——
   文件头注释正在讨论这件事，扫注释会把"说明它不存在"当成"它存在"的证据。
2. **模型只装 active**（P8.5-B 的教训直接搬过来）。candidate 只活在"意图提案"对象里。
   未确认与已确认是**真实语义差异**，一旦落盘就分不清"用户要的"与"AI 猜的"，
   而 `preview === commit`、`dryRun === commit` 两条逐字节不变量都建立在"模型里只有已确认的事"之上。
3. **`makeCandidateIntent` 没有参数能造出 active**，`proposalToCandidates` 同样产不出 active ——
   "AI 推断只能产生 candidate"不是一句承诺，是这两个函数的签名。

## 2.4 四道闸门（`validate.ts`，唯一实现）

| # | 闸门 | 拦什么 | 报错口径 |
|---|---|---|---|
| ① | **载荷禁数字**（第一位） | `goal` / `scope` / `openingKind` 里递归不许出现**任何数字或布尔**（数组也拒） | "设计意图的载荷里**不许出现数字**（坐标 / 尺寸 / 阈值一律属于几何层）" |
| ② | **词的闭集** | `goal` 不在词表里 | "不在设计意图词表里 —— 未知意图不被接受，不会"忽略掉继续"" |
| ③ | **载荷无实体** | `scope` 只认 `room` / `cabinet`；键闭集里没有 `wallId` / `openingId` | "scope 只回答"关于谁"；墙、洞口、坐标都不是意图能指的对象" |
| ④ | **生命周期** | candidate 自带 `confirmedBy` / active 无人认领 / AI 推断的 active 自己宣布生效 | 见下 |

### 2.4.1 为什么数字筛子放在**第一位**（一处刻意的顺序）

坐标走私是本层最想防的事，而**坐标一定是数字**。放在最前有两个好处：

- 报错最准：`scope.rotation = 90` 会直说"载荷里不许出现数字"，比"不认识的字段 rotation"点题；
- 这道筛子**真的会触发**，于是它不是一个永远轮不到执行的死分支。
  （本项目对"恒真断言 / 永不触发检查"的态度：没被证伪过的检查不算检查 —— 验收的变异测试专门关掉它一次，见 §2.8。）

**载荷禁的是"一切数字"，不是"名字叫 x 的字段"** —— 这比"禁止 x/y"强一档：
坐标在物理上无法表达，而不是"写了 x/y 会被拒、写了 px/py 就漏过去"。

### 2.4.2 坐标走私的两条路都堵死（验收第 47 条）

| 走私写法 | 撞上哪道门 |
|---|---|
| `scope: { …, x: 100 }` | ① 数字筛子 |
| `scope: { …, rotation: 90 }` | ① 数字筛子 |
| `{ …, placement: {x, y, rotation} }` | ③ 键闭集（报出字段名 `placement`） |
| `{ …, x: 1 }` | ③ 键闭集 |
| `scope: { kind: 'wall', wallId }` | ③ scope 实体闭集 |
| `openingKind: 2` | ① 数字筛子 |

**闸门是白名单不是黑名单**：多一个键就拒，不做"忽略不认识的字段继续"。
静默忽略是最危险的行为 —— 提的人以为生效了，系统以为没提。

### 2.4.3 提案通道（AI 的入口，`designIntentProposalError`）

- 顶层键闭集 `['intents', 'reply']`；空数组拒；一次最多 `DESIGN_INTENT_PROPOSAL_MAX = 8` 条；
  一条坏 → **整份拒**（原子）且报出"第 N 条"。
- **不挤进 `ACTIONS`**：动作清单管"AI 能改模型什么"，而意图提案**改不了模型**
  （只能产 candidate，要用户确认才生效）→ 不该让动作数从 21 变成 23。
  验收把 21 这条数当成漂移哨兵钉住。
- 每条都过**草案闸门**（`designIntentDraftError`），不另写一套 ——
  同一条规矩出现在两处时，只在一处拦 = 另一条路是敞的（`unitIntentsSemanticError` 的教训）。
- 草案**不许自带元信息**（`id / status / origin / confirmedBy / evidence / createdAt / updatedAt`），
  报错是**点名**的："提出者不能自己宣布生效（AI 推断只能产生 candidate，必须经用户确认）"。

## 2.5 载体与文件边界

**载体 = `Project.designIntents?`**（顶层扁平数组，与 `assemblies` 同构）。
Intent 是**这份设计的目标**（换项目就不成立）→ 属于这份设计的真相源；
Knowledge 是**跨项目仍成立的习惯**（`store.ts` 已写明"知识不进 project.json"）。

**悬空引用丢弃而不是拒绝整个文件**（与 `Cabinet.roomId` 悬空**故意不同**）：

| | 性质 | 悬空时怎么办 |
|---|---|---|
| `Cabinet.roomId` | **事实** | 悬空会让整组操作少动一个柜（静默做错事）→ **必须拒绝整个文件** |
| `designIntents[].scope` | **注解** | 顶多"少知道一条诉求"；拒绝文件会让用户连柜体尺寸都改不了 → **丢弃 + 可见警告** |

丢弃规则三条：形状/词表非法、**不是 active / 无人认领 / AI 推断却自己生效**、悬空引用。
**抹掉而不是留着**：留着一个系统认不出的值，存盘时会把垃圾写回文件（验收第 144 条钉住这一点）。

### 2.5.1 为什么不升 `schemaVersion`

版本号跟"这份文件用了哪些结构"走，判据是**旧读者会不会静默做错事**：

- `rows` / `assemblies` 会让旧读者按错误形状算板件（不报错地出错误尺寸）→ **必须升**；
- 设计意图**今天没有任何执行体**：旧读者忽略它时，设计结果与不忽略时**逐位相同**
  → 没有静默做错事的风险 → **不升版本，仍给 0.2**。

验收第 137 条直接断言含意图的文件 `schemaVersion === '0.2'`；
第 138～140 条断言**无意图的旧文件逐字节不变**且键根本不出现（不写空数组）。

## 2.6 AI 侧：为什么与 `spatialContext` 分成两块

`spatialContext`（P9.1）装的是**世界的样子**（派生事实）；`designIntent`（P9.2）装的是**人想要的样子**（用户确认的目标）。
混在一个块里，下一个人读快照时分不清哪句是事实、哪句是诉求 —— 而**这两者犯错的方式完全不同**：
事实错 = 系统算错；诉求错 = 系统会错，但它本来就是用户的权利。

```
AiDesignIntentContext { readOnly: true, count, intents: AiDesignIntent[] }
AiDesignIntent { id, goal, goalZh, scope, roomId?/cabinetId?, openingKind?, statement?, origin, fact, expect }
```

- **零坐标**：goal 是词、scope 是 id、openingKind 是枚举；`fact` 是**维度的名字**不是值。
- **只读**：只有 `activeDesignIntents(project)` 进块；candidate 与 rejected 都不出现。
- **排序稳定**：先按词表顺序、再按 id → 同一份模型永远给出同一段文本（提示词前缀逐字节一致）。
  验收用一个"反序存入"的夹具证明它不跟着模型里的存入顺序跑。
- **空项目也给形状齐备的空块**（`{readOnly:true,count:0,intents:[]}`），不是 `undefined`。

### 2.6.1 提示词里只给"能读"，并**明说**"本阶段不能写"

意图提案的语法与闸门已经就位，但**接线在 P9.3**（候选布局才会去消费它们）。
如果现在告诉模型"你可以提"，它会认真写一段 `intents` —— 而规划通道只读 `reply` / `actions`，
那段话就是**静默丢弃**：模型以为生效了，人以为生效了，实际没生效。
契约文件的铁律写着"静默忽略是最危险的行为"，所以宁可先说清"不能提"：

> 快照里的 `designIntent` 是**已经确认的设计目标**……它同样是**只读**的：
> 你可以据此判断该往哪个方向设计，但**这一轮你不能新增或修改设计意图**（目前没有这条通道，写了也不会生效）。

验收第 63～64 条同时断言这两句都在提示词里（"不能新增或修改" **且** "写了也不会生效"）。

## 2.9 本次实现踩到的坑（值得写下来）

1. **夹具撞 id**：两个夹具都从空集合取号 → 都拿到 `di_001` → `rejectIntent` 一次带走两条。

2. **同一条规矩的两处入口**：草案闸门有"不许自带 id/status/origin"，若记录闸门 = 草案判定 + 元信息，

3. **TS 收窄**：`scope.roomId` 在 `find((x) => …)` 回调里不会被收窄 → 先把可辨识字段取成局部常量再进回调。

   假绿。修法 = 只扫 import 说明符并断言**来源数量**。
5. **生成器时间戳**：逐字节比较前必须固定；`toNeutralExport` 的 `generatedAt` 还是嵌套的。
