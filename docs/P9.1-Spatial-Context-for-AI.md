# P9.1 Spatial Context for AI —— 审查 + 实施记录

- 基线：**P9.0 完成后的 master HEAD**（`0cba2ef` 功能 + `b4c62f4` 记忆 + P9.0 审查报告）
- 本阶段性质：**输入侧补齐**。让 AI 快照从"只知道房间名字"升级为"知道能用于设计推理的空间事实"。
- 遵守 P9.0 审查结论：**纯投影**，不新增判定、不新增模型字段、不改 `schemaVersion`、
  不改 Placement Resolver、不动 Spatial Truth、不把派生几何写进 Model、不接 LLM Planner、
  不引入 Candidate Layout / Constraint Graph、不进 P9.2+。

# 一、审查结果（实现前）

## 1.1 AI 当前到底能看到什么（逐字段核对 `src/ai/snapshot.ts`）

```
AiSnapshot
├─ contractVersion / projectName
├─ rooms[]      { index, id, name, wallCount }          ← 只有 4 个字段
├─ materials[]  { id, name, thickness, kind, canBeBodyBoard, canBeBack }
├─ limits       规则集上限（只读）
├─ cabinets[]   { index, id, name, roomId, placement{x,y,rotation},
│                 params{…}, layout{type,widthMode,units,rows,backUnits} }
└─ assemblies[] （仅在有组合时出现）
```

**结论：AI 目前对空间一无所知。** 它知道"某个房间叫什么、有几面墙"，
但拿不到：墙的 id / 长度 / 走向 / 名字、墙的厚度、洞口（门窗）及其尺寸、
房间形状、任何"柜↔墙 / 柜↔洞口 / 柜↔门扇"的关系。
`snapshot.ts` 的 `rooms` 是 `{index,id,name,wallCount}` 四字段，逐字确认过。

这正是 P9.0 §4.4「缺口 1（阻塞级）」与风险 **R1** 描述的状态：
**AI 在完全看不见房间的情况下被要求做室内设计** —— 它只能靠幻觉或靠用户口述。
这也是为什么 P9 的顺序是"先补输入可见性（P9.1）"而不是"先接 LLM（P9.5）"。

## 1.2 需求逐项 vs 现状 vs 唯一确定性来源

| 需求项 | 现状 | 唯一确定性来源（可投影的那一处） |
|---|---|---|
| Room.id / name | ✅ 已有 | `Room` |
| Room boundary 基础语义 | ❌ 缺 | `roomLoop(walls).status`（P8.7 `spatial/model.ts`，唯一口径） |
| Room 尺寸 / 面积 | ❌ 缺 | **无 area 实现**；只有 `bboxOf(loop.poly)`（`geometry/transform.ts`）→ 只能给"包围范围"，且必须如实叫它 extent |
| Wall.id / 所属 room | ❌ 缺 | `Room.walls`（结构本身回答归属） |
| Wall 方向 / 长度 | ❌ 缺 | 端点差：`hypot` 取长；`|dx|`/`|dy|` 比较判走向（**无三角函数**） |
| Wall 人类语义（北墙/东墙） | ⚠️ 半有 | `Wall.name` 是 **authored**（`docFactory.rectRoom` 生成的正是 南墙/东墙/北墙/西墙）→ **投影 name 即可，不新造方位推断** |
| Wall 是否存在洞口 | ❌ 缺 | `Wall.openings` |
| Opening id / kind / width / offset | ❌ 缺 | `Opening` |
| Opening swing（已确认的） | ❌ 缺 | P8.9 `DoorSwingFact`（hinge / direction / status / unknownReason） |
| Cabinet 空间关系事实 | ❌ 缺 | P8.7 `SpatialFacts.cabinets[]`（room / walls / openings） |
| Cabinet 门扇净空 | ❌ 缺 | P8.9 `DoorClearanceFact` |
| Cabinet 设计警告 | ❌ 缺 | 事实枚举本身（**不投影规则码与文案**，见 1.4） |

## 1.3 哪些信息可以安全进入 snapshot

判定准绳（沿用 `snapshot.ts` 文件头的白名单纪律 + `verify/ai-acceptance.ts` 的 I1/I2/I3）：

- ✅ **闭集枚举的关系事实**：`inside/outside/crossing/unknown`、`touching/near/crossing/none`、
  `clear/overlap/unknown`、`ok/unknown` + 原因码。这些是"结论"，不含几何。
- ✅ **整数标量**：长度、宽度、offset、缝隙、包围范围（X 向 × Y 向）。
- ✅ **authored 语义的投影**：房间名、墙名、洞口 kind/width/offset、门扇 hinge/direction / 门名。
  它们本来就在模型里（AI 早就看得到柜体 `placement`），投影一份不会新增可写面。
- ✅ **闭集 concern token**：把事实枚举翻成"设计关切"词（`crossing-wall` / `blocks-opening` / …），
  **不搬规则码、不搬中文文案**。

## 1.4 哪些必须保持 derived-only（绝不进快照）

| 数据 | 为什么 |
|---|---|
| `DoorSwingEnvelope`（`hinge` / `closedTip` / `openTip` / `poly`） | 含**坐标与多边形**。进了快照就是"给 AI 几何"，直接违反 I3 与"AI 不输出几何" |
| `wall.start` / `wall.end` / `openingRect` / `openingZoneRect` / `wallPolygon` | 几何真相；快照只给 `length` / `axis` / `name` |
| `SpatialFacts` 里的多边形与 bbox 形状 | 同上；包围范围必须拆成具名标量 `{width,depth}`，不能是数组 |
| `designValidation` 的 findings **文案与规则码** | 一给，AI 就学到一套规则词汇并可能把它当"可改的对象"；文案也可能被抄进 `reply` |
| `deriveSpatial().issues` | 「问题列表」是明确不给 AI 的那一类（`buildSystemPrompt` 第 4 条已写死） |

## 1.5 同一条纪律的另外两条落点

- **R7（快照/草案漂移）**：`draftSnapshot()` 已经用**草案**生成快照；新块必须走同一个
  `buildSnapshot()` 入口（因此天然继承），不能另开一条"从真项目读空间"的路。
- **P9.0 §11.3 对 P9.1 的建议**：「纯投影：不新增判定、不新增模型字段；派生事实必须与
  authored 明确分开（**建议独立 `spatialContext` 块，不混进 authored 快照**）」。
  → 本阶段按此执行：新增**独立顶层块 `spatialContext`**。

## 1.6 本阶段结论（做什么 / 不做什么）

**做**：新增 `src/ai/spatialContext.ts`，导出 `buildSpatialContext(project)`，作为
`AiSnapshot.spatialContext` 独立块；内容全部从 `core/spatial` 的既有派生结果投影。

**不做**：新判定、新模型字段、新契约动作、新 Resolver、新几何、坐标、多边形、
规则码文案；不接 LLM Planner；不引入 Candidate Layout / Constraint Graph。

`AiSpatialContext` 的形状：

```
rooms:        id / name / boundary{closed,status,wallCount,cornerCount} / extent?{width,depth}
walls:        id / roomId / name / length / axis / openingCount
```

## 2.2 三条纪律的落地证据

- **纯投影**：没有一处自己的几何/容差判定；`facts/doors/clearances` 全部原样取自
  `deriveSpatial(project)`；`SPATIAL_TOL` 一个数都没在本文件里重写。
- **派生与 authored 分开**：独立顶层块 + `readOnly: true`。authored 只做照抄
  （房间名、墙名、洞口尺寸、门扇意图）。
- **零坐标**：验收 §3 全快照与只扫本块**都 0 命中**（含"塞进包围盒必须被检出"的负样本）；
  门扇只给"判得出/判不出"，`envelope` 影子都没有。

## 2.3 实测发现的两处实现修正

1. **零长墙不能落进 `horizontal`**：初版 `axisOf` 按 `dy===0 → horizontal`，
   会给零长墙报一个不存在的方向 → 加 `'degenerate'`（对应 `SPATIAL-WALL-ZERO`）。
2. **`floating` 门槛收紧到 `roomRelation === 'inside'`**：`roomLoop` 在"房间里全是零长墙"时
   返回 `status='ok'` 而 `poly` 为空（既有口径，`facts.rooms[].closed` 因此为 `true`），
   照搬 `closed` 会得出"房间判不出内外"与"这柜悬空"同时成立。只在"确实知道它在屋里"
   时才报悬空；该差异**被验收 §5 第 58/59 条显式钉住**。

## 2.4 验证结果

- `verify:spatial-context-ai` **72 / 72**；四个变异测试各自确认会变红后还原：
  unknown→默认向内开（红 51/55）、走向一律 horizontal（红 7/59）、塞坐标（红 32/33）、
  放宽 floating（红 58/59）。
- `GOMEMLIMIT=1500MiB npx tsc --noEmit` → 0；`verify:all` → **EXIT=0，0 失败**（含 `verify:ui`）。
- 旧测试**零删除、零放宽**；`schemaVersion` 不变；AI 动作清单不变；Knowledge / Resolver /
  Validation / Manufacturing 全部未触碰。

## 2.5 停在 P9.1

不进入 P9.2（空间设计意图词汇）。本阶段明确不做：Candidate Layout、Constraint Graph、
Design Score、LLM Planner、自动布局、自动移柜、人流模拟、Z 轴、3D 动态开门、BIM/IFC。
