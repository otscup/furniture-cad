## 一、现状事实（回答问题 1）

### 1.1 两条生成路径

| 路径 | 位置 | 提议来源 | 组合方式 | 生成期硬过滤 |
|---|---|---|---|---|
| 单柜（P9.3） | `candidatesForTarget` | `candidateSpots` 全量（每墙 11 档） | 3 个策略各取第一个合格落点（保持朝向 / 换朝向 / 满足目标） | `detectCollisions` |
| 多柜协调（P9.7） | `coordinatedCandidates` | `anchorSpots`（每墙前 2 个、总量封顶 8） | 行链（锚点 × 自然/倒序） + L 型（有序对 × 2 种面组合） | `detectCollisions`（**整体克隆**） |

两条路径都遵守同一条链：提议 → `resolvePlacements` → 整体克隆 → 整体 `detectCollisions` → `deriveSpatialFacts` / `deriveContacts`（满足性）→ 组装 `CandidateLayout`。
**坐标从未在 generator 里算出来过。**

### 1.2 协调搜索空间的精确大小（最关键的一组数字）

【推算，依据 `snapPlace.ts` 的 `SLIDE` 常量与 `generate.ts` 的 `SPOTS_PER_WALL` / `MAX_ANCHOR_SPOTS`】

```
SLIDE = [0.5, 0.4, 0.6, 0.3, 0.7, 0.2, 0.8, 0.12, 0.88, 0.05, 0.95]   // 共 11 档
anchorSpots：每面墙只取前 SPOTS_PER_WALL = 2 个 → 恒为 SLIDE[0]=0.5 与 SLIDE[1]=0.4
            并且按成员当前共同朝向 classRot 过滤墙（orientation 保持）
矩形房间：4 面墙各自成一个朝向类（0 / 90 / 180 / 270）→ 同一 classRot 通常只剩 1 面墙
⇒ 行链锚点数 = 2；行链组合数 = 2 锚点 × 2 顺序 = 4
```

该推算与 **[实测]** 完全吻合：P9.7 真实回归里 `generation = {requested:3, generated:4, returned:3, truncated:1}`，其中 `generated = 4` 正是 2×2。

**换句话说：今天三柜整墙的协调候选空间实际只有 4 个组合，而且这 4 个组合的锚点位置彼此相差约 0.1 倍墙长（同一面墙中点附近的两个采样）。**

### 1.3 覆盖矩阵

| 维度 | 现状 | 是否覆盖 |
|---|---|---|
| 沿墙滑动采样 | 固定 11 档 SLIDE，协调路径只取前 2 档（0.5 / 0.4） | ❌ 0.6/0.3/…/0.05/0.95 全序列从未被协调路径使用；**墙两端角部从未试过** |
| 洞口感知的采样 | 无 | ❌ `candidateSpots` 完全不知道 `wall.openings` |
| 锚点按"组的总跨度"计算 | 无（`anchorSpots` 传的是首成员宽度） | ❌ 倒序时链的 head 换成了别的成员，采样集却没跟着换（推算：坐标仍合法，但采样集有偏） |
| 成员顺序 | 自然 / 倒序 | ⚠️ 三只柜以上的其余排列从未尝试；成员宽度不同 ⇒ 顺序会改变整体 footprint |
| 链的延伸方向 | 只 `attach left↔right`（向右续接） | ⚠️ 向左延伸未被直接表达（靠"倒序 + 锚点"部分近似；采样稀疏时不等价） |
| 面组合 | 行链只用 left↔right；front/back 只出现在 L 型 | ⚠️ 未成体系 |
| 贴面内对齐 | 只 `alignment: 'start'`（背面齐） | ❌ `center` / `end` 从未使用（混合深度场景 C 的形状差异没被表达） |
| **缝隙** | 无 | ❌ `PlacementIntent.attach.offset` **早已在 Resolver 契约里**，generator 从未使用 —— 能力就绪，没接线 |
| 多墙 / 整组换墙 | 无 | ❌ 见 §1.4 |
| 整组换朝向 | 无 | ❌ 见 §1.4（**被架构挡住，不是漏写**） |
| 组子集（3 只里 2 只成链、第 3 只另处） | 无 | ❌ 组 = 房间里全部目标柜 |
| 多意图联合协调 | 无 | ❌ 每条 intent 各枚举一遍 |
| 随机 / 遗传 / 退火 / LLM 坐标 | 无 | ✅ 明确禁止，保持不变 |

### 1.4 两个"不是漏写、而是结构性不可达"的点（重要）

**(a) 整组换朝向在现状架构下做不到。**
`resolveAttach`（`placement.ts:474-524`）返回 `rotation: target.rotation` —— **target 保持自己的朝向**；且 `FACE-NOT-OPPOSING` 要求两面法向点积 = -1，等价于"两柜相对旋转是 90° 整数倍且该两面恰成对面"。
⇒ 想让整条链贴到另一朝向的墙上，就必须让**每只成员自己的 rotation 先变成那个值**；而 rotation 只能由 `absolute` 意图给出，给每个成员各自一个 `absolute` 就意味着 generator 得自己算 x/y（红线）。
⇒ **orientation permutation 需要 Resolver 侧出现"继承参考对象朝向"的新能力，属于 Resolver 议题，不属于 P9.8 的搜索覆盖议题。**

**(b) 多墙组合同理受限。** 只有当成员的**既有 authored rotation** 恰好互成 ±90° 时，L 型模板才有东西可做 —— 这正是真实厨房里 L 型产出 0 条的原因（三只柜同朝向，所有有序对的 `rel` 都不在 {90,270}，`variants` 是空数组）。此外 L 型里的 A 被钉在自己的**当前位置**（no-op absolute），即 L 型从不换地方。

### 1.5 "谁淘汰了真实厨房候选" —— 这决定了修理处在哪一层

| 事实 | 依据 |
|---|---|
| 协调路径唯一硬过滤 = `detectCollisions` | `generate.ts:347` |
| `detectCollisions` **不认洞口**（柜盖洞口属 spatial 层 `SPATIAL-CABINET-OPENING`；门扇属 designValidation `DESIGN-CABINET-DOOR-SWING`） | `spatial/validate.ts:129`、`designValidation/*` |
| 因此"压门洞的整体候选"**照样被生成出来**，直到评分层 Gate 才判 `infeasible` | [实测] P9.7 真实回归：3 份多柜候选全部 infeasible，码就是上述两者 |
| 移除门洞后，同一份真实 `plannerRequest` 得到 `valid`（total 0，接触 c1~c2:butt / c2~c3:butt） | [实测] 同一份报告 §5.3 无门洞对照 |

**结论：不是规则错，也不是漏掉了某个"应当过滤"的地方，而是搜索压根没生成可行的那种摆法。修理处在提议空间，不在 Spatial / Score。**

## 二、边界：generator 与 Spatial / Resolver / Score 怎么分（问题 2、问题 5）

一句话边界：**generator 只提议（propose），不裁决（judge）。**

| 层 | 唯一职责 | 明确的**不做** |
|---|---|---|
| **Candidate Generator** | 决定"**试哪些组合**"；把组合表达成 `PlacementIntent[]`；进行确定性的**配额**统计；如实记账 | 不算 x/y；不复算"是否挡门 / 是否贴墙 / 是否好"；不读 Knowledge；不排序打分；不挑 winner |
| **Resolver（`placement.ts`）** | **唯一坐标出口**；依赖拓扑排序 + 环检测 | 不知道洞口、不知道设计意图、不做任何价值判断 |
| **Spatial（`spatial/*`）** | 事实：`touching/near/crossing`、`clear/overlap/unknown`（柜↔洞口）、空间派生 | 不提议位置、不自动移柜、不做"候选是否可行"的裁决 |
| **DesignValidation** | 把"几何合法 ≠ 设计合法"说清楚（门扇、开门净空……）→ `Issue` | 不提议、不改 rotation |
| **DesignScore** | Gate 前置 → valid / infeasible → 软评分；只读既有事实与 applicable 偏好 | 不参与搜什么、不反馈给 generator |
| **Compare UI / Planner** | 消费（`placements.map`）、展示、透传 | 不重算这条链上的任何东西 |

守住以下三条推论，扩搜就不会越界：

1. generator 新加的任何"避开门洞"**只能是提议偏好**（把锚点放到空白区段），**不能变成"把 overlap 组合扔掉"的过滤器** —— 否则某些场景会被静默饿死，连"整份不可行"这个诚实信号都会一起消失（见 §五 Q6、§六 Q8）。
2. generator 里出现 `overlap / clear` 的**判定代码**就是第二份真相源，禁止。需要结论时一律调既有函数（事实照样由 `deriveSpatialFacts` 给出）。
3. generator 一旦按"哪条候选更好"来截断或排序，等于把 Score 复制了一份。**我们停在"覆盖均匀"，不碰"选优"。**

## 三、不引入 ConstraintGraph、不让 AI 出坐标、不改 Semantic Model 的扩搜思路（问题 3）

三个扩建口，**全部落在提议侧**：

1. **沿墙提议阶梯升级（proposal ladder）**
   把"取 SLIDE 前 2 档"换成"由 authored 数据派生的锚点集合"：每面墙按 `wall.openings` 的 **authored span**（`offset` / `width`，纯模型字段，无需任何空间解释）切出若干**空白连续区段**；每个区段提议它的两端 + 中点；并且按**整组的总跨度**（Σ 成员宽 + 已确定的缝）而不是首成员宽度来判断能否放下。
   产出的仍是一串提案，每个照样经 `resolvePlacements` 与整体验证 —— 这与既有 `candidateSpots` 的性质完全一致（它本来就是"只负责生成候选，不负责判断放不放得下"）。

2. **组合维度的廉价扩展（全部使用现有 Resolver 能力）**
   · 顺序：自然 / 倒序 → 加循环移位（cyclic shift，n 个而不是 n! 个）
   · 对齐：`start` → 加 `center` / `end`（已存在的 `AttachAlignment`）
   · 缝隙：`attach.offset`（**已存在**），取值由 authored opening span 派生，不编 mm 常数
   · 面组合：链的续接方向 / L 型的 `back|front ↔ left|right`

3. **探索预算（search budget）**
   用"评估了多少个组合"来度量并如实记账（见 §五 Q7）。

**为什么不引入 ConstraintGraph**：这个项目已经有"提议 → 唯一 Resolver → 事实层 → 规则层 → 评分层"的单向 DAG。ConstraintGraph 会把这五层压进一个求解器，等于同时违反"唯一坐标出口"和"一种形状只许一处判断"。当前的缺口是**提议太稀疏**，不是**缺少求解器**。

## 四、八项候选能力逐项评估（问题 4）

> 必要性分级：**必做 / 建议 / 可选 / 不做**；依赖与风险均为具体项。

| # | 能力 | 必要性 | 依赖 | 风险 |
|---|---|---|---|---|
| 1 | **wall segment / usable wall segment（可用区段）** | **必做**（P9.8 最小内核） | 只读 `wall.openings` 的 authored `offset/width`；复用既有 `projectParamOnSegment`（`snapPlace` 已在用） | 中：区段截取是形状判断 ⇒ 必须确保它**只用于提议**、不起"禁区"的结论作用；一旦出现第二个消费者，就应上收到 spatial 层成为一等事实 |
| 2 | **opening avoidance（避开洞口）** | **必做**，但**只做提议式** | 依赖 #1 | 高（若做成过滤器）：① 会静默饿死候选集合；② 等于在 generator 里重判了一次 `SPATIAL-CABINET-OPENING`（第二份真相源，且那时候 Score 还没机会说话） |
| 3 | **多墙候选** | 可选（最小范围之外） | 依赖 #5（整组换朝向），否则只有成员本就多朝向时才有可能 | 高：牵扯"组的一部分在另一面墙"的表达，而 attach 要求 90° 倍数关系；收益主要在 L 型与不规则房间 |

| 5 | **orientation permutation（朝向排列）** | **不做**（本阶段结构性阻塞） | 依赖 Resolver 新增"继承参考朝向"能力 | 高：直接顶到"唯一坐标出口"红线。要么改 Resolver（动 P8 家族），要么 generator 算坐标（禁止）。**建议单独立项，不作为 P9.8 内容** |
| 6 | **attach / adjacent 组合 + 对齐 + offset** | **建议**（低成本高收益） | 现有 `PlacementIntent` 已全部支持（含 `offset`） | 低（offset 取值必须 derived，例如来自 authored opening span；**禁止**编一个 mm 常数） |

## 五、六个对应问题（Q5 见 §二、Q6 / Q7 / Q8 / Q9 / Q10 如下）

### Q6：`maxCandidates` / `generationLimited` / `truncated` / `unresolved` 语义在扩搜后是否仍成立

现状语义（`candidateLayout/model.ts`）：

- `requested` = 夹紧后的 `maxCandidates`（核侧 `clampMax` 上界 = `MAX_CANDIDATES_PER_TARGET = 3`；注意 AI 契约只要求 ≥1 整数，**3 是核侧自己的政策**）
- `generated` = 协调路径**硬过滤 + 去重后**的有效候选数
- `returned` / `truncated` = `returned = generated.slice(0, maxCandidates)`，`truncated = generated - returned`
- `generationLimited = truncated > 0`

扩搜后的**四个语义风险**（必须在 P9.8 之前议决）：

1. **`generated` 的定义会失真**：今天它是"去重后的输出条数"。扩搜之后，读者最需要的是"试过多少、因什么被拒"，而这些今天只存在于 `unresolved` 的一句中文里（`rejectedTotal` 没有进 stats）。
   → 建议给 `CandidateGenerationStats` **追加可选字段**（追加不影响 `generated === returned + truncated` 这条既有不变式）：`explored`（实际评估组合数）、`rejected`（按 `resolve` / `collision` 分类）、`budgetExhausted`。既有字段含义一字不改，既有断言（验收第 34 项）继续为绿。
2. **`returned` 的选取规则会变成主要矛盾**：今天 `returned = slice(0, N)` = **枚举顺序的前 N 条**。真实厨房已暴露后果 —— 三条同处一片的候选全 INF，而空缺的可行摆法压根没被枚举到；即便它被枚举到但排在 N 之后，也会变成"静默被截断的可行解"。
   → `returned` 的选取必须**确定性 + 覆盖式**（见 Q8），而不是"前 N 条"。
3. **`requested` 与"更多覆盖"直接冲突**：返回上限恒为 3，搜索再宽也只能给 3 条。**是否上调核侧夹取上界是政策决策，必须显式列出，并同步更新受影响的既有验收期望**（不得以"放宽测试"的方式处理）。
4. **`unresolved` 的诚实账要保持**：扩搜不能把"整个候选空间里不存在可行解"变成空候选集合；搜不出结论必须是明明白白的 unresolved（"本阶段不支持 X，所以整体空间里没有可行解"），不是沉默。

### Q7：候选爆炸 —— 确定性的边界 / 去重 / 停止条件（不使用 magic number）

**原则：任何上界必须溯源到两类东西之一 —— (A) authored 数据规模（墙数、洞口数、区段数、成员数），或 (B) 已公开的既有政策常数（`maxCandidates`、`PLANNER_LIMITS.maxCabinets`）。**

- **区段数上界 = 由 authored 洞口切出的区段数本身**（每墙 ≤ 洞口数 + 1，全房 ≤ Σ(洞口数+1)）。这是数据规模，不是常数。
- **每个区段的提议点 = 该区段的两端 + 中点**（3 个），且只有"容得下当前组合总跨度"的区段才提议。同样由数据与组合自身的 Σ 宽导出。
- **顺序变体 = 2n（循环移位 + 倒序）**，不是 n!；n≤3 时可全排列（6），由组规模决定。
- **去重键沿用 `candidateSignature`**（targetId + resolved 输出，排序后拼接）：现有键已经足够，扩搜后**不需要新的去重结构** —— 所有差异都会体现在 resolved 结果上；不同对齐/续接方式若落到相同坐标，就是真的同一份布局。
- **停止条件（三条，全部可观测）**：
  1. 提议笛卡尔积枚举完终止（空间有限，且由数据导出）；
  2. 返回预算（= `maxCandidates`）被"覆盖式配额"填满终止 —— 按 family 轮转，而非前 N 条；
  3. 探索预算耗尽终止 → **必须落 `budgetExhausted = true` 并写入 `unresolved`**，绝不静默。
- **成本模型**：每个组合 = 1 次 `resolvePlacements` + 1 次整体克隆 + 1 次 `detectCollisions` +（存活后）1 次 facts/contacts。今天已经这么计费，扩大后线性增长 —— 所以预算的第一公民是"评估过的组合数"。

### Q8：真实厨房「三柜 + 南墙门洞 + wall-contact」的成因与出路（问题 8）

**已知实测**（P9.7 报告 §5.3）：

- 房间 5200×4200，三只 900 宽同朝向柜，`di_001` 房间级 `wall-contact`
- 多柜候选 cl_010：`c1 (2150,60,0)` + `c2 (3050,60,0)` + `c3 (3950,60,0)` —— 一条整墙链
- 三条多柜候选全部 `infeasible`：`SPATIAL-CABINET-OPENING` ×2 + `DESIGN-CABINET-DOOR-SWING` ×2
- 无门洞对照：cl_010 `valid`

**[推算] 成因还原：**

- 链的连续跨度 = 3×900 = 2700；锚点只有两档（t=0.5 → head x=2150；t=0.4 → head x=1550）
- 两档差异仅约 0.1 倍墙长 ≈ 500mm，也就是说**三条返回候选本质上是"同一处的几种排序"**
- 洞口只需要覆盖到 x≈3300~4200 一带（与"×2 只柜报警"自洽：c2 / c3 两只压上），那么 t=0.5 与 t=0.4 两个锚点都会压上；而**左半空白区段长约 3300 ≥ 2700 —— 空间里客观存在"整条链靠左堆放"的可行解**
- 失手点非常确切：**系统从未采样过"贴墙端 / 贴洞口边缘"的摆法**（SLIDE 阶梯里有 0.05 / 0.95，但协调路径只取了前 2 档）

**出路（仅最小内核就能覆盖该场景）：**

1. 用 authored opening span 把该墙切成空白区段；
2. 每个空白区段的**两端 + 中点**各给一个锚点（两端 = 贴角 / 贴洞口边，正是可行解所在的位置）；
3. 按"组总跨度 2700"过滤放不下该组的区段；
4. 命中之后仍然整体克隆验证，并交给既有 Spatial / Validation / Score 落判。

**若碰上"任何区段都容不下整组"（组宽 > 最长空白区段）**：最小内核会被证伪 —— 这时需要"链条中留缝（`attach.offset` 跨过洞口）"或"把组拆到两面墙 / 只协调子集"。**这两项必须在 `unresolved` 里明说自己不支持**，不许给一堆 infeasible 假装已经搜过了。

### Q9：是否需要 P9.8 新增数据结构

**结论：最小 P9.8 不需要新的顶层数据结构。**

| 想表达的诉求 | 复用的既有结构 |
|---|---|
| 多成员一次整体表达 | `CandidateLayout.placements[]`（P9.7 已允许多项，坐标来自 `resolved`） |
| 留缝 / 间隙 | `PlacementIntent.attach.offset`（P8.2 已存在，generator 未用） |
| 面内对齐变体 | `AttachAlignment = start \| center \| end`（已存在） |
| 洞口的位置信息 | `wall.openings[].offset / width`（authored 模型字段，纯读取） |
| 侵占与否的事实结论 | `SpatialFacts.cabinets[].openings[].relation`（已派生：`clear` / `overlap` / `unknown`） |
| 探索预算台账 | `CandidateGenerationStats` 追加**可选**计数字段（运行态，不落盘，不触 `schemaVersion`） |
| 候选来源的人话 | `CandidateLayout.explanations[]`（已是自由字符串列表） |

**唯一可能被议论的新抽象**：如果将来出现第二个消费者也需要"墙面空白区段"（例如 Knowledge 或未来的 adopt），那就该在 `spatial/` 把它提升为一等派生事实（如 `SpatialFacts.walls[].freeSegments`）。**现在只有一个消费者（generator 的提议器），此时上收 spatial 层属于过早抽象** —— 但代码里必须把"这是提议，不是裁决"写死，并留出平移路径。

## 六、最小可行的 P9.8 scope（建议只做这一片）

### S1（建议采纳 = P9.8 的全部内容）

1. **空白区段感知的锚点阶梯**：替换 `anchorSpots` 的"每墙前 2 档 SLIDE" —— 按每面墙的 authored openings 切出空白连续区段，输出那些"放得下当前组合总跨度"的区段的两端与中点。
2. **按组（而非按首成员）计算跨度**：修掉"倒序时 head 换了成员、采样集却按首成员宽度算"的错配；链的锚点按 Σ 宽（+ 已确定的缝）来算。
3. **覆盖式返回配额**：把 `returned = slice(0, N)` 换成**按 family（区段 / 顺序族）轮转的确定性配额**；明确这不是"选优"（不选 winner、不看 Score）。
4. **探索预算 + 台账**：`explored` / `rejected{resolve, collision}` / `budgetExhausted`；预算耗尽必须进 `unresolved`，并且仍然必须让人读到"整体维度不可行"的证据。
5. **保留既有硬过滤集合**：仍只用整体碰撞作为生成期硬过滤；设计语义的判断继续留给评分层（保持 P9.7 场景 D 的诚实信号不被饿死）。
6. **确定性承诺**：同输入逐字节一致；遍历顺序仅由 authored 数据的固定顺序（project → rooms → walls → cabinets）与组合规模决定。

- 对齐：`start | center | end` 三档

## 九、建议的验收标准（方向，不写测试）

**A. 覆盖有效性（新增）**

1. 有门洞的厨房夹具：≥1 份多柜候选在 `deriveSpatialFacts` 上全部成员 `openings.relation === 'clear'`，且评分 Gate 通过。
2. 该候选中**至少有一条**是"贴空白区段端点"的（证明不是撞运气落在中点）。
3. 同一夹具的无门洞对照仍 `valid`（不得因换搜索方式而丢掉 P9.7 的既有结论）。

**B. 纪律不变（新增）**

4. 每个 placement 重跑 `resolvePlacements` **逐字节一致**。
5. generator 源码中不存在自己算最终坐标的证据（不得出现 `atan2 / cos / sin / hypot`，也不得在 `resolved` 之上二次加工）。
6. generator **不 import** `designScore`、`ai/knowledge`、`spatial/validate` 的裁决入口。
7. 候选生成前后 `serializeProjectFile` 逐字节相同。
8. 洞口为 `unknown` 时：区段计算**不得**把 unknown 区域当成空白；必须如实进入 `unresolved`。
9. 循环依赖组合仍明确 invalid（`PLACEMENT-CYCLE`，不自动打断）。
10. `PlannerRequest` 键集封闭，且仍未出现 x / y / rotation / placements / polygon。

**C. 预算与覆盖（新增）**

11. `generated === returned + truncated` 仍成立（既有不变式）。
12. 人为构造的组合空间较大的场景：触发预算耗尽 → `budgetExhausted === true` 且 `unresolved` 有对应记录。
13. 返回的 N 条候选**跨 family**（family 数 ≤ N 时每族至少 1 条）；禁止"前 N 条同源"重演真实厨房事故。
14. 同输入两次生成逐字节一致；候选顺序一致。
15. `maxCandidates = 1` 时 `returned === 1`，且取自优先级最高的 family（确定性）。

**D. 上下游**

16. `planCandidates` 与直接调用 `scoreCandidateLayout` 对同一候选逐字节相同。
17. Compare UI：`buildCandidateComparison` 对多柜行保留全部 placements；UI 源码仍是 `placements.map`。
