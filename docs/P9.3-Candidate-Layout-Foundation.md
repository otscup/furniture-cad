## 一、架构审查（先于编码）

### 1.1 通读对象与结论

| 文件 | 角色 | 与 P9.3 的关系 |
|---|---|---|
| `core/variants.ts` | 方案对比候选（同规格不同风格 → 候选 `Cabinet`） | **只可复用思想，不可复用结构**（见 1.3） |
| `core/designIntent/*` | P9.2 设计意图（用户目标，active 才进模型） | 候选的**输入**：`activeDesignIntents(project)` |
| `core/placement.ts` | 确定性落位引擎 `resolvePlacement(intent→ResolvedPlacement)` | 候选落位的**唯一**坐标出口（绕不过） |
| `core/spatial/*` + `core/designValidation/*` | 空间事实层 | 候选**满足性**判定的唯一真相源（不重判） |
| `ai/designIntentContext.ts` + `ai/proposal.ts` | AI 只读投影 + 需求级提案 | AI 只输出 `CandidateRequest`（无坐标） |
| `commandBus.ts` | 唯一写入口 | 候选**不碰**它（不新增 op、不写模型） |
| `projectFile.ts` | 文件 schema 边界 | 候选**不进** project.json |

### 1.2 是否已有 VariantDraft 可复用 —— 否（结构不可复用）

`VariantDraft` 的核心是 `cabinet: Cabinet`（一个**完整候选柜体**，占位 id）。它的生命周期哲学（临时运行对象 / id 只在本会话有意义 / 不进 Project / 派生失败要说出来 / 单一 adopt 通道）**值得复用**；但它的**承载结构**是一只 `Cabinet`。

而 P9.3 的候选讲的是**同一批已有柜体的不同落位**，不是"造一只新柜"。若复用 `VariantDraft` 结构 = 候选里塞 `Cabinet` = 把候选变成 Cabinet，正好踩中红线"不把 candidate 变成 Cabinet"。

**结论**：复用 *thinking*，不复用 *type*。候选承载的是「语义落位意图 + 经 Resolver 解析出的坐标 + 满足性结论」，不是 `Cabinet`。

### 1.3 Candidate Layout 与 Variant 的关系

| | Variant（P3，已有） | Candidate Layout（P9.3，新增） |
|---|---|---|
| 操作轴 | 同规格、不同**风格/预设** → 新柜 | 同柜、不同**落位** → 新坐标 |
| 承载 | `cabinet: Cabinet` | `placements: CandidatePlacement[]`（含 `PlacementIntent` + `ResolvedPlacement`，**无 Cabinet**） |
| 进入模型 | `adoptVariant` → `CMD.createCabinet`（新建柜 + 换 id） | 本阶段**没有 adopt**（P9.4+） |
| 不变量 | 候选不在任何 Project 里 | 候选不在任何 Project 里（同） |

两者都遵守"候选不是真相源、选定才成为真相源"。P9.3 禁止复制一套 Variant 系统：不引入 `VariantDraft` 的字段，不引入第二套"候选柜体"。

### 1.4 哪些数据只能临时存在

- `CandidateLayout` 整体：会话内对象，**不进 `Project`、不进 project.json、不进 schemaVersion**。
- 每条 `CandidatePlacement.resolved`（坐标）：只活在候选里，是 `resolvePlacement` 的**产物**，绝不直接写回 `Cabinet.placement`。
- 与 P8.5-B 同一纪律：候选坐标是"系统算出来的第二种读数"，一旦落盘就分不清"用户摆的"与"系统猜的"，会破坏 `preview===commit` / `dryRun===commit` 逐字节不变量。所以**候选只活在内存，落盘即消失**。

### 1.5 如何保证候选不是第二真相源

四条硬保证（逐条可测）：
1. **类型保证**：`CandidatePlacement` 不含 `Cabinet`，只含 `PlacementIntent`（语义）+ `ResolvedPlacement`（坐标）。想写成 Cabinet 写不出来。
2. **写保证**：本层**不 import `commandBus` / `ai` / `export` / `manufacturing`**，没有写入口；`generateCandidateLayouts` 接收 `project` 只在**克隆副本**上试算，绝不改入参。
3. **路由保证**：每个候选落位是一份 `PlacementIntent`，**必须**经 `resolvePlacement` 得到坐标；不存在"直接把 x/y 塞进 `ResolvedPlacement`"的旁路。
4. **无 adopt**：本阶段**不导出任何 adopt/apply/commit 函数**——候选到不了模型，物理上无法变成真相源。

### 1.6 用户 12 条边界的逐条确认（本阶段怎么做）

| 边界 | 本阶段落点 |
|---|---|
| 不是 Project / 不是 Cabinet / 不是 File schema | `CandidateLayout` 是独立临时类型，三者都不是 |
| 候选只能描述"如果这样摆会怎样" | `placements[].resolved` + `issues` + `explanations` 正是"结果"，不替代真实 placement |
| 禁止直接改 `Cabinet.placement` | 仅克隆副本试算；不碰入参 |
| 禁止随机搜索 | `candidateSpots` 是确定性枚举；无 `Math.random` |
| 禁止 LLM 自生成坐标 | 坐标只由 `candidateSpots`+`resolvePlacement` 决定；AI 只输出 `CandidateRequest`（无 x/y/rotation） |
| 必须 Intent ↓ CandidatePlacement ↓ resolvePlacement ↓ validation | 生成器严格走这条链 |
| 当前只允许 draft | `CandidateStatus = 'draft'`（字面量，类型层没有 evaluated/adopted） |
| 不能自动 adopt | 无 adopt 函数 |
| AI 读 SpatialContext + DesignIntent，输出 CandidateRequest | `CandidateRequest` 只引用意图 id / 柜 id，无坐标 |
| 与 Variant 复用思想、禁复制系统 | 见 1.3 |
| 验收 9 项 + 变异 3 项 | 见 §二 实施记录 |

### 1.7 本阶段结论（做 / 不做）

**做**：纯临时对象 `CandidateLayout`（model）+ 确定性枚举器 `generateCandidateLayouts`（generate）+ `CandidateRequest`（AI 输出形态）+ 复用 `resolvePlacement`/`candidateSpots`/`detectCollisions`/`deriveSpatial`/`deriveContacts` 作为唯一真相源。

**不做**：评分（P9.4）、选 winner、AI Planner、LLM 自动布局、`adopt`、改 Resolver、改 Semantic Model、写 project.json、把 candidate 变成 Cabinet、新增任何 `CommandBus` op。

### 2.2 关键架构决策

1. **复用 Variant 的思想、不复用它的结构**（审查结论 1.2/1.3 的落地）：候选落位是「`PlacementIntent`（语义）+ `ResolvedPlacement`（Resolver 产物）+ `issues` + `satisfies`」，**没有** `Cabinet`。于是"候选变成 Cabinet"在类型层就写不出来。
2. **Resolver 是唯一坐标出口**：每个贴墙落点先包成一份 `absolute`（`origin:'authored'`）`PlacementIntent`，再 `resolvePlacement(intent, scene)` 得坐标。这里的 `authored` 只表示"候选沙盒里一个确定的坐标提案"，**不代表用户对真实模型授权**（候选根本不碰模型）。
3. **只读克隆试算**：`cloneWithPlacement()` 用 `{...project, cabinets: map(...)}` 造副本，入参 `project` 一个字节都不动（验收第 10/11 条钉死）。
4. **判定零第二份**：冲突用 `detectCollisions`（与 CommandBus 同一来源）、满足性用 `deriveSpatialFacts`/`deriveContacts`（事实层）。候选层**不写第二套 AABB、不写第二套"贴没贴墙"**。
5. **生命周期在类型层封死**：`CandidateStatus = 'draft'` 是字面量 —— 写不出 `'evaluated'`/`'adopted'`（与 P9.2 去掉 `'system'` 同款手法）。
6. **无 adopt 通道**：`index.ts` 不导出任何 adopt/apply/commit/persist；候选只到"描述结果"为止。

### 2.3 生成链（严格走 Intent → Placement → Resolver → validation）

```
activeDesignIntents(project)                       ← 读侧唯一入口，只有 active 算数
  → 过滤「可构造目标」= {wall-contact, standalone}  ← 其余（取舍方向 / 别的构造器）如实进 unresolved
  → candidateSpots(project, roomId, width)         ← 确定性贴墙枚举（与 Variant 同一份）
  → PlacementIntent{relation:'absolute', origin:'authored'}
  → resolvePlacement(intent, scene)                ← ★ 唯一坐标出口
  → cloneWithPlacement(project, cabId, resolved)   ← 只在副本上
  → detectCollisions(clone) + deriveSpatialFacts + deriveContacts  ← 冲突 / 满足性（唯一真相源）
  → CandidateLayout{...}
```

### 2.4 三档候选 A / B / C（确定性，无随机、无组合爆炸）

对每个（可构造意图 × 目标柜），遍历贴墙落点（`candidateSpots` 按"长墙优先 + 沿墙滑 11 个比例点"），按策略各取**第一个**合格落点：

| 策略 | 含义 | 对应 |
|---|---|---|
| `wall-same` | 第一个"放得下 + 朝向与现状相同"的贴墙落点 | 尝试**贴墙** |
| `wall-other` | 第一个"放得下 + 朝向与现状不同"的贴墙落点 | 尝试**不同朝向** |
| `satisfy` | 第一个"放得下 + 真正满足该意图"的贴墙落点 | 尝试**满足 wall-contact intent** |

- "放得下"的判据**只有一份**：`detectCollisions`（撞墙 RULE-CABINET-IN-WALL / 撞柜 RULE-CABINET-OVERLAP 都筛掉）。
- 每策略只取一个、总上限 `maxCandidates`（缺省 `MAX_CANDIDATES_PER_TARGET = 3`，超过夹到 3）。
- 同一输入两次生成**逐字节相同**（无 `Math.random`、无时钟；id 由 `nextId('cl', taken)` 确定性取号）。

### 2.5 生命周期、draft 与"无 adopt"

- 本阶段**只允许 draft**；`CandidateLayoutSet.status` 与每个 `CandidateLayout.status` 恒为 `'draft'`。
- 候选**不进入** `Cabinet` / `Project` / `project.json` / `schemaVersion`：生成前后 `project` 与 `serializeProjectFile(project)` 逐字节不变，序列化结果里不出现任何 `cl_xxx`，也不出现 `candidate` 字样。
- 适配 P8.5-B 纪律：候选坐标是"系统算的第二种读数"，一旦落盘就分不清"用户摆的"与"系统猜的"，会破坏 `preview===commit` / `dryRun===commit` 逐字节不变量 → **候选只活内存**。
- **没有 adopt**：导出面里没有 adopt/apply/commit/persist 任何名字（验收第 34/35/36/37 条）。要真正生效只能走未来的通道（且那时也必须过 CommandBus）。

### 2.6 AI 边界

- AI 可读：`spatialContext`（P9.1）+ `designIntent`（P9.2）——都只读。
- AI 可输出：`candidateRequest = { intentIds?, cabinetIds?, scope, maxCandidates? }`，**只有 id 与枚举，没有 x/y/rotation**。
- `validateCandidateRequest()` 是**白名单校验**：`x`/`y`/`rotation`/`placements`/`geometry`/`angle`… 一律 `GEOMETRY_FORBIDDEN` 拒收；未知键 `EXTRA_KEY` 整条拒收；缺 `scope` 归一为 `'project'`。
- 提示词（`buildUserMessage`）明说：候选请求"**只用 id**、**绝对不要给 x/y/rotation**"、"系统会据此确定性枚举"、"**候选不会被自动采用**（本阶段没有'采用'这一步）"。
- **动作清单仍 21 条**，一个字未改；候选请求**不是动作**（它不改模型，所以不进 `ACTIONS`）。

### 2.8 变异测试（三项，实测必须红，已还原）

> 判据纪律：变异测试不是"跑了绿"，而是"**改坏之后真的变红**"，并在还原后重新变绿。

| # | 变异 | 实测变红的断言 | 说明 |
|---|---|---|---|
| A | 在候选落位里塞 `cabinet: cab`（候选写入 Cabinet） | **第 3 / 4 / 5 / 63 条** | `placementClean` 哨兵逮住多出来的键；第 5 条逮住 `params`/`layout` |
| B | 绕过 Resolver：删掉 `resolvePlacement` 调用、直接手写坐标 | **第 18 / 21 / 23 条**（且 §9 第 66 条哨兵自检为绿） | 第 21 条（源码必须真的存在 resolver 调用）逮住"删调用"；第 18 条（`resolved` 必须等于 resolver 输出）逮住"自己算了一个不同的坐标（+5）" |
| C | 给候选层加一个 `export function adoptCandidate`（候选自动 adopt） | **第 34 / 35 / 37 条** | 导出面扫描 + 源码扫描 + 显式存在性检查三处同时变红 |

**B 的诚实说明**：候选的 intent 是 `absolute`，而 Resolver 对 `absolute` 只做取整（整数进 = 整数出，属恒等）—— 所以"值不变地绕过 resolver"单靠动态等值判据**抓不住**，必须靠第 21 条（源码里真的存在 `resolvePlacement(` 调用）兜底。这一点在验收脚本里如实写着，不粉饰。

§9 的**哨兵自检**（第 63–68 条）保证三条哨兵**不是空的**：用一个"故意写坏的样本"（塞了 `cabinet` 的落位 / 手改了 x 的落位 / 伪造的导出名列表）确认判据真能返回 false —— 断言不可信比失败更危险。

### 2.10 遗留问题 / 明确不做（本阶段边界）

- **不做**（红线）：P9.4 评分、选 winner、AI Planner、LLM 自动布局、`adopt`、改 Resolver、改 Semantic Model、写 project.json、把 candidate 变成 Cabinet、新增 CommandBus op。

- **一份候选只重摆一只柜**（room-scope 意图逐柜生成候选）：多柜**组合**枚举（真正"整套布局"）留待后续；本阶段刻意不做组合爆炸。
- **候选没有 UI 接线**：本阶段是基础设施，界面入口与"比较/采用"交互属后续阶段。
