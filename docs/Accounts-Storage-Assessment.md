# 账号库存储评估：JSON → DB？（2026-09-24，Task #27）

## 结论

**现阶段保持 JSON 文件，不换 DB。** 预设一条明确的迁移触发线，而不是"以后再说"。

## 依据

### 为什么 JSON 目前是对的

1. **数据形状**：账号库是「少量低频改写的结构化对象」——账号数（个人使用）≤ 10，
   写操作只发生在登录/改密/管理动作，读操作每请求一次鉴权。JSON 全量读写
   在这个量级下是微秒级，SQLite/Postgres 的查询能力完全用不上。
2. **运维面**：本地优先（无 VPS）。JSON 文件 = 备份是复制、迁移是复制、
   排障是记事本打开。引入 SQLite 需要 node:sqlite 或 better-sqlite3 原生依赖
   （跨机器部署多一个编译失败点），引入 Postgres 直接违背单机约束。
3. **崩溃面不变**：无论 JSON 还是 DB，写路径都是 `#save()` 单点。换成 SQLite
   并不会让崩溃一致性变得更好——当前 `writeFileSync` 全量覆盖 + 原子性由
   OS 保证，账号库损坏时初始化代码已有"格式不对就当空库"的降级。
4. **真实瓶颈不在存储**：`authenticate()` 每请求线性扫全部账号的全部会话。
   瓶颈是**内存数据结构**，不是磁盘格式。真要优化，先做 token 哈希 → 账号的
   Map 索引（纯内存改动），与换 DB 无关。

### 迁移触发线（满足任一条就启动迁移）

| 触发条件 | 目标 |
|---|---|
| 账号数 > 100 或多租户（tenantId 出现多个租户） | SQLite（node:sqlite，无原生编译） |
| 会话数 > 1000（线性扫描开始被观测到） | 先做内存索引，再评估 DB |
| 出现第二台机器要共享账号库（哪怕只读） | SQLite + 文件共享 或直接 Postgres |
| 审计日志 > 50 万条 / 需要按字段查询审计 | 审计单独进 SQLite（只追加，最安全的一张表） |
| 服务需要多进程 / 多实例 | SQLite(WAL) 起步，并发冲突出现再上 Postgres |

### 迁移时的红线（现在就写下来）

- token 哈希格式（`sha256`）与口令哈希格式（自描述 scrypt 串）**不变**——
  迁移是搬存储，不是重新哈希，否则所有用户被迫改密。
- 审计 JSONL 已产生的历史文件**原样保留**，迁移只针对新写入。
- `auth.mjs` 的公开方法签名不变 —— 上层 server.mjs 与验收（verify/admin-acceptance.ts）
  不感知存储切换。这也是现在就把会话管理做成方法而不是散在 server.mjs 里的原因。
