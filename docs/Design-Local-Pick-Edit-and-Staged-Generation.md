> 本轮**只做设计，未改动任何代码**。所有结论基于真实文件勘察，引用处给路径与行号。

## 0. 结论先行

| 你的想法 | 能做吗 | 我要改的地方 |
|---|---|---|
| A · 点选一条线 → 让 AI 改这个位置 | **能做**，但"改这条线"必须换成"改这个语义部件" | 需要新增一层**几何 → 语义的反查**（`PickLine`） |
| A · 圈选一个范围 → 让 AI 改 | **能做**，比上一条简单 | 圈选结果必须是**对象集合**，不能是"几何区域" |
| A · "生成的内容要和整体对接上" | **已经是结构性保证**，不用额外做 | 缺的是"这次改动会波及谁"的影响面提示 |
| B · 先出正面图 → 出两个风格 → 选完再出四视图 | **流程能实现**，但中间产物必须换一个 | 中间产物不能是"正面图"，必须是**候选语义方案** |

**最重要的一条：B 的"从正面图生成四视图"必须改成"从候选语义方案生成四视图"。**
界面上看起来一模一样（都是先看正面图），但内部不同。区别在于一句话：

> **600 的进深从哪来？**
> 正面图里根本没有深度信息。如果正面图成了中间产物、还被手改过，
> 那么侧视图和俯视图只能去"猜" —— 而"猜"出来的东西**对不上正面图**，
> 正是你现在这套 `views.ts` 用结构映射彻底消灭掉的那类问题。

## 1. 现状勘察（真实文件）

### 1.1 现在能"点到"什么

| 能力 | 状态 | 证据 |
|---|---|---|
| 命中优先级 | 夹点 > 柜体 > 墙（夹点最高，理由写在注释里） | `src/viewport/hitTest.ts:6-12`、`:80-112` |
| 夹点**已经是语义句柄** | `cab-width-l` / `cab-width-r` / `cab-depth-f` / `cab-move` | `hitTest.ts:14 GripRole` |
| 框选（窗口 / 交叉） | **已实现**，且用的是 AutoCAD 约定（左→右=窗口，右→左=交叉） | `hitTest.ts:139-165 boxSelect`、`:168 boxSelectMode` |

| 视图模式切换 | `mode: 'plan' \| 'sheet'`（平面图 / 四视图图幅） | `src/ui/Viewport.tsx:46` |
| **线 / 部件的拾取** | ❌ **完全没有** | `hitTest.ts` 的最小粒度是"整个柜体"或"整面墙" |

> **关键缺口：`hitTest` 只能告诉你"点到哪个柜体"，不能告诉你"点到柜体的哪个部位"。**

### 1.2 AI 契约现在能"指向"什么

```js
// shared/aiContract.mjs:255
const TARGET_KEYS = new Set(['cabinetId', 'cabinetName', 'roomId', 'roomName', 'unit']);
```

| 粒度 | 现状 |
|---|---|
| 柜体 | ✅ `cabinetId` / `cabinetName` |
| 房间 | ✅ `roomId` / `roomName` |
| 分区 | ✅ `unit`（1 起序号或昵称，`resolveUnit` 会做模糊匹配并报出候选） |
| **部件（门缝 / 层板线 / 踢脚线 / 顶板线）** | ❌ **指不到** |

而且 `src/ai/compile.ts:116-121` 已经有一张**"做不到"表**，如实登记了现状：

```
doors: '门板由柜体的分区类型决定，当前动作清单里没有"给已有分区加门"'
```

这种"做不到就说做不到，不许编"的做法是对的，**扩展时必须保持**。

### 1.3 四视图是怎么来的

- `buildCabinetViews(cab, rules, opts)` → `ViewSet`，`prims: Record<ViewKind, Prim[]>` —— **4 个视图一次全出**
- `ViewOpts` 现在只有 `x / y / gapTop / gapSide / gapInt`（`views.ts:124-131`）—— **没有"只要正面图"的开关**
- 投影不变量是**结构性**的：俯视图在正视图正下方 → 长对正；侧视图在正视图正右方 → 高平齐（`ViewsPanel.tsx:80-82`）

> **所以你说的"带逻辑的四视图"已经具备了** —— 它现在就是派生的、恒等对正的。
> 缺的不是"逻辑"，是**"先对比再定稿"这个阶段**。

## 2. 功能 A：点选 / 圈选 → AI 局部编辑

### 2.1 第一个必须说清的问题：你的"线条"在模型里不存在

`plan` / `elevation` 里的线是 `Prim`（派生图元，`types.ts:189-192`）。
**模型里没有任何"线"这个对象** —— `Project` 里只有房间、墙、柜体（`types.ts:21-27`）。

这是主动设计的结果，不是遗漏。项目铁律：

> **拖动 = 改语义参数字段，严禁改坐标 / 线条**

所以"点选这条线，让 AI 把它往右挪 50mm" **不能做** —— 那等于引入第二个真相源，
此后这条线和它背后的 `params.width` 谁对谁错永远说不清。

### 2.2 正确做法：几何 → 语义的反查（`PickLine`）

**新增一层，不改动 `Prim` 本身**：

```ts
// src/viewport/pickResolve.ts（新）
export interface PickLine {
  /** 哪一个视图里的线（正视图上的线和俯视图上的同名线不是一回事） */
  view: ViewKind;
  /** 图元上的点，用于命中测试 */
  pts: Vec2[];
  layer: string;
  /** ── 下面三项是这一层存在的全部意义 ── */
  cabinetId: string;
  /** 语义部件：闭合词汇表，不许自由文本 */
  part: CabinetPart;
  /** 它由哪个参数决定 —— AI 最终改的就是这个路径 */
  paramPath: string;
  /** 人能看懂的名字，界面上直接显示 */
  labelZh: string;
}

export type CabinetPart =
  | 'outer.width' | 'outer.height' | 'outer.depth'
  | 'bodyLift'            // 踢脚线
  | 'topBoard' | 'bottomBoard' | 'sideBoard'
  | 'unit.divider'        // 分区之间的中立板
  | 'door.gapMid' | 'door.gapOuter' | 'door.edge'
  | 'shelf.line'          // 层板线
  | 'drawer.divider'      // 抽屉分格线
  | 'rod.line';           // 挂衣杆
```

**为什么是"生成图元时同时产出"，而不是"事后反查"：**

- `Prim` 只有 `layer` 和 `pts`，**不携带"这条线是哪个参数画出来的"**
- 事后反查 = 另写一份判定逻辑 → 会和生成器漂移，两边一起错就永远发现不了
  （这正是 `src/core/rules/validate.ts:9-11` 明确禁止的："校验器必须校验生成器的输出，而不是自己另算一遍"）
- 由生成器产出 → **与几何同源，结构上不可能漂移**，并且可以单测：
  "正视图踢脚线的 `paramPath` 必须等于 `params.bodyLift`"

### 2.3 反查表（正视图上的线 → 语义）

| 你在正面图上点到的线 | 解析成 | AI 可改的动作 |
|---|---|---|
| 左右最外轮廓 | `outer.width` | `cabinet.resize` |
| 上下最外轮廓 | `outer.height` | `cabinet.resize` |
| 底部踢脚线 | `bodyLift` | `cabinet.setBodyLift` |
| 分区之间的竖线 | `unit.divider` | `cabinet.setUnitWidth` |
| 门缝（中缝 / 边缝） | `door.gapMid` / `door.gapOuter` | `cabinet.setUnitParam` |
| 层板的水平线 | `shelf.line` | `cabinet.setUnitParam`（`shelves.count`） |
| 抽屉分格线 | `drawer.divider` | `cabinet.setUnitParam`（`drawers.count`） |

**AI 收到的永远是 `{ cabinetId, part, paramPath }`，永远收不到坐标。**
这一条要在契约里写成断言（和现有 I1–I3"快照里不许出现几何"对齐）。

### 2.4 圈选：给**选择集**，不给几何范围

`boxSelect` 已经返回**对象 id 集合**（柜体 + 墙），不是像素区域。这是对的，别改。

AI 侧需要的扩展：

```js
// aiContract.mjs
const TARGET_KEYS = new Set([..., 'scope']);

// 两种指向方式，互斥
target: { cabinetName: '主卧衣柜', part: 'door.gapMid' }     // 点选
target: { scope: 'selection' }                                // 圈选：当前选择集
```

**绝不能出现的是**：`target: { rect: [x1,y1,x2,y2] }`。
理由：AI 不该知道坐标；而且"一个矩形范围"在语义上是空的 —— 圈到半个柜体算什么？

**边界必须显式处理**：圈选里混了柜体和墙时怎么办？
→ 建议：**按类型分组，只把 AI 能处理的那部分交给它，并在界面上如实说"另有 N 面墙不在 AI 可改范围内"**。
不要静默过滤（这是这个项目一贯的立场）。

### 2.5 你担心的"对不上" —— 架构已经保证了

```
AI 改语义参数 → Command → CommandBus → derive → validate（IDENTITY-* 恒等式断言）
```

**只要 AI 改的是语义参数，"局部改动与整体对接"就是结构性保证，不需要额外机制。**
一旦对不上，`IDENTITY-FAIL` / `LAYOUT-CACHE-STALE` 会当场报错。

**但有一个真缺口**：现在没有**影响面提示**。
用户点一条层板线说"往下挪 200"，他不知道这会连带影响门板高度、抽屉分格、铰链数量。
→ 建议：干跑预览里加一条「这次改动会连带改变：门板高 −200 / 抽屉分格重排 / 铰链 4→3」。
这个信息**后端已经算得出来**（`geom.layout` 前后对比），只是现在没展示。

### 2.6 三条不能做的事

| 不能做 | 为什么 |
|---|---|
| 让 AI 输出坐标或偏移量来挪线条 | 违反「几何永不来自 AI」（`aiContract.mjs:24` 铁律 1） |
| 建立一个"可编辑的线条层" | 等于引入第二真相源，此后线与参数谁对谁错说不清 |
| 圈选一个**几何区域**让 AI "在这块区域里加东西" | 区域在语义上是空的；必须解析成对象集合 |

### 2.7 引用失效 —— 现有机制已经覆盖

一个必须先想的问题：**AI 改了分区数之后，它引用的那条"第 3 块层板"可能已经不存在了。**

现有实现已经处理：`compileAction` 的注释（`:126-129`）说明**每一步对着上一步的结果编译**，
`resolveUnit` 会返回"没有叫 XX 的分区（现有：…）"并列出候选。
新增 `part` 后，必须为 `part` 做同样的事：**编译前校验该部件仍然存在，不存在就报出候选，不许静默改别的东西。**

## 3. 功能 B：分阶段生成（正面图 → 选风格 → 四视图）

### 3.1 你的流程能实现 —— 但中间产物必须换一个

**你的流程（界面视角）**：
```
说"生成一个 2400×2400×600 的柜子"
  → 出正面图（同时给 2 个不同风格）
  → 客户选一个、改到满意
  → 生成带逻辑的四视图
```

**必须改成（内部视角）**：
```
  → 生成 N 份【候选语义方案】（差异只在风格参数上）
  → 每份派生它的正面图，并排对比      ← 界面上你看到的就是这一步
  → 选定一份 → 它成为真相源
  → 完整四视图从这份方案派生
```

**界面上完全一样，内部差一个东西：中间产物是"方案"不是"图"。**

### 3.2 为什么必须换 —— 那句关键的话

> **如果中间产物是正面图，那 600 的进深从哪来？**

正面图里只有宽和高。深在俯视图和侧视图里。若四视图要"从正面图生成"，
就必须从一张没有深度信息的图反推出深度 —— 那只能是猜。

而你现在的代码里，深度**不是猜出来的**：`buildCabinetViews` 从 `cab.params.depth` 取（`views.ts:246`），
四视图共用同一份 `(X,Y,Z)`、只做"取两个分量 + 平移/翻转"，所以长对正 / 高平齐 / 宽相等是**结构性**的。

**把中间产物定成"正面图"，等于把这个结构性保证换成一次反推。** 这是我要改你方案的唯一一处，但很要紧。

### 3.3 风格 = 一组语义参数，放在规则集里

"风格"不是一个图面样式（不是换个颜色/线型），它是**一组语义参数的取值**：

```ts
// 规则集里新增（换工厂 = 换文件，与现有 RuleSet 一致）
interface StylePreset {
  id: string;
  nameZh: string;                 // 「一门到顶」「上下分段」「抽屉 + 上翻门」
  note?: string;                  // 假设/工艺说明，界面上要显示
  patch: {
    layout?: { units: Array<{ kind: UnitSpec['kind']; requestedWidth: number; nickname?: string }> };
    doors?: { count: number; gapMid: number; gapOuter: number };
    boardMaterial?: string;
    backMaterial?: string;
    hardwarePatch?: Record<string, string>;
  };
}
```

放在**规则集**而不是代码里，符合现有约定："换工厂 = 换规则文件"（`aiContract.mjs:26` 铁律 2）。

**为什么必须是语义参数而不是图面样式**：图面样式改不出"门扇数从 2 变 3"，
而客户选风格恰恰就是在选分格方式。而且只有语义参数才能让四视图**一致地**跟着变。

### 3.4 变体**不写进** `Project`

```ts
// 视图状态（不是模型）
interface VariantDraft {
  id: string;
  nameZh: string;
  sourcePresetId: string;
  /** 一份【候选】语义模型 —— 还没成为真相源 */
  cabinet: Cabinet;
  /** 派生出来的正面图，只用于对比 */
  front: Prim[];
  issues: Issue[];      // 这份方案的校验结果 —— 让客户在选的时候就看到问题
}
```

**候选不是模型。选定之后才走 `cabinet.create` 落地。**
否则 `Project` 里就会躺着 3 个"半成立的柜体"，而真相源只能有一个（铁律 1）。

> 顺带一个好处：**每份候选都带自己的 `issues`** —— 客户选风格的时候就能看到
> "这门板高 2302mm 超过上限"，而不是选完才发现。这是纯增量的价值。

### 3.5 改动其实很小

| 需要改 | 说明 |
|---|---|
| `ViewOpts` 加 `kinds?: ViewKind[]` | `views.ts:124`，让 `buildCabinetViews` 能只出正面图 |
| 新增 `buildVariants(spec, presets, rules)` | 纯函数：一份规格 + N 个风格 → N 份候选模型 |
| 新增 `VariantCompare` 面板 / 命令行 | 并排显示 N 张正面图 + 各自的 issue |
| 选定 → `CMD.createCabinet` | **复用现有命令**，不新增写入口 |

**"带逻辑的四视图"不用改** —— 选定之后走的就是现有 `buildProjectViews`。

### 建议顺序

**先做 B，再做 A。** 三条理由：

1. **B 的风险低得多**：B1 只加一个可选字段，B3 是纯函数，B5 复用现有命令。
   而 A 要新增一层反查，它必须和几何**同源**才不漂移 —— 这是这个项目里最容易做错的一类改动。
2. **B 直接对着客户**：你说"用于客户选择"，这是能立刻产生价值的东西。
3. **A 依赖一个判断要先定下来**：`CabinetPart` 这个闭合词汇表的边界划在哪。
   定得太粗，AI 指不准；定得太细，词汇表会膨胀到模型选不对（和现有 18 个动作的取舍是同一个问题）。

### 6.2 期间发现的三个真缺陷（都不是断言写错）

**D1 —— 候选没有落点，采用必定被记忆门拦下。**
候选柜体建在 (0,0)（对比阶段不需要位置），而默认项目里 `cab_001` 在 (400,60)、
南墙内表面也在 y=60 —— 于是采用时同时撞墙和撞柜，`RULE-CABINET-IN-WALL` +
`RULE-CABINET-OVERLAP` 被记忆门拦下。界面上只说一句"被记忆拦住"，
**用户第一次点「采用这个方案」就失败**。
而原本 41 项 Node 验收**一条都抓不到**：候选是孤立校验的，不参与项目级干涉检查。
修法：新增 `candidateSpots()`（`snapPlace.ts`，沿每面墙贴放、从中间向两端滑）
+ `placeVariant()`（`variants.ts`），判据由调用方用 **CommandBus 干跑**提供 ——
不自己写第二份 AABB。放不下时返回 `null` 并如实告知，不许退化成"先放进去再说"。

**D2 —— `sin(π)` 不是 0，旋转过的柜体贴不上墙。**
`Math.sin(Math.PI)` = 1.2246e-16。一个旋转 180°、背靠北墙内表面 (y=2540) 的柜体，
算出来足迹 `max.y = 2540.0000000000005`，比墙面大了 **4.5e-13 mm**；
而碰撞判定用的是严格小于（"相切不算干涉"），于是"贴墙"被判成"扎进墙里"。
它只在 rotation ≠ 0 时出现，而手工测试几乎总是转 0°，所以能一直藏着 ——
直到 D1 的自动落点第一次尝试"贴着某面墙放"才暴露。
修法：`geometry/transform.ts` 的旋转矩阵里，本该是 0 / ±1 的分量**精确取值**。

**D3 —— 采用后设的选中被"切模式"的 effect 清掉。**
`onAdopted` 里 `setSelection([id])` 与 `setMode('sheet')` 在同一批提交，
随后 `useEffect([mode])` 跑起来把选中清成空 —— 静默失效，界面上什么都没报错。
修法：用一个 ref 指定"切模式后该选中谁"，两条路（effect 触发 / 不触发）都成立。

### 6.3 断言自己写错的四条（诚实记录）

1. `topIssue(wide)?.code === 'RULE-DOOR-MAX-WIDTH'` —— 3600 宽时第一条 ERROR 是
   `RULE-PANEL-OVER-SHEET`，门宽超限排在后面；`topIssue` 返回的是**第一条** ERROR。
2. `panelSet('宽 W','1800')` 没生效 —— `NumField` 是**失焦/回车才提交**
   （否则输入 2400 会在撤销栈里留下 4 条命令），探针只派了 input/change。
3. `text('.toast-ok')` 只读到**第一条** toast —— 生成那步的提示还没消失，
   把采用的回执挡住了。改成读整条 `.toasts`。
4. B19 的页签清单漏了新加的「方案」，于是那个面板的类名一个都没被审计到。

### 6.4 一条方法论：断言必须证明自己抓得住

D2 的第一版回归断言是"贴墙不算撞墙"。**关掉修复后它照样通过** ——
因为墙的多边形自己也带同一类残差，两边偶然抵消了。
只断言"没有报错"等于什么都没断言。后来改成钉根因：
**足迹坐标必须是精确整数 mm**（`Number.isInteger`），关掉修复立刻红 2 条。

→ 规则：新增的回归断言，要临时把修复关掉跑一次，确认它**真的会失败**。
  一个从没红过的断言，是负债不是资产。
