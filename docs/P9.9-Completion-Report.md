### 1.1 约束一：三个**透传**缺口 + 一个**显式拒绝**

| 位置 | 此前 | 现在 |
|---|---|---|
| `ai/proposal.ts` `ProposalUnit` | **没有** `doorMaterial` 字段 → 方案路径把玻璃门**静默降级**成默认木门 | 声明 `doorMaterial?: string \| null`（契约 `UNIT_INTENT_ITEM` 与 legacy `compile.ts` 本来就支持它） |
| `ai/compileProposal.ts` `stripUnit` | 闭集拷贝，**不含** `doorMaterial` | 显式拷贝 `doorMaterial` |
| `ai/vision/visionResultToNormalized.ts` `mapUnit` | 未读 `rodHeight` → 视觉识别到的挂杆高被丢 | 透传 `rodHeight` |
| `ai/snapshot.ts` `AiUnitView` / `unitView` | 无门板材质 → AI 看不到"这扇门是玻璃的" | `doors.material` 透传 |
| **表外字段**（`customHardware` 这类） | 全局无声明 ⇒ **纯静默丢失** | `validateProposal` 新增**字段白名单** ⇒ `PROPOSAL-UNIT-FIELD`（进 `issues` **且**进 `notes`），**拒绝该字段但保留整份方案** |

**为什么白名单从契约读**（`Object.keys(UNIT_INTENT_ITEM)`）而不是另写一份常量：
写死一份必然与契约分家 —— 契约加了字段、这边的拒绝还在报旧表。`stripUnit` 是"闭集拷贝"，
本表是"闭集校验"，**两者必须同源**，否则又会长出"校验放行、拷贝丢掉"的静默丢字段。

### 1.2 约束二：解释层为什么不是第二真相源

`core/candidateLayout/explain.ts` 的每一条都是对既有对象的**引用/重塑**，没有新事实：

| 解释层字段 | 来源（**唯一**） | 验收钉死的性质 |
|---|---|---|
| `status` | `score.status` | 恒等，**不得**从 `components` 反推（A3 / A3b） |
| `blocking[]` | `score.hardFailures` | 逐条**五项**（code/severity/target/message/source）一致（A4） |
| `placements[].items` + `crossCutting` | `score.components` | code 集合**恰好等于** `components.map(id)`，不多不少（A5） |
| `generationNotes` | `layout.explanations` | **逐字节相同**（不解析/不改写/不排序）（A6 / A6b） |
| `placements[].generatorSignals` | `placement.satisfies` | 标为**生成期粗判**，与事实项**分区**，绝不并入结论（C10/C11） |
| `unresolved` | `layout.unresolved` | 原样引用 |
| `summaryZh` | 由上面这些字段拼出 | 无"最好/最优/推荐/建议选/最佳"（B8）；`unknown` 写"判不出来"（D12b/D13） |

**归因口径（决策 D2，取路 ①）**：`DesignScoreComponent` **本身没有** `cabinetId`。本层按
"能追到柜才追"的原则：`blocking` → 按 `hardFailure.target`；`preference` → 按
`preferenceMatches[].cabinetId`；其余（condition / unavailable）→ **一律落 `crossCutting`**
（尤其房间级 `unavailable`：验收 E16 明令不许塞进任一 placement）。
**严禁靠解析中文 `label` 反推柜名。** 取路 ① 的代价是本层收 `project` 做 id 映射，
换来的收益是 **P9.4 封板模型一动不动**。

### 1.3 约束三：Selection 身份（真实错指）

**问题实证**：候选 id 由 `candidateLayoutId(taken)` 生成，**位置性** —— 每轮从空集起算（`cl_001`…）。
所以"选中 `cl_003`"在**重新生成**之后会指到**另一个候选**（同 id、不同内容）。

**修法**：
1. `generate.ts` 里既有的内容签名 `candidateSignature` **改名导出**为 `candidateKey`
   （仍是**唯一实现**，不是另写一份口径）；
2. sessionStorage `p96:selectedCandidate` 里改存 **JSON**：`{candidateId, key}`；
3. 恢复走 `resolveSelection(plan, stored)`：**id 找得到 且 该候选当前 `candidateKey` 与存下来的逐字符相同**；
4. 任一不成立 ⇒ 返回 `null` ⇒ 调用方**清除**选中，**绝不回退**到"id 相同就认"。

验收用**真实重生成**证明：把柜宽 900→1200（落墙锚点变 ⇒ 解析坐标变 ⇒ 内容键变），
`cl_001` **仍在**但 `candidateKey` 已从 `1|c1@1550,60,0` 变成 `1|c1@1400,60,0`
⇒ `resolveSelection` 必须返回 `null`（F19）。

## 二、三个关键技术决策

| # | 决策 | 理由 |
|---|---|---|
| **D1** | **M1（给 `CandidateLayout` 加结构化 `searchFamily`）不落地** | `CandidateLayout` 是**已封板**对象。"搜索族"目前以自由文本住在 `explanations` 里；加字段会**静默破坏** `verify:candidate-layout` 第 6 项（"键恰好是 {...}"），而按纪律该套件**不许放宽**。⇒ 解释层把 `generationNotes` **整串原样透传**、不解析（A6b 就是防"正则解析后重组"） |
| **D2** | component → 柜的归因取**路 ①**（解释层收 `project`，**不动** P9.4 模型） | P9.4 已封板 133 项。给 `DesignScoreComponent` 加 `cabinetId?` 更"干净"，但那是改封板模型；本轮尽量只做**投影** |
| **D3** | 表外字段取 **WARNING**（不阻塞）而非 ERROR | 全族 `PROPOSAL-*` 多为 ERROR，但多写一个字段**不该把整份方案退回**；取"**不阻塞 + 双通道显式**"（`issues` 进 UI 的"提示"计数 + 写进 `notes`）更合适。判据**只有一处**（`validateProposal`），`compileProposal` 只**转述**不重判 |

> **D3 的措辞纪律**：`notes` 里那句必须**指名道姓**说清是哪个字段（"系统**不会**静默忽略它 ——
> 忽略了你就会以为它配上了"）—— 否则"不静默"就退化成了"打了个不起眼的警告"。

## 五、真实厨房三柜回归（本地、确定性管线）

用与 P9.8 报告 §五**同一形态**的真实厨房夹具（5200×4200、三只 900 宽柜、南墙
`offset 1000 / width 900 / hinge start / into-room` 门洞、房级 `wall-contact` 意图），
走**真实管线** `planCandidates(project, { scope:'project', cabinetIds:['c1','c2','c3'], maxCandidates:6 })`：

| 项 | P9.8 实测 | **P9.9 实测** |
|---|---|---|
| 探索台账 | `requested:6, generated:24, returned:6, truncated:18, generationLimited:true, explored:90, rejected{0,18,48}, budget:216, budgetExhausted:false` | **逐项完全相同** |
| 候选总数 / 三柜整体候选 | 15 / 6 | **15 / 6** |
| valid / infeasible | 4 valid + 2 infeasible 共存（多柜部分） | 共存（`J33`） |

**这就是"P9.9 一行没碰生产侧"的硬证据**：台账是生成期算出来的，它逐项不变，
说明候选生成 + 台账记账在 P9.9 里零改动。

在此基础上，新的解释层对**同一批真实候选**（`J34`–`J38`）：
- 三柜候选 → 解释块 **3 块**，`targetId` 与 `placements` **同序**；
- `infeasible` 候选的 `blocking` **逐条五项**等于 `hardFailures`（洞口/门摆阻断如实透传，不美化）；
- 解释项**零坐标外泄**；构建解释前后 `JSON.stringify(plan)` **逐字节不变**（只读，不回写）。

**真实厨房的一个真实读法**（同批候选，解释层原文）：
- 可用候选：`共 1 条依据：命中 0 条、未命中 0 条、1 条判不出来。（生成期粗判：1/1 只按几何接触初判为"疑似满足"，仅供追溯，非最终结论）`
- 不可行候选：`被硬约束否决（不评分），有 2 处阻断（SPATIAL-CABINET-OPENING、DESIGN-CABINET-DOOR-SWING）`
- 规划级 `unresolved`：`协调枚举：墙「rK墙1」的空白区段容不下整组（组总宽 4500mm，缝 900mm）—— 不缩尺寸、不猜位置`

> 注意"1 条判不出来"：那是 `unavailable`（本阶段判不了），措辞**必须**是"判不出来"而不是"未满足"
> —— 这正是 D13 要防的"把判不出来写成没满足"。

## 六、本阶段新踩到的坑（写入记忆）

1. **`?? []` 不是多余的防御，是必需的诚实**：`buildCandidateExplanation` 初版写
   `p.satisfies.map(...)`，被 `verify:candidate-compare` 第 7 项（**手工构造的最小候选**，
   压根没有 `satisfies`）当场崩掉。教训：解释层必须容忍**上游给的最小对象**；
   并且"没有信号"要当 `[]`，**绝不能**当 `false` —— 那会把"没被问过"读成"不满足"（P9.4 点名的坑）。
2. **变异 harness 被 `| head` 掐死会留残留**：SIGPIPE 让 node 在 `finally` 还原之前退出，
   源码就停在变异态（本轮**实测发生过一次**）。补法不是"记得清理"，而是 harness **启动时
   用已知的 `to` 文本反推还原**（保留 CRLF）；已用"注入残留 → 自动还原 → md5 一致"实测验证。
3. **`typeof 未声明标识符` 不抛错**：变异补丁用它把"本层不许出现的标识符"塞进**实码**
   —— 既能被源码扫描抓住，又不会因 `ReferenceError` 把"崩溃"误判成"判红"。
4. **`git checkout -- app/verify/out/` 是提交前的固定动作**：`verify:ui` 会重写那批截图，
   不还原就会把几十个二进制 diff 带进提交（本轮再次命中）。
5. **验收脚本自己也要被"变异"验证**：新增 J 段的台账断言，其非空洞性由 P9.8 封板套件
   （49 / 55）从**生成侧**钉住同一批数字来交叉保证 —— 单靠"跑绿了"不足以说明它不是恒真。
