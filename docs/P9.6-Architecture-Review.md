# P9.6 架构审查（Multi-Candidate Compare UI）

> 阶段目标：把 P9.3 `CandidateLayout` + P9.4 `DesignScore` + P9.5 `PlannerPlan` 的**运行态**结果展示给用户，让用户手动选一份。
> 红线：不造 winner / 不自动 adopt / 不写 Semantic Model / 不写 Cabinet placement / 不新增自动布局 / candidate 不进 project.json。
> 本审查在写任何 UI 之前完成（用户 §一 要求"先做架构审查"）。

## 1. 运行态数据模型（已通读确认）

| 层 | 类型 | 关键字段 | 结论 |
|---|---|---|---|
| P9.3 | `CandidateLayout` | `id, status:'draft', sourceIntent[], placements[], explanations[], unresolved[]` | 候选只到 draft；坐标只在 `placements[].resolved`（由 `resolvePlacement` 唯一产出） |
| P9.4 | `EvaluatedCandidate` | `candidateId, fromStatus:'draft', lifecycle:'evaluated', score` | score 与 candidate 是**两份平行数组**，用 `candidateId` 关联 |
| P9.4 | `DesignScore` | `status:'valid'\|'infeasible', total:number\|null, totalKind, weights(null), components[], hardFailures[], preferenceMatches[], explanations[]` | infeasible ⇒ `total:null` + `components:[]`（不转低分） |
| P9.5 | `PlannerPlan` | `request, unresolved[], candidates: CandidateLayout[], scores: EvaluatedCandidate[], explanations[]` | **无 winner/adopt/apply/commit 字段** |

**确认点 1–4**：四类结构如上，Compare UI 消费它们即可，不需重算任何一项。

## 2. Compare 数据模型（新增纯 UI/运行态 DTO）

- 新增 `ui/panels/candidateCompare.ts` 里的 `CandidateComparison`：**只做关联与展示用投影**，绝不持有 `x/y/rotation/polygon`。
- 它 = `{ plan: PlannerPlan, byId: Map<candidateId, {layout, score}>, selectedCandidateId?: string }`。`selectedCandidateId` 是 UI/session 态，不进 project.json（红线 §十/§十一）。
- 不新增任何"确定性判定"：collision / wall contact / room relation / opening / door swing / score / preference 全部直接读 `plan` 里既有字段。

## 3. 现有 PlanRunView 是否可复用（确认点 5）

- `ui/panels/PlanRunView.tsx`：纯渲染 `PlanRun`（steps/diff/issues/impact），所有动作靠回调上抛，**不持有状态、不碰总线**。可复用其样式（`.plan-step`/`.diff-list`/`.btn-row`）。
- 但它消费的是 `PlanRun`（AI 动作清单的干跑结果），**不是 `PlannerPlan`**。所以不能直接把 `PlannerPlan` 塞给它。
- 决策：P9.6 新建 `CandidateComparePanel`，**复用 PlanRunView 的视觉元素类名与"只渲染、动作上抛"的纪律**，但不复用其组件（数据形状不同）。

## 4. 现有 Variant Compare UI（确认点 6）

- `ui/panels/VariantPanel.tsx` 是已有的"方案对比" UI，但它针对 **stylePresets 风格变体**（`VariantDraft → Cabinet`），`adopt` 走 `adoptVariant(d, project)`。
- ⚠ `core/variants.ts` 的 `adoptVariant(VariantDraft): Cabinet` 语义是"变体草稿 → 柜体"，与 P9.6"候选布局只引用已有柜、用户选一份后走既有 Plan/Draft 提交"语义**不同**（用户 §九 明确警示不可因名字相似复用）。
- 决策：P9.6 **不复用 `adoptVariant`**，也不复用 VariantPanel 的 adopt 逻辑。候选选择 → 进入既有 `dryRunPlan`/`commitPlan`（或 `draftSession`）。

## 5. 用户点击"选择"后如何进入既有提交链路（确认点 7）

- 既有链路（已通读）：`ai/planRunner.ts` 的 `dryRunPlan({bus, actions})` → `PlanRun` → `commitPlan(run, bus)`；多轮累积走 `ai/draftSession.ts` 的 `finalizeDraft`。
- 候选落地语义：一份 `CandidateLayout` 描述的是"把某只已有柜重摆到 `placements[].resolved`"。它等价于一条 `cabinet.place`（或带 placement 的 command）。
- 决策：Compare UI 的"选择此方案"按钮 → 回调 `onSelect(candidateId)` → 上层把该候选的 `resolved` 翻译成一条 `cabinet.place` 动作 → 走 `dryRunPlan` → `PlanRunView` 预览 → 用户确认 → `commitPlan`。**这是唯一提交路径**，不在 Compare UI 里建第二条。

## 6. sessionStorage 不会误存候选（确认点 8）

- 现有持久化扫描：`state/draftStore.ts`（localStorage 自动存 project 快照，`serializeProjectFile`）、`ai/knowledge/store.ts`、`ai/correctionStore.ts`、`ui/panels/AIPanel.tsx`（sessionStorage 存会话 CONVO_KEY/ROOM_KEY）、`ai/aiClient.ts`（sessionStorage 存 token）。
- 风险点：`draftStore` 序列化的是**真项目**，只要候选不进 `project.json`，就不会被它误存。
- 决策：`selectedCandidateId` 用**独立、显式前缀的 sessionStorage key**（如 `p96:selectedCandidate`），且只存 id（不存整个 candidate/score/comparison 对象）；刷新后仅恢复高亮，不恢复任何模型状态。candidate/score/comparison **永不**进 `project.json`（类型层也不支持，运行态只活在前端内存）。

## 7. AI 关系（§十二/§二十三）

- P9.6 不新增任何 AI 写入口。`ai/candidateScoreContext.ts`（只读、零坐标、不决策）已是 P9.4 的 AI 投影，P9.6 不改它。
- AI 契约里没有"评分入口/坐标/选择动作"——Compare UI 是纯前端消费，不影响 `shared/aiContract.mjs` 的动作清单（仍 21 条）。

## 8. 红线落地清单（实现时逐条核对）

| 红线 | 落点 |
|---|---|
| 不造 winner | `CandidateComparePanel` 不出现"最佳/推荐/winner/auto-select"文案；排序只用 `compareDesignScores()` 且旁注"显示排序，非 winner 判定" |
| 不自动 adopt/commit | 选中只改 UI 高亮 + session id；提交必须用户点"预览→确认" |
| 不写 Semantic Model / Cabinet placement | 候选描述只引用已有柜；落地经 `cabinet.place` 命令 + CommandBus |
| 不新增自动布局 | 候选来自 P9.3 枚举，Compare UI 零枚举 |
| candidate 不进 project.json | 运行态只在内存；selected id 仅 sessionStorage（独立前缀 key） |
| 复用既有提交链路 | 选中 → `dryRunPlan` → `PlanRunView` → `commitPlan`，不建第二条 |
| 不重算 | 只读 `plan.candidates/scores`，UI 不调 `detectCollisions`/`validateDesign`/`resolvePlacement`/评分 |
| 未知不猜 | `DesignScoreHit='unknown'` 原样显示（clear / 不折算 0 分），hard failure 原样传递 |
| 不复用 adoptVariant | 候选落地走 `cabinet.place` 命令，不调 `core/variants.ts` 的 `adoptVariant` |

## 9. §二十七 上游语义缺口（实现前先补最小必要语义）

- **玻璃门（F/G）**：`UnitSpec.doors.material?` 已支持 `kind:'glass'`（清单按材质分流到甲购件）。但 AI 编译链 `ai/compile.ts` 的 `doorIntentOf` 只返回 `{count}`，`makeUnit` 的 `doors` 不收 material → 玻璃门被降级成普通门。
  - 最小修复：在 `shared/aiContract.mjs` 的 `cabinet.create` 与 unit 模式加 `doorMaterial`（引用 `RuleSet.materials`）；`doorIntentOf(count, material?)` 透传；`makeUnit({..., doors:{count, material}})`。建立 requested=compiled 不变量（玻璃门材质原样保留）。
- **上下分区（A/C/D）**：示例"下2抽屉上2层板"用**显式行高**表达（`[{height: H1, units:[drawerBank×2]}, {height: H2, units:[shelves×2]}]`），**不写两个 `'fill'`**（P1 会拒）、**不靠 50/50 均分**（`aiContract.mjs` 的"height 不给=各行均分内高"是另一机制，本示例明确给高，避开它）。数量≠高度：抽屉/层板数来自 `count`，与行高无关。
- **禁止项**：不放松 P1 `fill`（仍只许一个且末行）；不默认 50/50；不自动猜高度；不把普通门伪装成玻璃门；不改旧测试；不在 Compare UI 做补偿逻辑。

## 10. 入口位置（实现）

- `ui/panels/AIPanel.tsx`：在 AI 规划结果处新增"规划候选对比"触发——当 AI 产出 `PlannerRequest`（或用户手动点"生成候选对比"）时调用 `planCandidates(project, request, entries)` 得到 `PlannerPlan`，传给 `CandidateComparePanel`。
- 触发参数：默认 `scope:'room'`（或项目），读 `activeDesignIntents` 作为枚举目标。无 active 意图时 `planCandidates` 天然返回空候选（如实），UI 显示"没有生效的设计意图，无法枚举候选"。
