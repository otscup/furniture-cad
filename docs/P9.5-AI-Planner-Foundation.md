### 1.2 `DesignProposal` 能不能表达「一个完整设计计划」？

**不能，而且不应该让它表达。**

`DesignProposal` 的语义是"**从无到有**建一批柜"：它的每个 `ProposalCabinet` 都会编译成 `cabinet.create`。
它回答的是"要建哪些柜"。

Planner 要回答的是"**已有的这批柜**，在这些设计目标下可以怎么摆、摆了会怎样"。它
**不新建任何柜**（新建 = `Cabinet` 的一等公民变化 = 触碰 Semantic Model），只引用 id。

两者的输出也不同：Proposal → `AiAction[]`（要执行）；Planner → `PlannerPlan{请求, 候选, 评分, unresolved}`（只给人看）。
**结论**：`DesignProposal` 不是 Planner 的载体；Planner 另建一个纯语义的临时对象。二者共用的是
**"AI 只出语义、确定性层决定工程"** 这一条原则，而不是同一个类型。

### 1.3 `CandidateRequest` 当前能不能覆盖多柜场景？

形状上**能**（`cabinetIds?: string[]`），语义上**不够**，两处缺口：

1. **表达不了"这次规划想达到哪些方向"**。它只有 `intentIds`（引用已确认的意图），没有"目标方向"这一层 ——
   而 §四 要求 AI 能说出"请为厨房里这些柜体生成满足*这些*意图的方案"。用户真实的一句话往往
   **先有方向（"想让厨房走起来顺手、柜子尽量靠墙"）**，意图是方向被确认后的产物。
   AI 若能给出方向词，系统就能把"这次该枚举什么"限定住（`generationGoals`）。
2. **没有显式的规模上限**。`maxCandidates` 限的是"每个目标出几条候选"，**不限"这份请求覆盖多少只柜"**。
   一次规划覆盖 200 只柜在形状上是合法的 —— 枚举成本与给模型看的上下文都会失控。

**结论**：`candidateRequest` **不够**。新增一个**最小**的 `plannerRequest`（见 §1.9），
`candidateRequest` **原样保留**（P9.3 已发布，不静默改语义）。

### 1.4 P9.3「一次只重摆一只柜」是否已经成为瓶颈？

**分两件事看，混在一起就会得到一个假的"是"。**

- **"一份候选只描述一只柜"** —— 这是**对的**，不是瓶颈。一份候选 = 一个可比较的具体摆法；
  把三只柜的不同组合塞进一份候选，"这份好在哪"就说不清了。
- **"一次规划只能覆盖一只柜"** —— 这在 P9.3 **并不成立**：`generateCandidateLayouts` 早已对
  `intent × 目标柜` 双层循环（`targetCabinets()` 会返回 scope 内的**全部**柜体），
  同一次调用对 3 只柜会产出 3 组候选。**P9.5 不需要新写生成器**。
- **真正的缺口（现在就有，且本阶段不假装补上）**：候选是**逐柜独立**枚举的 —— 它不会生成
  "把 3 只柜作为**一个整体**同时挪"的联合方案（那需要组合搜索/约束求解）。
  本阶段的处理是**如实登记**：`PlannerPlan.unresolved` 里写明
  "本层逐柜独立枚举，不生成整体联动方案"。
  **不猜、不补启发式、不把"逐柜最优"冒充成"整墙最优"。**

### 1.5 P9.4 `candidateScore` 如何进入 planner context

三条硬纪律（与 §十二 一致）：

1. **它是系统算出来的**（`scoreCandidateLayoutSet`），AI 只能**读**。Planner 上下文里它是
   `readOnly: true` 的投影，**没有**任何写回通道；AI 也无法"把自己上一轮的判断注入评分"——
   评分层不接受任何来自 AI 的输入（它的入参只有 `project / layout / entries`）。
2. **不让 AI 重定义 `score` / `weight` / `feasibility`**：`candidateScore` 投影里只有
   结论码与计数（`status` / `total` / `unavailable` / `hardFailures[].code`），
   **没有** `weights`、没有 component 明细可以"改"，也没有任何可以提交回去的字段。
3. **三个只读块合成规划输入**，由 `ai/plannerContext.ts` 的 `buildPlannerContext(snapshot)`
   提供 —— 它是**视图**（取快照上已有的三个键），**零新增计算**，
   并有一条断言钉死"它 == 快照的那三个键逐字节相同"（防它偷偷长出自己的判定）。

### 1.6 ★ `MAX_ACTIONS = 12` 专项：这是架构问题，不是数字问题

#### (a) 限制在哪

```
shared/aiContract.mjs:36   export const MAX_ACTIONS = 12;
shared/aiContract.mjs:938  if (list.length > MAX_ACTIONS) { return { ok:false, error: `…超过上限 ${MAX_ACTIONS} —— 请把需求拆成几步说` } }
```
它只有**一处**实现，作用于 `validatePlan`（AI 一轮输出的**动作**条数）。
`MAX_ACTIONS` 与 `cabinet.create` 的 `count`（1–12）、`DESIGN_INTENT_PROPOSAL_MAX` 是三个独立的东西，不要混。

#### (b) 为什么 6 柜布局正好触顶

一个"整墙 6 柜"的提案，编译产物是：

```
6 × cabinet.create      （每只柜 1 条）
6 × cabinet.place       （每只柜 1 条 —— 落位必须在 create 之后，且 cabinet.create 不接受 placement）
= 12 条
```

**12 条正好等于上限**：0 余量。用户下一句"顺便把台面加高一点"或"第 7 只柜" → 13 条 → **整份被拒**。
根因不是 12 太小，而是 **"一只柜要花 2 条动作"**（建 + 摆），于是 N 柜布局的固定成本是 2N。

#### (c) 溢出时的现有行为（先确认，再决定要不要改）

`validatePlan` 在超限时**返回 `ok:false` 且 `actions: []`** —— 即
**整份拒绝，绝不截断、绝不丢柜**。`requestPlan` 还会把它拼成人话 error 交给界面。

> **所以「不得静默截断 / 不得静默丢柜」这两条，现有实现已经满足**（是硬拒，不是截断）。
> 本阶段的验收是把这条性质**钉死**（负样本：13 条 → 必须 ok:false 且 actions 为空），
> 而不是去"修"一个不存在的 bug。

#### (d) 三个候选方案与裁决

| 方案 | 内容 | 代价 / 风险 | 裁决 |
|---|---|---|---|
| **A. Planner Plan 分批执行** | 规划产出 > 上限 时，按**依赖闭包**确定性地拆成若干批，每批 ≤ 上限；**每批各自**走 `dryRunPlan → 预览 → commitPlan` | 每批各是一次原子提交（多批之间不是原子的）；需要"不许把 create 和它的 place 拆开"的分组逻辑 | ✅ **采用** |
| **B. 新增高层批量语义动作**（如 `cabinet.createBatch`） | 一条动作建 N 只柜 | 要新增 CommandBus 命令 + 白名单 + 编译器 + 迁移；**改动唯一写入口**，是 P9.5 之外的大手术 | ❌ 本阶段不做 |
| **C. 扩大 action budget**（12 → 100） | 改一个常数 | 该上限的原用途是"**限制单轮 AI 能改多少模型**"（防"顺手重排整套房子"）。数字一涨，**单轮最大破坏面同比放大**；而且它只解决"条数"，不解决"一次提交的爆炸半径" | ❌ **拒绝**。原因见下 |

**为什么不能简单把数字改大（正面回答 §七 的要求）**

- **原限制用途**：单轮 AI 输出的动作条数上限 = **单次预览/提交的影响面上限**。
  它同时约束三件事：模型的输出长度（`DEFAULT_MAX_TOKENS` 的注释直接引用它）、
  用户一次要复核的 diff 规模、以及"一条坏计划能造成多大破坏"。
- **若改大所需的新依据**：需要一个**与影响面挂钩**的指标（例如"受影响柜体数 ≤ N"），
  而不是"条数 ≤ N"—— 但现在**没有**这样一个指标，也没有证据支持任何具体数字。
- **风险**：把 12 改成 100，等于把"一次点应用最多动 12 步"变成"最多动 100 步"，
  **用户复核能力与回滚粒度同时退化**，而这三条不变量正是本项目最贵的东西：
  `preview === commit`、`plan 的原子性`、`undo/redo 语义`。
- **回归测试**：本阶段**不提供**"扩大数字"的回归，因为**不扩大**。提供的是**分批**的回归
  （见 §十九 的 44–48 项断言）。
- **为什么这不是绕过安全限制**：分批**没有**放宽任何一条限制 —— 上限仍是 12，
  每一批仍然整份通过/整份拒绝，仍然 `preview === commit`。
  它只是把"一次说不完"变成"分几次说清楚"，**影响面反而更小**（每批更小）。

#### (e) 采纳方案 A 的具体形态（本阶段实现）

`ai/actionBudget.ts`（**纯函数**，不 import 总线、不改模型）：

```ts
planActionBatches(actions, limit = MAX_ACTIONS)
  → { count, limit, fits, overflow, batches, unsplittable, note }
```

- **依赖闭包分组**：`cabinet.create` 带 `ref: R`，后续动作用 `$ref:R` 引用它（`target` 或 `params`）。
  把"定义 R 的动作"和"所有引用 `$ref:R` 的动作"**放进同一组**（并查集，传递闭包）。
  分组内顺序 = 原顺序；组间按"组内最小下标"升序。
- **贪心装箱**：按组顺序装箱，每组整体放进当前批；装不下就开新批。**永不拆组、永不丢动作**。
- **装不下就说装不下**：若**单个组**就 > limit（例如 20 只柜的 create 全被后面的 place 引用），
  返回 `unsplittable: true` + `note`，**绝不从中截断**。
- **不改 `MAX_ACTIONS`**：`ACTION_BUDGET = MAX_ACTIONS`（同一处真相的再导出）。

**与 `draftSession` 的关系**：每一批就是一次普通的 `dryRunPlan → commitPlan`（或一轮 `addDraftRound`），
所以分批**不需要**任何新的执行机制 —— 这正是方案 A 胜过 B/C 的地方。

### 1.7 `draftSession` / `PlanRun` 是否适合承载 Planner

**适合承载"多批执行"，不适合承载"规划"本身。**

- `PlanRun` / `DraftSession` 是**动作侧**的载体（它们的元素是 `AiAction` / `PlanStep`）。
  Planner 的产出是**语义侧**的（`PlannerPlan`），两者不同层。
- 但方案 A 需要的"多批"**正好落在** `DraftSession` 的既有语义上：多轮、每轮独立干跑、
  累积 `steps` 后一次 `finalizeDraft`。所以**不新造** `plannerApply / plannerCommit / plannerExecutor`
  —— Planner 只产出**批计划**（`batches: AiAction[][]`），执行仍由既有链路做。
- 本阶段**不接线 UI**：Planner 只到"产出批计划 + 说明"。执行是既有 UI + 既有两个入口的事。

### 1.8 是否已有可复用的批量计划载体

- 有：`CandidateLayoutSet`（P9.3，已支持多柜 × 多候选）、`EvaluatedCandidate[]`（P9.4，已支持整批评分）。
  → Phase B **直接复用**，无新生成器。
- 有：`PlanRun` + `DraftSession`（多步/多轮）→ 方案 A 直接复用，无新执行器。
- 没有：**规划请求**这一层的载体（现在的 `candidateRequest` 是候选层，不是规划层）。
  → 这是 P9.5 唯一需要新建的东西。

### 1.9 Planner 的输出模型（与契约的最小增量）

**Phase A 输出（AI → 系统）—— 新增 `plannerRequest`（不是 action）**

```
{ scope, intentIds?, cabinetIds?, generationGoals?, maxCandidates? }
```
- `scope`：`'room' | 'project'`（与 `candidateRequest` 同口径；房间由意图/柜体的 scope 派生，不新增 `roomId` 字段）。
- `generationGoals`：**目标方向词**（9 词闭集），语义校验在 core 层做（契约只管形状）。
- **类型层禁止几何**：`PlannerRequest` 混入一个 `x?: never; y?: never; rotation?: never;
  polygon?: never; wallId?: never; wallStart?: never; wallEnd?: never; …` 的
  `PlannerGeometryForbidden` —— **赋一个数就编译不过**（与 P9.2 把 `'system'` 从联合里拿掉同一手法）。
- **`unresolved` 不在请求里**：AI **不许**自己声明"哪些解决不了"（那等于让模型编造系统状态）。
  它由系统在 Phase B 填进 `PlannerPlan.unresolved`。这是 §三 的一处**有意偏离**，理由见 §1.11。

**Phase B 输出（系统 → 人）—— `PlannerPlan`**

```
PlannerPlan { request, unresolved[], candidates: CandidateLayout[], scores: EvaluatedCandidate[], explanations[] }
```
**没有** `winner` / `best` / `recommended` / `adopted` —— 类型层与导出面都没有。

### 1.10 四类硬保证（Planner 不是第二真相源）

| # | 保证 | 落点 |
|---|---|---|
| ① | **类型保证**：请求里写不出坐标/多边形/墙端点；计划里没有 Cabinet | `PlannerGeometryForbidden` + `PlannerPlan` 只含 `CandidateLayout` / `EvaluatedCandidate` |
| ② | **写保证**：`core/planner` 不 import `commandBus` / `aiClient` / `export` / `manufacturing` | 源码扫描断言 |
| ③ | **路由保证**：候选坐标仍**只能**来自 `resolvePlacement`（P9.3 已钉）；Planner 不自己算 | 复用 P9.3 链 + 断言 `planCandidates` 不出现任何几何算法 |
| ④ | **无 adopt**：导出面无 `winner/best/recommended/pick/adopt/apply/commit/persist` | 导出面扫描断言 |

### 1.11 本阶段做 / 不做

**做**
- `core/planner/`：`PlannerRequest` / `PlannerPlan` 模型 + 语义归一化 + `planCandidates()`（Phase B 编排）。
- `ai/plannerContext.ts`：三个只读块的组合视图（零新增计算）。
- `ai/actionBudget.ts`：`MAX_ACTIONS` 的**分批方案**（依赖闭包分组 + 贪心装箱 + 不可拆时如实说）。
- `shared/aiContract.mjs`：`PLANNER_REQUEST_KEYS` / `PLANNER_LIMITS` / `validatePlannerRequest` + 提示词一段；**动作清单仍 21 条**。
- `verify:ai-planner`：§十七 的 48 项 + 变异哨兵自检。

**不做**（严格停在 P9.5）
- 不改 `MAX_ACTIONS`；不新增 Command；不改 `types.ts` / `schemaVersion`；不写 `project.json`；不进 Knowledge。
- 不碰 Resolver / Spatial Truth / Manufacturing / DXF / Vision。
- 不做候选 Compare UI、winner UI、自动 adopt、选方案落盘 —— 全部留 P9.6。
- 不把 Planner 的产物接进 UI 主流程（本阶段它可被调用、可被验收，但不是界面主线）。
- **`unresolved` 的有意偏离**：用户给的 `PlannerRequest` 形状里含 `unresolved`，
  但本实现把它放在 **`PlannerPlan`（系统产出）** 而不是 **`PlannerRequest`（AI 输入）** ——
  理由：AI 声明"哪些没解决"就是让模型编造系统状态（P9.2 已为此把 `'system'` 从 origin 里拿掉）。
  两者都有 `unresolved` 这个**语义位置**，只是归属在系统的产出侧。

### 2.2 关键实现决策

**① `plannerRequest` 是"请求"不是"动作"**

契约里新增的是一条**请求通道**，与 `candidateRequest` 同级，**不进 `ACTIONS`** ——
动作清单仍是 21 条（断言 60 钉住）。理由：它不改模型，所以它不该出现在"可提交动作"这个集合里；
一旦进去，"规划"与"落地"就混成同一件事，两段式的第一段就不存在了。

**② 契约只管形状，语义归 core**

`validatePlannerRequest()`（纯 JS、前后端共用）只判：是不是对象、有没有几何键、有没有契约外键、规模是否超限。
"这些 id 在这个项目里真的存在吗 / 是 active 吗 / 目标词在闭集里吗"全在 `core/planner/request.ts` ——
它要读项目，而契约不该依赖项目。分层做，不重复。

**③ 规模超限 = 整份拒绝，不裁剪**

`intentIds > 12` / `cabinetIds > 24` / `goals > 9` 一律 `ok:false`。
砍掉几条 = 用户以为整屋都规划了，实际只处理了前 24 只 —— **静默丢柜是最坏的一种**，
与 `MAX_ACTIONS` 的处理同一口径：宁可明确说不，不许悄悄少做。

**④ 阈值陷阱（审查之外的实测发现）**

`generateCandidateLayouts()` 把 `intentIds` 为空读成"用全部 active" —— 那是它对"没给筛选条件"的合理口径。
但 `planCandidates()` 把 `generationGoals` 收窄后可能筛出**空集**，此时若原样下传，
系统会**静默扩大范围**按整屋规划。所以 `planCandidates()` 在 `effectiveIds.length === 0` 时**提前返回**，
明确说"没有可枚举的目标"（断言 43d 钉住）。这是"两处各自都合理、拼起来是错的"的典型，
靠断言而不是靠注释钉住。

**⑤ Planner 不读 Knowledge，只转发**

`planCandidates(project, raw, entries)` 把 `entries` **原样转发**给 P9.4 评分层，
由 `resolveKnowledge()` 决定谁能进 `applicable`。`core/planner` **不 import** 解析器 / 存储
（断言 30d 扫 import 行钉住）。这样"哪条偏好在生效"只有一处判定。

**⑥ 导出面本身是一条纪律**

`core/planner/index.ts` 只 re-export 三个文件。`PlannerPlan` 里没有 `winner` 字段，
导出面里没有 `pickBest` / `adoptPlan`（变异 V8 / V9 实测能红）。

### 2.3 ★ 用户盯的第一处：`MAX_ACTIONS = 12`

**结论：数字一个字节没改；问题按架构问题处理。**

- 现状核实：`MAX_ACTIONS = 12`（契约第 36 行）；`validatePlan` 超限时 `ok:false` + `actions: []`（**整份拒绝，不截断**）。
  一只柜 = 2 条动作（`cabinet.create` + `cabinet.place`）⇒ **6 柜正好 12 条、0 余量**，第 7 只柜即 13 条被拒。
  根因不是 12 太小，是 **2N 的固定成本**。
- 采纳方案 **A（依赖安全的分批）**：`actionBudget.planActionBatches()`
  按 `$ref` **依赖闭包**（并查集）分组 → 贪心装箱 → 每批各走一次**既有**的
  `dryRunPlan → 预览 → commitPlan`（执行链路一行都没改）。
  单组自身超限 ⇒ `unsplittable: true`（**不给假批次**，也不从中截断）。
- 明确**拒绝**方案 B（新增高层批量命令：要动唯一写入口与两段式原子性）与方案 C（把数字改大：
  放大单轮破坏面、用户复核能力与回滚粒度同时退化）。
- 分批**没有放宽任何限制**：上限仍是 12、每批仍整份通过或整份拒绝、仍 `preview === commit`，
  且**每批更小、影响面更小**。
- 断言钉住：45（6 柜正好装下）/ 46（7 柜触发分批）/ 47（**一条不少、顺序不变**）/
  48（每只柜的 create 与 place **同批**）/ 48b（不可拆时如实说不拆）/ 48c（超限整份拒绝）/
  48d（12 条不再被拒）/ 48e（每批都 ≤ 上限）。
- 变异钉住：V10 把装箱改成"丢弃装不下的组" ⇒ 46 / 47 / 48 **同时变红**。

### 2.4 ★ 用户盯的第二处：AI Planner ↔ Candidate Generator 的边界

**一句话：Planner 只决定"该枚举什么"，坐标与判定一个都不归它。**

| 环节 | 唯一实现 | Planner 的角色 | 钉住它的断言 |
|---|---|---|---|
| 枚举候选 | P9.3 `generateCandidateLayouts()` | 传 `CandidateRequest`（scope / intentIds / cabinetIds / maxCandidates） | 12（与直接调生成器**逐字节相同**） |
| 算坐标 | P9.3 内的 `resolvePlacement()` | 完全不出现 | 13（每条坐标 == resolver 输出）、13b（生成器源码里真有调用点） |
| 判碰撞 | `detectCollisions()` | 完全不出现 | 14（候选 `issues` 与真实调用**逐字节相同**） |
| 判门扇净空 | P8.9 | 完全不出现 | 17b（判不出 ⇒ `hit:'unknown'`） |
| 评分 | P9.4 `scoreCandidateLayoutSet()` | 传 `entries`，不读它 | 15（与直接调用**逐字节相同**） |
| 选方案 | **没有** | 不做 | 41 / 42 / 37b（导出面无 winner/adopt） |

变异钉住：V4 让 `plan.ts` 自己把坐标 +5 ⇒ 12 / 13 变红；
V6 把 `entries` 一律当 active 转发 ⇒ 27 / 28 变红；
V7 让计划里擅自默认门向 ⇒ 19 变红；V7b 把假设写进模型 ⇒ 19b 变红。

### 2.5 `unresolved` 归属：一处有意偏离（已在 §1.11 记录）

用户给的形状是 `PlannerRequest { …, unresolved }`。实现里 `unresolved` 放在 **`PlannerPlan`**（系统产出），
`PlannerRequest`（AI 输入）里**没有**这个键 —— AI 声明"哪些没解决"等于让模型编造系统状态。
契约层因此把 `unresolved` 判为 `EXTRA_KEY` 拒收。两者语义位置相同，只是归属在产出侧。

### 2.8 遗留 / 明确不做（P9.6 及以后）

- 逐柜独立枚举 ⇒ **不做整体联动方案**（组合搜索）。本阶段**如实登记进 `unresolved`**，

- 候选 Compare UI / winner UI / 自动 adopt：**全部未做**（§一.11 明列为不做）。
